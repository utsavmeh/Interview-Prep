# Comprehensive Study Guide: Rack Middleware in Ruby on Rails

> **Role:** Senior Staff Engineer / Rails Core Contributor / Interview Coach
> **Topic:** Rack Middleware
> **Target Audience:** Senior/Staff Backend Engineer Candidate

---

## 1. Overview

### What it is
Rack Middleware is a component that sits between the web server (e.g., Puma, Unicorn) and the Ruby web application (e.g., Rails, Sinatra). It implements the Rack specification, acting as a filter or interceptor. It processes incoming HTTP requests before they reach your application's routing/controllers, and processes outgoing HTTP responses before they are sent back to the client.

### Why it exists
Middleware exists to enforce the **Separation of Concerns (SoC)** at the HTTP boundary. Instead of bloating your Rails application with generic HTTP processing logic (like parsing JSON, handling CORS, logging, or rate limiting), you extract these into composable, reusable, and framework-agnostic Rack middleware. It provides a modular pipeline.

### When to use it
- **Pre-processing requests:** Authentication checks (e.g., Warden), IP blocking, rate limiting (`Rack::Attack`), parsing custom payloads, setting request IDs for tracing.
- **Post-processing responses:** Gzip compression, adding security headers (HSTS, CSP), ETag generation, CORS headers (`Rack::Cors`).
- **Short-circuiting requests:** Serving static assets (`ActionDispatch::Static`), maintenance mode pages, returning 404 for bad routes before booting the Rails engine.

### Common misconceptions
- **"Middleware is a Rails concept."** *False.* Middleware is a Rack concept. Any Rack-compliant framework (Rails, Sinatra, Hanami, Roda) uses them.
- **"Middleware only alters headers."** *False.* Middleware can alter the body, halt the request entirely, rewrite the URL, or redirect the user.
- **"Rails Controllers and Middleware are interchangeable for logic."** *False.* Middleware operates on the raw HTTP level (the `env` hash). Controllers operate in the Rails domain space (with access to `params`, `session`, `ActiveRecord`). Domain logic belongs in Controllers/Services; generic HTTP transport logic belongs in Middleware.

## 2. Core Concepts

### The Rack Contract
To be a valid Rack application or middleware, an object must:
1. Respond to `#call`.
2. Accept a single argument: `env` (a Ruby Hash containing CGI-like headers and Rack-specific variables).
3. Return an Array of exactly three elements: `[status, headers, body]`.
    - `status`: Integer (e.g., `200`, `404`).
    - `headers`: Hash of HTTP headers (keys and values must be Strings; Rack 3 enforces Arrays for multiple values).
    - `body`: An object responding to `#each` that yields Strings (or an Array of Strings).

### The `env` Hash
This is a mutable dictionary representing the HTTP request. Key variables include:
- `REQUEST_METHOD`: "GET", "POST", etc.
- `PATH_INFO`: "/users/1"
- `QUERY_STRING`: "sort=asc"
- `rack.input`: An IO-like object containing the raw HTTP request body.
- `HTTP_...`: Headers sent by the client (e.g., `HTTP_USER_AGENT`).

### The Middleware Stack (The Onion Architecture)
Middleware forms a pipeline. Middleware A wraps Middleware B, which wraps Middleware C, which wraps your Rails app. The request flows *in* through the layers, hits the app, and the response flows *out* through the layers in reverse order.

## 3. Internal Working & Lifecycle Step-by-Step

Let's trace a request from Nginx to Rails and back.

1. **TCP Socket:** Nginx accepts a TCP connection and reverse-proxies the HTTP payload to Puma via a Unix domain socket or port.
2. **Web Server Parsing (Puma):** Puma reads the HTTP text and parses it into the Rack `env` hash.
3. **Application Invocation:** Puma calls `Rails.application.call(env)`. (`Rails.application` is the outermost Rack app).
4. **Middleware Traversal (Inbound):** 
   - Rails uses `ActionDispatch::MiddlewareStack`. It iterates through its array of middleware.
   - `Middleware1#call(env)` is invoked. It might mutate `env` and then calls `@app.call(env)`, passing control to the next middleware.
   - `Middleware2` intercepts, maybe checks rate limits. If rate limit exceeded, it returns `[429, {}, ["Too Many Requests"]]` and the chain halts (Short-circuiting).
   - If not halted, the chain continues until the bottom.
5. **The Rails Router:** The "bottom" of the stack is `ActionDispatch::Routing::RouteSet`. It matches `PATH_INFO` to a Controller action.
6. **Controller Execution:** The Controller processes the request and generates a response. The Router translates this back into a Rack response `[status, headers, body]`.
7. **Middleware Traversal (Outbound):** 
   - The stack unwinds.
   - `Middleware2` receives the response array. It does nothing and returns it up.
   - `Middleware1` receives it, perhaps adds a `X-Frame-Options` header, and returns the modified array.
8. **Web Server Response (Puma):** Puma receives the final `[status, headers, body]`. It serializes this back into a raw HTTP response string and writes it to the socket.

## 5. Real Production Examples

1. **`Rack::Attack`**: Standard for rate-limiting and throttling based on IP, user ID, or path. It prevents brute-force attacks at the middleware layer, saving DB connections.
2. **`Warden`**: The engine behind Devise. It sits in the middleware stack, intercepts requests to check sessions, and injects the `warden` object into the `env` hash so controllers can access `current_user`.
3. **`ActionDispatch::RequestId`**: Generates a unique `X-Request-Id` UUID for every request. This is critical for distributed tracing in microservices (e.g., passing the ID to Datadog/NewRelic logs).
4. **`Rack::Cors`**: Intercepts `OPTIONS` preflight requests from browsers and responds immediately with allowed origins/methods without ever booting Rails routing.
5. **`Rack::Timeout` (Heroku's classic)**: Raises an exception if a request takes longer than a specified time. *(Note: Highly controversial due to Ruby threading issues, often considered an anti-pattern now compared to DB/HTTP client timeouts).*

## 6. Common Mistakes

### Junior Developers
- **Putting Business Logic in Middleware:** Writing `User.create(env['params'])` inside middleware. Middleware should not know about ActiveRecord models if possible.
- **Forgetting `@app.call(env)`:** If you don't call the next app in the chain, the request never reaches the Rails router, resulting in blank pages or hanging requests.
- **Incorrect Header Modification:** Trying to modify `env['HTTP_AUTHORIZATION']` using symbols instead of strings. Rack strictly requires String keys.

### Mid-Level Developers
- **Not Rewinding `rack.input`:** If you read the request body in middleware (e.g., to log a JSON payload) using `env['rack.input'].read`, the IO pointer is at EOF. The Rails controller will receive an empty params hash. **Fix:** Always call `env['rack.input'].rewind` after reading.
- **Not Closing the Body:** If you intercept and replace the response body, you MUST call `#close` on the original body if it responds to it. Failing to do so causes memory/file descriptor leaks.

### Senior/Staff Developers
- **THREAD SAFETY VIOLATIONS (The Deadliest Sin):**
  Middleware instances are created **ONCE** during application boot. The `#call` method is executed concurrently by multiple threads (in Puma). 
  *Mistake:* Using instance variables (e.g., `@current_user = ...`) to store request state. This creates race conditions where User A's data leaks to User B. 
  *Fix:* Only use local variables inside `#call`, or store request-specific state in the `env` hash.
- **Buffering Large Responses:** Reading the entire response body into a String to modify it destroys streaming capabilities and causes memory spikes on large file downloads.

## 7. Performance Considerations

- **Latency Overhead:** Every middleware in the stack adds microseconds to *every single request*, even static file requests. A bloated stack (50+ middlewares) noticeably degrades TTFB (Time to First Byte).
- **String Allocations:** In high-throughput APIs, poorly written middleware allocating unnecessary strings or arrays inside `#call` will trigger the Ruby Garbage Collector frequently. Use frozen string literals and mutate carefully.
- **Streaming & Memory:** If your middleware intercepts the response body:
  ```ruby
  # BAD: Loads whole response into memory
  body_string = ""
  body.each { |chunk| body_string << chunk } 
  ```
  This breaks HTTP streaming (ActionController::Live). If you must modify the body, use a proxy object that yields modified chunks via its own `#each` method.

---

## 8. Security Considerations

- **Sanitization:** Middleware is the best place to sanitize malicious input (e.g., stripping invalid UTF-8 bytes) before it hits the application's XML/JSON parsers (preventing CVEs).
- **Information Leakage:** Custom error-handling middleware must be careful not to leak stack traces or internal IP addresses in production responses.
- **Timing Attacks:** If writing custom authentication middleware (e.g., verifying HMAC signatures), use `Rack::Utils.secure_compare` (constant-time comparison) to prevent timing attacks.

---

## 9. Debugging

1. **Viewing the Stack:** Run `bin/rails middleware` in your terminal. This shows the exact ordered list of middleware.
2. **Insertion Points:** When debugging why a middleware isn't working, check its order. If your CORS middleware is inserted *after* authentication, preflight requests will fail with 401 Unauthorized. Use `config.middleware.insert_before` or `insert_after`.
3. **Prying into `env`:** Insert `binding.irb` or `byebug` inside the `#call` method to inspect the raw `env` hash before Rails alters it.
4. **Profiler:** Use `rack-mini-profiler`. It injects itself at the top of the stack and measures the time taken by the rest of the stack.

---

## 10. Best Practices

1. **Pure Functions (Mostly):** Treat `#call` as a pure function as much as possible. Inputs (`env`), outputs (`[status, headers, body]`). No shared mutable state.
2. **Defensive Programming:** Never assume specific headers exist. Handle `nil` gracefully.
3. **Use `Rack::Request` and `Rack::Response`:** Instead of raw array manipulation, use `req = Rack::Request.new(env)` to easily parse params, IPs, and cookies. Use `res = Rack::Response.new` to build the return array cleanly.
4. **Namespace `env` variables:** If you add custom data to `env`, namespace it to avoid collisions: `env['company_name.tenant_id'] = 123`.

---

## 11. Anti-patterns

1. **The "God" Middleware:** A single `RequestProcessor` middleware doing auth, metrics, logging, and tenant resolution. Split them up.
2. **Using Exceptions for Control Flow:** Raising a custom exception in middleware just to catch it in another middleware to render a 404. Use standard Rack responses `[404, {}, ['Not Found']]` to halt the chain elegantly.
3. **Modifying Frozen Objects (Rack 3):** Rack 3 heavily utilizes frozen strings and arrays. Mutating `env` values in place without duplicating them first will cause `FrozenError`.

## 12. Interview Questions

### Basic
**Q:** What is the required interface for a Rack application?
**A:** An object responding to `#call(env)` returning `[status, headers, body]`.

### Intermediate
**Q:** How do you halt a request in middleware without hitting the Rails controller?
**A:** Simply return a valid Rack response array and *do not* call `@app.call(env)`.
```ruby
def call(env)
  if env['PATH_INFO'] == '/health'
    return [200, { 'Content-Type' => 'text/plain' }, ['OK']]
  end
  @app.call(env)
end
```

### Senior
**Q:** You wrote a middleware to log the raw JSON request body. After deploying, controllers are raising errors saying `params` are empty. Why?
**A:** The `env['rack.input']` object is an IO stream. When the middleware read it, the pointer moved to the end of the file (EOF). When the Rails router later tries to parse the JSON, there is nothing left to read. I must call `env['rack.input'].rewind` in the middleware after reading.

### Staff/Architect
**Q:** We want to add a middleware that tracks active requests per user to prevent concurrent request abuse. How would you design this for a distributed system running across 50 Puma instances, and what are the performance/thread-safety implications?
**A:** 
1. **State:** We cannot use instance variables or class variables because state must be shared across 50 independent Puma processes (and their threads). We need an external datastore like Redis.
2. **Logic:** In `#call`, extract user identifier (e.g., from session/JWT). Increment a Redis counter (using INCR or a Lua script for atomicity) with a TTL. If > limit, return 429. If not, yield to `@app.call`. In an `ensure` block, decrement the counter.
3. **Performance:** Redis adds network latency to *every* request. We should pipeline the Redis commands or use a local memory store (like Memcached/Redis on localhost) or use a probabilist approach if exact counts aren't critical.
4. **Thread Safety:** The Redis client connection pool must be thread-safe (e.g., using `ConnectionPool` gem) since Puma is multi-threaded.

## 13. Practical Coding Examples

### Example 1: Thread-Safe Request Timer (Standard Pattern)
```ruby
class RequestTimer
  def initialize(app)
    @app = app
    # Only initialization config goes here
  end

  def call(env)
    start_time = Process.clock_gettime(Process::CLOCK_MONOTONIC)
    
    status, headers, body = @app.call(env)
    
    end_time = Process.clock_gettime(Process::CLOCK_MONOTONIC)
    duration = ((end_time - start_time) * 1000).round(2)
    
    # Safely modify headers (Duplicate to avoid frozen errors)
    headers = headers.dup
    headers['X-Request-Duration-Ms'] = duration.to_s
    
    [status, headers, body]
  end
end
```

### Example 2: The Dangerous Stateful Middleware (DO NOT DO THIS)
```ruby
class BadMiddleware
  def initialize(app)
    @app = app
  end

  def call(env)
    # DISASTER: @user is shared across all Puma threads!
    # User B might see User A's data!
    @user = find_user(env) 
    
    if @user.banned?
      [403, {}, ["Banned"]]
    else
      @app.call(env)
    end
  end
end
```

### Example 3: Body Proxy (Streaming Safe)
How to modify the body without buffering the whole thing in memory.
```ruby
class UpcaseBodyProxy
  def initialize(body)
    @body = body
  end

  # Respond to each, yielding modified chunks
  def each
    @body.each { |chunk| yield chunk.upcase }
  end

  # Ensure the original body is closed to prevent leaks
  def close
    @body.close if @body.respond_to?(:close)
  end
end

class UpcaseMiddleware
  def initialize(app); @app = app; end

  def call(env)
    status, headers, body = @app.call(env)
    [status, headers, UpcaseBodyProxy.new(body)]
  end
end
```

## 14. Edge Cases

- **Rack 3 Header Arrays:** In Rack 3, headers with multiple values (like `Set-Cookie`) must be represented as an Array of Strings, not a newline-separated String like in Rack 2. Middleware must handle this conditionally if supporting both.
- **`Rack::Sendfile`:** If your web server intercepts `X-Sendfile` headers to serve files directly, and your middleware modifies the body of the response, you will break the web server's ability to serve that file because the body is no longer a File object responding to `to_path`.

## 15. Comparison Table

| Feature | Rack Middleware | Rails `before_action` (Filters) | ActiveSupport::Notifications |
| :--- | :--- | :--- | :--- |
| **Layer** | HTTP / Web Server Boundary | Application / Controller Boundary | Application / Instrumentation |
| **Context** | Raw HTTP (`env` Hash) | Rails Domain (`params`, `session`) | Event Pub/Sub |
| **Performance Overhead** | Very Low (Executes before Rails boots routing) | Medium (Requires Rails Routing & Controller instantiation) | Low |
| **Best Used For** | Rate limiting, CORS, Tracing, Parsing | Authorization, loading DB records | Logging, Metrics, APM tracing |
| **Short-Circuiting** | Halts at TCP/HTTP layer | Halts at Controller layer | Cannot halt request |

## 17. Summary (Revision Sheet)

- **What:** Rack middleware forms a pipeline between the web server and Rails.
- **Contract:** Object with `#call(env)` returning `[status, headers, body]`.
- **Flow:** Inbound -> `env` mutation -> `@app.call` -> Outbound -> response mutation.
- **Thread Safety:** Instantiate once, run concurrently. **NO INSTANCE VARIABLES** for request state.
- **Short-circuiting:** Return a Rack array and skip `@app.call` to halt requests early.
- **Inspection:** `bin/rails middleware` shows the stack.
- **IO Handling:** Always `rewind` `rack.input` if you read from it. Close the `body` if you proxy it.

## 18. Cheat Sheet

**Insert Middleware in `application.rb`:**
```ruby
config.middleware.use CustomMiddleware
config.middleware.insert_before ActionDispatch::Static, CustomMiddleware
config.middleware.insert_after Rack::Attack, CustomMiddleware
config.middleware.delete Rack::Timeout
```

**Minimal Valid Middleware:**
```ruby
class PingPong
  def initialize(app); @app = app; end
  def call(env)
    return [200, {"Content-Type" => "text/plain"}, ["Pong"]] if env['PATH_INFO'] == '/ping'
    @app.call(env)
  end
end
```

## 19. Practice Exercises

- **Easy:** Create `XHeaderInjector` middleware that adds `X-App-Version: 1.0` to every outgoing response.
- **Medium:** Create `AdminOnly` middleware. If the route starts with `/admin`, check the `env['HTTP_AUTHORIZATION']` header for a specific bearer token. If missing, return 401. Otherwise, pass to `@app.call`.
- **Hard:** Create `GzipCompressor` middleware. Intercept the response array. If `status` is 200 and `headers['Content-Type']` is `text/html`, compress the body using `Zlib::GzipWriter`, update the `Content-Length` header, and set `Content-Encoding: gzip`. Ensure you handle the body as an IO stream (using a Proxy) rather than buffering it entirely in memory.
