## 1. Overview

### What it is

**Route recognition** is the process of taking an incoming HTTP request (method + URL path) and figuring out which controller action should handle it.

Think of it like a receptionist at a big office building. A visitor says: *"I need room 402 on the 4th floor."* The receptionist looks at the directory and tells them exactly where to go. Rails does the same thing with URLs.

```
GET /products/42  →  ProductsController#show  (with params[:id] = "42")
```

This is the **incoming direction** of routing. The opposite direction — building a URL from a route name — is called **route generation** (covered in the next chapter).

### Why it exists

Without route recognition, every URL would need manual parsing in every controller. You would write code like:

```ruby
# Without routing — painful and error-prone
if request.path =~ %r{^/products/(\d+)$}
  @product = Product.find($1)
end
```

Rails centralizes all URL-to-controller mapping in `config/routes.rb`. One file defines the entire URL structure of your app. Controllers stay focused on business logic.

### When you care about route recognition

- **Debugging 404 errors** — "Why doesn't this URL work?"
- **Designing APIs** — choosing clean, predictable URL patterns
- **Security reviews** — ensuring sensitive endpoints aren't accidentally exposed
- **Performance tuning** — understanding why route matching takes time on large apps
- **Multi-tenant apps** — routing requests to the right shop/account based on subdomain or path

### Common misconceptions

| Misconception | Reality |
|---|---|
| "Rails checks routes one by one from top to bottom" | Rails compiles routes into a **tree (AST)** and matches efficiently — not a naive linear scan |
| "Only GET requests need routing" | Every HTTP verb (GET, POST, PATCH, DELETE, etc.) is part of recognition |
| "Route recognition happens in the controller" | It happens **before** the controller — in `ActionDispatch::Routing::RouteSet` |
| "Query strings are part of route recognition" | Query strings (`?page=2`) are **not** matched by routes — they become `params` separately |

## 2. Core Concepts

### The RouteSet

When Rails boots, it reads `config/routes.rb` and builds a `ActionDispatch::Routing::RouteSet` object. This is stored at:

```ruby
Rails.application.routes
```

Every incoming request eventually hits this object.

### Journey — Rails' Routing Engine

Since Rails 3, route matching is handled by an internal engine called **Journey** (located in `actionpack/lib/action_dispatch/journey/`).

Journey compiles your routes into a **simulated finite automaton** — essentially a decision tree. When a request arrives, Journey walks this tree character by character through the path.

```
Path: /products/42/reviews

Tree walk:
  / → products → :id → reviews → MATCH!
  
Extracted params: { id: "42" }
Controller: ReviewsController#index (or whatever you defined)
```

### Route Parts

Every route has these components:

| Part | Example | Purpose |
|---|---|---|
| **HTTP Verb** | `GET`, `POST`, `PATCH` | Which request methods match |
| **Path Pattern** | `/products/:id` | The URL structure |
| **Constraints** | `{ id: /\d+/ }` | Extra rules (covered in constraints chapter) |
| **Defaults** | `{ format: 'json' }` | Pre-filled parameter values |
| **Target** | `ProductsController#show` | Where to dispatch |

### Dynamic Segments

Segments starting with `:` are **placeholders** captured into `params`:

```ruby
# config/routes.rb
get '/products/:id', to: 'products#show'

# Request: GET /products/42
# Result:  ProductsController#show
# params[:id] == "42"
```

### Optional Segments

Use parentheses for optional parts:

```ruby
get '/products(/:category)', to: 'products#index'

# Matches: /products AND /products/electronics
```

### Glob Segments (Catch-All)

Use `*segment` to capture the rest of the path:

```ruby
get '/files/*path', to: 'files#show'

# GET /files/docs/readme.md
# params[:path] == "docs/readme.md"
```

Use glob routes carefully — they are slower and can accidentally swallow routes defined below them.

### The Recognition Output

When recognition succeeds, Rails produces:

1. **Controller class** — e.g., `ProductsController`
2. **Action name** — e.g., `show`
3. **Path parameters** — e.g., `{ controller: "products", action: "show", id: "42" }`
4. **Route object** — metadata about the matched route (used for URL generation)

When recognition **fails**, Rails raises `ActionController::RoutingError` (404 in production).

## 3. Internal Working (Step-by-Step)

Here is exactly what happens when `GET /products/42` hits your Rails app.

### Step 1: Middleware Stack Completes

By the time routing runs, middleware has already parsed cookies, sessions, and the request body. The router receives a Rack `env` hash.

### Step 2: RouteSet#call

`ActionDispatch::Routing::RouteSet` is the last middleware in the stack. Its `#call` method:

1. Wraps `env` in an `ActionDispatch::Request` object
2. Calls `recognize_request(request)` internally

### Step 3: Journey Tree Lookup

Journey takes:
- `request.path_info` → `"/products/42"`
- `request.request_method` → `"GET"`

It walks the compiled route tree:

```
Root
 └── GET
      └── "products"
           └── :id (constraint: /\d+/ ?)
                └── → Route#878 → ProductsController#show
```

If the `:id` segment fails a constraint, Journey backtracks and tries the next possible route.

### Step 4: Parameter Extraction

Journey extracts named segments into a params hash:

```ruby
{
  controller: "products",
  action: "show",
  id: "42"
}
```

These merge with query string params and POST body params later in the controller.

### Step 5: Controller Dispatch

The router calls:

```ruby
ProductsController.dispatch(:show, request, response)
```

This creates a **new controller instance** for this request and runs the `show` action.

### What Happens on No Match?

If no route matches:

```ruby
# Development: detailed error page showing all routes
# Production: 404 response

raise ActionController::RoutingError, "No route matches [GET] \"/unknown\""
```

## 4. Architecture — Where Recognition Fits

```text
Client Request: GET /products/42
        │
        ▼
   [Puma / Web Server]
        │
        ▼
   [Rack Middleware Stack]
   (Sessions, Cookies, Body Parser, etc.)
        │
        ▼
   ┌─────────────────────────────┐
   │  RouteSet (Recognition)     │  ← YOU ARE HERE
   │  Journey engine matches     │
   │  path + method → controller │
   └─────────────────────────────┘
        │
        ▼
   [Controller#action]
        │
        ▼
   [Models / Views / Response]
```

Recognition is the **gateway** between HTTP transport and your application code. Nothing in your controller runs until recognition succeeds.

## 5. Real Production Examples

### Example 1: Shopify's Storefront Routing

Shopify serves millions of merchant storefronts. A request like:

```
GET https://cool-sneakers.myshopify.com/products/running-shoe
```

Must be recognized as a product show page **for that specific shop**. Shopify uses:

- **Subdomain constraints** to identify the shop
- **Path-based routing** for products, collections, cart, checkout
- **Catch-all fallbacks** for custom merchant themes

At lead level, the lesson is: recognition isn't just `controller#action` — real apps add tenant context during recognition via constraints and middleware.

### Example 2: API Versioning via Path

```ruby
# config/routes.rb
namespace :api do
  namespace :v1 do
    resources :orders
  end

  namespace :v2 do
    resources :orders
  end
end

# GET /api/v1/orders/5  → Api::V1::OrdersController#show
# GET /api/v2/orders/5  → Api::V2::OrdersController#show
```

Same resource, different controller — recognized purely by the URL path prefix.

### Example 3: Admin vs Public Same Resource

```ruby
# Public
resources :products, only: [:index, :show]

# Admin (separate controller, stricter constraints)
namespace :admin do
  resources :products
end

# GET /products/1       → ProductsController#show
# GET /admin/products/1 → Admin::ProductsController#show
```

## 6. Common Mistakes

### Beginner Mistakes

**1. Route order doesn't matter (wrong!)**

While Journey uses a tree (not pure top-to-bottom), **catch-all and broad routes can shadow specific ones** if defined carelessly:

```ruby
# BAD — glob swallows everything
get '/*path', to: 'pages#show'
get '/about', to: 'pages#about'  # Never reached in some setups

# GOOD — specific routes first, catch-all last
get '/about', to: 'pages#about'
get '/*path', to: 'pages#show'
```

**2. Forgetting the HTTP verb**

```ruby
# This only matches GET
get '/products/:id', to: 'products#show'

# POST /products/42 → 404 (No route matches)
```

Use `resources` or define each verb explicitly.

**3. Expecting query params in the route**

```ruby
get '/search', to: 'products#search'

# GET /search?q=shoes
# The route matches /search
# params[:q] comes from the query string, NOT the route definition
```

### Mid-Level Mistakes

**4. Duplicate route names**

Two routes with the same name cause the second to silently overwrite the first in helpers. Always run `bin/rails routes | grep my_route`.

**5. Hardcoding paths instead of using recognition knowledge**

When debugging, developers often `puts request.path` everywhere instead of using:

```ruby
# In console or debugging
Rails.application.routes.recognize_path("/products/42", method: :get)
# => { controller: "products", action: "show", id: "42" }
```

**6. Not handling format segments**

```ruby
# GET /products/1.json vs /products/1.html
# Both match resources :products
# params[:format] == "json" or "html"
```

### Senior/Lead Mistakes

**7. Massive flat routes.rb with no organization**

A 2000-line `routes.rb` is a maintenance nightmare. At Shopify scale, routes are split across engines, concerns, and draw blocks.

**8. Route recognition in hot paths without caching**

Calling `recognize_path` in a loop or on every Sidekiq job is expensive. Cache recognized routes or pass structured params instead.

**9. Security: exposing internal routes**

```ruby
# Accidentally exposing Sidekiq Web UI or admin routes
mount Sidekiq::Web => '/sidekiq'  # Without authentication constraint!
```

Always audit `bin/rails routes` in production mode before deploying.

## 7. Performance Considerations

### Route Compilation Happens at Boot

Routes are compiled once when Rails boots (or when routes reload in development). Recognition itself is fast — it's a tree walk, not regex scanning every route.

### Factors That Slow Recognition

| Factor | Impact |
|---|---|
| **Thousands of routes** | Larger tree, slightly slower lookups |
| **Complex regex constraints** | Backtracking during tree walk |
| **Many glob/catch-all routes** | Ambiguous paths require more backtracking |
| **Route reload in dev** | Recompiles on every file save |

### Production Tip

In production, routes are eager-loaded and frozen. Recognition is typically **sub-millisecond**. If you see routing slowness, the problem is usually middleware or controller code — not Journey itself.

### Benchmarking Recognition

```ruby
# rails console
require 'benchmark'

Benchmark.realtime do
  10_000.times do
    Rails.application.routes.recognize_path("/products/42", method: :get)
  end
end
# Typically ~0.1-0.3 seconds for 10k recognitions
```

## 8. Security Considerations

### Route Enumeration

Attackers probe common paths (`/admin`, `/api/internal`, `/debug`). Audit your routes:

```bash
RAILS_ENV=production bin/rails routes
```

### Constraint-Based Access Control

Recognition happens **before** authentication. Use route constraints for IP-based or subdomain-based access:

```ruby
constraints ->(req) { req.env['REMOTE_ADDR'] == '10.0.0.1' } do
  mount Sidekiq::Web => '/sidekiq'
end
```

This is defense-in-depth — still add controller-level authorization.

### Parameter Injection via Path Segments

```ruby
get '/users/:id', to: 'users#show'

# GET /users/1 OR /users/1%20DROP%20TABLE
# Always sanitize in the controller:
User.find(params[:id])  # ActiveRecord parameterizes queries safely
```

Never trust `params[:id]` for filesystem paths or SQL without validation.

## 9. Debugging Route Recognition

### View All Routes

```bash
bin/rails routes
bin/rails routes -g product    # grep for "product"
bin/rails routes -c Products   # routes for ProductsController
```

### Recognize a Path in Console

```ruby
Rails.application.routes.recognize_path("/products/42")
# => { controller: "products", action: "show", id: "42" }

Rails.application.routes.recognize_path("/products/42", method: :post)
# ActionController::RoutingError — no POST route
```

### See Which Route Matched (Development)

Check the Rails server log:

```
Started GET "/products/42" for 127.0.0.1 at 2026-01-15 10:00:00 +0530
Processing by ProductsController#show as HTML
  Parameters: {"id"=>"42"}
```

### Common 404 Debugging Checklist

1. Is the HTTP verb correct? (GET vs POST)
2. Is there a trailing slash mismatch?
3. Is a constraint blocking the match?
4. Is the route inside a `namespace` or `scope` you forgot about?
5. Did you restart the server after changing routes? (Production always; dev usually auto-reloads)

## 10. Best Practices

1. **Use `resources` for CRUD** — let Rails generate standard, recognizable patterns
2. **Group routes logically** — namespaces, scopes, and `draw` blocks for large apps
3. **Name your routes** — named routes enable generation and make logs readable
4. **Run `bin/rails routes` after every change** — make it a habit
5. **Test recognition in request specs** — not just unit tests
6. **Document non-obvious routes** — especially API versioning and webhooks
7. **Keep catch-all routes at the bottom**

---

## 11. Anti-Patterns

| Anti-Pattern | Why It's Bad | Better Approach |
|---|---|---|
| Parsing `request.path` manually in controllers | Bypasses Rails routing, untestable | Define a proper route |
| One giant `routes.rb` | Unmaintainable at scale | Split with `draw :admin`, engines, concerns |
| Regex-heavy path patterns | Hard to read, slow to match | Use constraints on segments |
| Duplicate paths with different verbs to same action | Confusing logs and debugging | Use `match` or `via:` explicitly |
| `any` routes everywhere | Matches all verbs, security risk | Be explicit about HTTP methods |

## 12. Interview Questions

### Basic

**Q: What happens when Rails receives `GET /users/5`?**

**A:** The RouteSet uses Journey to match the path and HTTP method against the compiled route tree. If a route like `resources :users` exists, it maps to `UsersController#show` with `params[:id] = "5"`. The controller action runs only after this match succeeds.

### Intermediate

**Q: What is the difference between route recognition and route generation?**

**A:** Recognition converts an incoming URL + HTTP method into a controller/action + params. Generation does the reverse — takes a route name and params and produces a URL string. They are two directions of the same route table.

### Senior

**Q: How does Journey differ from a simple array of regexes?**

**A:** Journey compiles routes into a finite automaton (tree). Matching walks the tree character-by-character, which is O(path length) rather than O(number of routes). Regex constraints are applied at specific nodes, not on every route. This scales to thousands of routes efficiently.

### Staff/Lead

**Q: You inherit a Rails app with 3000 routes and P99 routing latency is high. How do you investigate and fix it?**

**A:**
1. Profile with rack-mini-profiler to confirm routing (not middleware/DB) is the bottleneck
2. Audit for glob routes, expensive regex constraints, and redundant routes
3. Split routes across engines and lazy-mount engines where possible
4. Check for middleware doing `recognize_path` on every request
5. Consider route caching for frequently resolved paths in custom middleware
6. Remove dead routes from legacy features
7. Ensure production has eager-loaded, cached route set (not reloading)

## 15. Summary (Revision Sheet)

1. **Route recognition** maps incoming HTTP method + URL path → controller#action + params
2. Powered by **Journey**, a tree-based matching engine (not linear regex scanning)
3. Happens in **`ActionDispatch::Routing::RouteSet`** before any controller code runs
4. Dynamic segments (`:id`) become **`params`**
5. Query strings are **not** part of route matching — they merge into params separately
6. Debug with **`bin/rails routes`** and **`recognize_path`**
7. At scale: organize routes, avoid glob/regex abuse, audit exposed endpoints
