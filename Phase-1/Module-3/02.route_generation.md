# Route Generation — Comprehensive Study Guide

> **Module:** Phase 1 — Module 3 (Routing)
> **Topic:** Route Generation
> **Target Audience:** Rails developers preparing for Senior/Lead roles

---

## 1. Overview

### What it is

**Route generation** is the process of building a URL path (and optionally a full URL) from a **route name** and **parameters**.

If route recognition answers: *"Where does `/products/42` go?"*

Route generation answers: *"What URL takes me to product 42's show page?"*

```ruby
# Recognition (incoming):
# GET /products/42 → ProductsController#show

# Generation (outgoing):
product_path(42)    # => "/products/42"
product_url(42)     # => "http://localhost:3000/products/42"
```

### Why it exists

Hardcoding URLs in views, mailers, and APIs is fragile. When routes change, every hardcoded string breaks silently or causes 404s.

Route generation gives you **one source of truth** — change `routes.rb` once, and all generated URLs update automatically.

```ruby
# BAD — breaks when routes change
link_to "View Product", "/products/#{product.id}"

# GOOD — always correct
link_to "View Product", product_path(product)
```

### When you use route generation

- **Views** — `link_to`, `button_to`, `form_with`
- **Controllers** — `redirect_to product_path(@product)`
- **Mailers** — embedding links in emails
- **Background jobs** — generating URLs for notifications
- **API serializers** — including `href` links (JSON:API, HAL)
- **Tests** — asserting redirect locations

### Common misconceptions

| Misconception | Reality |
|---|---|
| "`_path` and `_url` are interchangeable" | `_path` gives a relative path; `_url` includes host, protocol, and port |
| "Route helpers only work in views" | They work anywhere you include `Rails.application.routes.url_helpers` |
| "You must pass IDs to route helpers" | You can pass objects — Rails calls `.to_param` on them |
| "Route generation is slow" | It's a hash lookup + string interpolation — extremely fast |

## 2. Core Concepts

### Named Routes

When you give a route a name (via `as:` or `resources`), Rails creates **helper methods**:

```ruby
# config/routes.rb
get '/products/:id', to: 'products#show', as: :product
```

This creates two methods:

| Method | Returns | Example Output |
|---|---|---|
| `product_path(id)` | Relative path | `"/products/42"` |
| `product_url(id)` | Full URL | `"http://localhost:3000/products/42"` |

The `_path` suffix = path only. The `_url` suffix = full URL with host.

### How `resources` Names Helpers

```ruby
resources :products
```

| Helper | HTTP Verb | Path | Purpose |
|---|---|---|---|
| `products_path` | GET | `/products` | Index |
| `new_product_path` | GET | `/products/new` | New form |
| `product_path(id)` | GET | `/products/:id` | Show |
| `edit_product_path(id)` | GET | `/products/:id/edit` | Edit form |

For POST/PATCH/DELETE, you typically use the same path helpers inside `form_with` or `link_to` with a `method:` option — Rails handles the verb separately.

### Passing Objects (Polymorphic Magic)

Rails calls `.to_param` on objects you pass:

```ruby
product = Product.find(42)
product_path(product)  # => "/products/42"

# Product#to_param returns id by default
class Product < ApplicationRecord
  def to_param
    slug  # Now: product_path(product) => "/products/running-shoe"
  end
end
```

For nested routes, pass parent and child:

```ruby
product_review_path(@product, @review)
# => "/products/42/reviews/7"
```

### Polymorphic Route Helpers

When you don't know the model type at compile time:

```ruby
# Works for any ActiveRecord model with proper routes
polymorphic_path(@record)       # show path
edit_polymorphic_path(@record)  # edit path
polymorphic_url(@record)        # full URL

# Example:
polymorphic_path(Product.find(1))  # => "/products/1"
polymorphic_path(Order.find(5))    # => "/orders/5"
```

### URL Options and Defaults

Generation merges parameters from multiple sources:

```ruby
product_path(42, format: :json)           # => "/products/42.json"
product_path(42, anchor: 'reviews')      # => "/products/42#reviews"
product_path(42, sort: 'asc')             # => "/products/42?sort=asc"
```

For `_url` helpers, you need host configuration:

```ruby
# config/environments/production.rb
config.action_mailer.default_url_options = { host: 'shop.example.com', protocol: 'https' }
config.action_controller.default_url_options = { host: 'shop.example.com' }
```

Without host config, `_url` helpers raise `ArgumentError: Missing host`.

## 3. Internal Working (Step-by-Step)

### Step 1: Route Named at Boot

When Rails loads `routes.rb`, each named route registers a helper in `ActionDispatch::Routing::NamedRouteCollection`.

```ruby
# Simplified internal representation
{
  product: #<NamedRoute name: :product, pattern: "/products/:id", ...>
}
```

### Step 2: Helper Method Invocation

When you call `product_path(42)`:

1. Rails looks up the `:product` named route
2. Validates required parameters (`:id` must be present)
3. Interpolates `:id` into the path template
4. Appends optional query params and format
5. Returns the string

### Step 3: Parameter Validation

If you forget a required parameter:

```ruby
product_path  # ArgumentError: Missing required key: :id
```

If you pass an unknown parameter:

```ruby
product_path(42, foo: 'bar')
# => "/products/42?foo=bar"  (extra params become query string)
```

### Step 4: `url_for` — The Universal Generator

Under the hood, most helpers delegate to `url_for`:

```ruby
url_for(controller: 'products', action: 'show', id: 42)
# => "/products/42"

url_for(@product)
# => "/products/42"  (uses polymorphic routing)

url_for(action: 'index', only_path: true)
# => "/products"  (current controller context)
```

`link_to "Show", @product` internally calls `url_for(@product)`.

## 4. Architecture — Generation in the Request Cycle

```text
┌─────────────────────────────────────────────────┐
│                  routes.rb                       │
│  (Single source of truth for all URLs)           │
└──────────────────────┬──────────────────────────┘
                       │ compiled at boot
                       ▼
┌─────────────────────────────────────────────────┐
│            NamedRouteCollection                  │
│  product_path / product_url / products_path ...  │
└──────────┬──────────┬──────────┬────────────────┘
           │          │          │
           ▼          ▼          ▼
       [Views]   [Mailers]  [Controllers]
       link_to   email      redirect_to
       form_with links      background jobs
```

Generation never touches the HTTP request. It's pure string building from the route table.

## 5. Real Production Examples

### Example 1: Email Links in a Background Job

```ruby
# app/jobs/order_confirmation_job.rb
class OrderConfirmationJob < ApplicationJob
  include Rails.application.routes.url_helpers

  def perform(order_id)
    @order = Order.find(order_id)

    OrderMailer.confirmation(
      @order,
      order_url(@order, host: 'shop.example.com', protocol: 'https')
    ).deliver_now
  end
end
```

Background jobs don't have a request context, so you **must** pass `host` explicitly for `_url` helpers.

### Example 2: JSON API with HATEOAS Links

```ruby
# app/serializers/product_serializer.rb
class ProductSerializer
  include Rails.application.routes.url_helpers

  def as_json(product)
    {
      id: product.id,
      name: product.name,
      links: {
        self: product_url(product),
        reviews: product_reviews_url(product)
      }
    }
  end
end
```

### Example 3: Shopify-Style Multi-Tenant URLs

```ruby
# Generate URLs scoped to a specific shop
shop_product_url(shop_slug: 'cool-sneakers', id: product.slug, host: 'myshopify.com')
# => "https://cool-sneakers.myshopify.com/products/running-shoe"
```

At scale, generation must respect tenant context — never generate a link that points to the wrong shop.

## 6. Common Mistakes

### Beginner Mistakes

**1. Hardcoding URLs**

```ruby
# Fragile
redirect_to "/products/#{@product.id}"

# Robust
redirect_to @product  # or product_path(@product)
```

**2. Using `_url` in views without host config**

```ruby
# Raises in test/mailer unless configured
product_url(@product)

# Fix: set default_url_options in environment config
```

**3. Wrong parameter order in nested helpers**

```ruby
# WRONG
review_path(@review, @product)

# RIGHT — parent first, then child
product_review_path(@product, @review)
```

### Mid-Level Mistakes

**4. Forgetting `only_path: true` in mailers/jobs**

Use `_path` when you don't need the full URL, or pass explicit host to `_url`.

**5. Not overriding `to_param` when using slugs**

```ruby
# Route expects slug but to_param returns id
get '/products/:slug', to: 'products#show'

class Product
  def to_param
    slug  # MUST override or generation produces wrong URLs
  end
end
```

**6. Route name collisions**

```ruby
# Two routes named :product — second wins silently
get '/items/:id', to: 'items#show', as: :product
get '/products/:id', to: 'products#show', as: :product
```

### Senior/Lead Mistakes

**7. Generating URLs in model callbacks**

Models shouldn't know about routing. Keep URL generation in views, mailers, serializers, or presenters.

**8. N+1 URL generation in serializers**

Generating URLs for 1000 records in a loop is fine (it's cheap), but if your serializer hits the DB for each URL, that's the real problem.

**9. Not testing generated URLs across environments**

Development uses `localhost:3000`, staging uses `staging.example.com`. Test mailers and jobs with explicit host options.

## 7. Performance Considerations

Route generation is **extremely fast** — it's a template lookup and string interpolation. No regex matching involved.

```ruby
# Benchmark: 100k generations ≈ 0.05 seconds
100_000.times { product_path(42) }
```

Performance concerns arise when:

- Generating URLs triggers DB queries (via `to_param` calling associations)
- Building complex URLs in tight loops without caching
- Using `url_for` with heavy option hashes in serializers at scale

**Tip:** Precompute URLs in bulk operations or cache them if building sitemaps with millions of entries.

## 8. Security Considerations

### Open Redirect Vulnerabilities

```ruby
# DANGEROUS — user controls redirect destination
redirect_to params[:return_to]

# SAFE — validate against allowed paths
redirect_to safe_return_path(params[:return_to])
```

Never pass user input directly to URL generation without validation.

### Host Header Injection

If you generate `_url` helpers using `request.host` without validation, attackers can inject malicious hosts into password reset emails.

```ruby
# Use configured host, not request host
config.action_mailer.default_url_options = { host: 'shop.example.com' }
```

### Leaking Internal Routes in Generated Links

Ensure generated URLs don't expose admin or internal paths to unauthorized users. Generation creates the URL — authorization is still your job in the controller.

## 9. Debugging Route Generation

### List Helper Names

```bash
bin/rails routes
# Look at the "Prefix" column — that's the helper name
```

### Generate in Console

```ruby
include Rails.application.routes.url_helpers

product_path(42)
# => "/products/42"

app.product_path(42)  # in rails console using 'app' helper
```

### Find Which Route a Helper Maps To

```bash
bin/rails routes -g product
# Prefix: product
# Helper: product_path(id)
```

### Common Errors

| Error | Cause | Fix |
|---|---|---|
| `No route matches { ... }` | Missing/wrong params | Check `bin/rails routes` for required keys |
| `Missing host` | Using `_url` without host | Set `default_url_options` or pass `host:` |
| `ArgumentError: Missing required key: :id` | Forgot parameter | Pass all required dynamic segments |

## 10. Best Practices

1. **Never hardcode paths** — always use route helpers
2. **Use `_path` in views/controllers** — relative paths are portable
3. **Use `_url` in mailers/jobs** — always include explicit host
4. **Pass objects, not IDs** — `product_path(@product)` not `product_path(@product.id)`
5. **Override `to_param`** when using slugs or composite keys
6. **Include url_helpers** in mailers, jobs, and serializers explicitly
7. **Test generated URLs** in request specs and mailer specs

---

## 11. Anti-Patterns

| Anti-Pattern | Better Approach |
|---|---|
| `"/products/#{id}"` string interpolation | `product_path(id)` |
| URL generation in models | Presenters, serializers, or view helpers |
| `redirect_to request.referrer` without validation | Whitelist allowed referrers |
| Building URLs with string concatenation for query params | Pass hash: `products_path(sort: 'asc', page: 2)` |
| Using `_url` in HTML views when `_path` suffices | `_path` unless you need absolute URLs |

## 12. Interview Questions

### Basic

**Q: What is the difference between `product_path` and `product_url`?**

**A:** `product_path(42)` returns a relative path (`"/products/42"`). `product_url(42)` returns a full URL including protocol and host (`"http://localhost:3000/products/42"`). Use `_path` in views and `_url` in mailers/emails.

### Intermediate

**Q: Why does `product_url(@product)` fail in a Sidekiq job?**

**A:** `_url` helpers need a host to build the full URL. Controllers and views have request context with a host. Background jobs don't. Fix by passing `host:` explicitly or configuring `default_url_options`.

### Senior

**Q: Explain polymorphic routing and when you'd use it.**

**A:** `polymorphic_path(record)` generates the correct path for any model based on its class. Useful in shared partials (`_comment.html.erb` rendered for comments on products, orders, or posts), generic admin interfaces, or activity feeds where the record type varies.

### Staff/Lead

**Q: How would you design URL generation for a multi-tenant SaaS app where each tenant has a custom subdomain?**

**A:**
1. Define routes with subdomain constraints or path-based tenant scoping
2. Create a `TenantUrlHelper` module that wraps route helpers, always injecting the current tenant's subdomain/host
3. Set `default_url_options` dynamically per request via middleware (store tenant in `CurrentAttributes`)
4. In mailers/jobs, pass tenant context explicitly — never rely on request context
5. Test URL generation per tenant to prevent cross-tenant link leakage

## 13. Practical Examples

### Example 1: View Links

```erb
<%# app/views/products/index.html.erb %>
<% @products.each do |product| %>
  <%= link_to product.name, product_path(product) %>
  <%= link_to "Edit", edit_product_path(product) %>
<% end %>

<%= link_to "New Product", new_product_path %>
```

### Example 2: Controller Redirects

```ruby
class ProductsController < ApplicationController
  def create
    @product = Product.create(product_params)
    redirect_to @product, notice: "Created!"
  end

  def destroy
    @product = Product.find(params[:id])
    @product.destroy
    redirect_to products_path, status: :see_other
  end
end
```

### Example 3: Mailer with Full URLs

```ruby
class OrderMailer < ApplicationMailer
  def confirmation(order)
    @order = order
    @url = order_url(@order)  # Uses default_url_options host
    mail(to: order.email, subject: "Order Confirmed")
  end
end
```

### Example 4: Job with Explicit Host

```ruby
class NotificationJob < ApplicationJob
  include Rails.application.routes.url_helpers

  def perform(user_id, post_id)
    user = User.find(user_id)
    post = Post.find(post_id)
    url = post_url(post, host: ENV.fetch('APP_HOST'), protocol: 'https')
    PushNotifier.send(user, "New post: #{url}")
  end
end
```

### Example 5: Query Parameters and Format

```ruby
products_path(sort: 'price', direction: 'asc', page: 2)
# => "/products?direction=asc&page=2&sort=price"

product_path(42, format: :json)
# => "/products/42.json"
```
