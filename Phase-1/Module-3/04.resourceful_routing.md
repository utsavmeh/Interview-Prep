## 1. Overview

### What it is

**Resourceful routing** is Rails' convention for mapping HTTP verbs to CRUD (Create, Read, Update, Delete) controller actions using a single line:

```ruby
resources :products
```

This one line creates **7 routes** that follow REST conventions — the same patterns used by Shopify, GitHub, Stripe, and virtually every modern API.

### Why it exists

Before resourceful routing, developers manually wrote every route:

```ruby
# Old way — repetitive and inconsistent
get    '/products',          to: 'products#index'
get    '/products/new',      to: 'products#new'
post   '/products',          to: 'products#create'
get    '/products/:id',      to: 'products#show'
get    '/products/:id/edit', to: 'products#edit'
patch  '/products/:id',      to: 'products#update'
delete '/products/:id',      to: 'products#destroy'
```

`resources :products` generates all of these with consistent naming, helper methods, and HTTP verb mapping. It is the foundation of "Rails way" routing.

### When to use it

- **Any CRUD resource** — products, users, orders, posts
- **API endpoints** — JSON APIs follow the same REST mapping
- **Admin panels** — `namespace :admin { resources :products }`
- **Partial CRUD** — use `only:` or `except:` to limit actions

### Common misconceptions

| Misconception | Reality |
|---|---|
| "`resources` creates 7 controller methods automatically" | It creates **routes** — you still write controller actions |
| "REST means you must use all 7 actions" | Use `only:` / `except:` — most resources don't need all 7 |
| "`new` and `edit` are REST actions" | They are **member routes** for HTML forms — not REST verbs |
| "Resourceful routing is only for HTML apps" | APIs use the same mapping minus `new`/`edit` |

## 2. Core Concepts

### The 7 RESTful Actions

| HTTP Verb | Path | Controller Action | Purpose |
|---|---|---|---|
| GET | `/products` | `index` | List all products |
| GET | `/products/new` | `new` | Show "new product" form |
| POST | `/products` | `create` | Create a product |
| GET | `/products/:id` | `show` | Show one product |
| GET | `/products/:id/edit` | `edit` | Show "edit product" form |
| PATCH/PUT | `/products/:id` | `update` | Update a product |
| DELETE | `/products/:id` | `destroy` | Delete a product |

### Visual Map

```text
                    products
                   /   |   \
              index  create  show (:id)
               |              |
             new            edit
```

- **Collection routes** (`index`, `new`, `create`) — operate on the collection (`/products`)
- **Member routes** (`show`, `edit`, `update`, `destroy`) — operate on one item (`/products/:id`)

### Singular vs Plural Resources

```ruby
resources :products   # Plural — many products (index makes sense)
resource :profile     # Singular — one profile per user (no index)
```

| Declaration | Index? | Show path | Use case |
|---|---|---|---|
| `resources :products` | Yes | `/products/:id` | Products, orders, users |
| `resource :profile` | No | `/profile` | User profile, account settings |
| `resource :cart` | No | `/cart` | Shopping cart (one per session) |

### Limiting Routes

```ruby
# Only specific actions
resources :products, only: [:index, :show]

# Everything except
resources :products, except: [:destroy]

# Read-only API
resources :products, only: [:index, :show, :create]
```

Always run `bin/rails routes` after changing to verify.

### Route Helpers Created

For `resources :products`:

| Helper | Path |
|---|---|
| `products_path` | `/products` |
| `new_product_path` | `/products/new` |
| `product_path(id)` | `/products/:id` |
| `edit_product_path(id)` | `/products/:id/edit` |

## 3. Internal Working

When Rails encounters `resources :products`:

1. **RouteSet** receives a `Mapper#resources` call
2. Seven route definitions are registered (or fewer with `only:`/`except:`)
3. Each route gets a **named helper** in `NamedRouteCollection`
4. Journey compiles all routes into the matching tree
5. Controller name is inferred: `:products` → `ProductsController`

```ruby
# Simplified equivalent of resources :products
scope '/products', as: 'products', controller: 'products' do
  get    '/',      action: 'index'
  post   '/',      action: 'create'
  get    '/new',   action: 'new'
  get    '/:id',   action: 'show'
  patch  '/:id',   action: 'update'
  put    '/:id',   action: 'update'
  delete '/:id',   action: 'destroy'
  get    '/:id/edit', action: 'edit'
end
```

You rarely write this manually — but knowing the expansion helps in interviews and debugging.

## 4. Architecture — REST in Rails

```text
HTTP Request                    Rails Router              Controller
─────────────                   ────────────              ──────────
GET    /products        →       index            →       def index
POST   /products        →       create           →       def create
GET    /products/1      →       show             →       def show
PATCH  /products/1      →       update           →       def update
DELETE /products/1      →       destroy          →       def destroy
```

This mapping is the **contract** between your API consumers and your application. Breaking it (e.g., using GET for delete) causes confusion and security issues.

## 5. Real Production Examples

### Example 1: Shopify Admin Products API

```ruby
# Simplified Shopify-style admin routes
namespace :admin do
  resources :products do
    member do
      post :duplicate
    end
    collection do
      post :bulk_update
    end
  end
end
```

Standard CRUD plus custom actions — the pattern used at every large Rails shop.

### Example 2: Read-Only Public API

```ruby
namespace :api do
  namespace :v1 do
    resources :products, only: [:index, :show]
    resources :collections, only: [:index, :show]
  end
end
```

Public storefront APIs typically expose only read actions.

### Example 3: Singular Resource — User Settings

```ruby
resource :settings, only: [:show, :update]
# GET    /settings  → SettingsController#show
# PATCH  /settings  → SettingsController#update
# No :id needed — one settings page per user
```

## 6. Common Mistakes

### Beginner

**1. Missing controller actions**

```ruby
resources :products, only: [:index, :show]
# But ProductsController only defines #index — #show raises UnknownAction error
```

**2. Using GET for destructive actions**

```ruby
# NEVER do this
get '/products/:id/delete', to: 'products#destroy'

# Crawlers and prefetchers can trigger GET requests!
# Always use DELETE verb
```

**3. Forgetting strong params in create/update**

Routes get the request to the controller — strong parameters are still required.

### Mid-Level

**4. Over-generating routes**

```ruby
resources :products  # Generates 7 routes
# But you only need index and show for a catalog page
# Use only: to reduce attack surface
```

**5. Inconsistent pluralization**

```ruby
resources :category  # Wrong — should be :categories
# Rails expects CategoriesController, not CategoryController
```

Rails infers controller name from the resource name. Use correct plural forms.

### Senior/Lead

**6. Not versioning API resources**

When you need breaking changes, create a new namespace rather than modifying existing routes.

**7. Exposing admin CRUD on public routes**

Separate public read-only routes from admin full CRUD using namespaces and authorization.

## 7. Performance Considerations

- Each `resources` call adds 7 routes to the tree — use `only:`/`except:` to keep the tree lean
- Large apps with hundreds of resources should split routes files
- Read-only APIs with `only: [:index, :show]` cut route count by ~70%

---

## 8. Security Considerations

- **Principle of least privilege** — only expose routes you need
- **DELETE and PATCH must not be GET** — prevents CSRF via link prefetching
- **Route exposure audit** — run `bin/rails routes` and review what's public
- **API authentication** — routes define endpoints; controllers enforce auth

## 10. Best Practices

1. Default to `resources` for any CRUD entity
2. Use `only:` / `except:` aggressively — don't generate unused routes
3. Use `resource` (singular) for one-per-user resources
4. Match controller name to resource name (`:products` → `ProductsController`)
5. Separate public and admin resources with namespaces
6. Document custom actions with clear names (`:publish`, not `:do_thing`)

---

## 11. Anti-Patterns

| Anti-Pattern | Better Approach |
|---|---|
| `match '/products/:id', via: :all` | Explicit verbs per action |
| Custom CRUD verbs (`activate_product`) as separate controllers | Member routes on the resource |
| `resources :product` (singular pluralization) | `resource :product` or `resources :products` |
| 7 routes for a read-only catalog | `only: [:index, :show]` |

## 12. Interview Questions

### Basic

**Q: What routes does `resources :posts` create?**

**A:** Seven routes mapping to index, new, create, show, edit, update, and destroy actions on PostsController, with paths under `/posts` and named helpers like `posts_path` and `post_path(id)`.

### Intermediate

**Q: When would you use `resource` instead of `resources`?**

**A:** When there is exactly one instance per scope — user profile, account settings, shopping cart. No index action, no `:id` in the path. `resource :profile` gives `/profile` not `/profiles/:id`.

### Senior

**Q: How would you design routes for a product that can be archived (soft delete)?**

**A:** Keep standard `destroy` for soft delete internally. Add `member { post :restore }` for unarchiving. Don't create a separate controller — extend the existing resource with member actions. Alternatively, use PATCH with a status field for API-style updates.

## 13. Practical Examples

### Full CRUD Setup

```ruby
# config/routes.rb
resources :products

# app/controllers/products_controller.rb
class ProductsController < ApplicationController
  def index
    @products = Product.all
  end

  def show
    @product = Product.find(params[:id])
  end

  def new
    @product = Product.new
  end

  def create
    @product = Product.create(product_params)
    redirect_to @product
  end

  def edit
    @product = Product.find(params[:id])
  end

  def update
    @product = Product.find(params[:id])
    @product.update(product_params)
    redirect_to @product
  end

  def destroy
    @product = Product.find(params[:id])
    @product.destroy
    redirect_to products_path
  end

  private

  def product_params
    params.require(:product).permit(:name, :price)
  end
end
```

### API-Style (No HTML Forms)

```ruby
namespace :api do
  namespace :v1 do
    resources :products, only: [:index, :show, :create, :update, :destroy]
  end
end
```

### Singular Resource

```ruby
resource :cart, only: [:show, :update, :destroy]
# GET    /cart    → CartsController#show
# PATCH  /cart    → CartsController#update
# DELETE /cart    → CartsController#destroy
```
