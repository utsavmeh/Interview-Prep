# Member vs Collection Routes — Comprehensive Study Guide

> **Module:** Phase 1 — Module 3 (Routing)
> **Topic:** Member vs Collection Routes
> **Target Audience:** Rails developers preparing for Senior/Lead roles

---

## 1. Overview

### What it is

Standard `resources` gives you 7 CRUD actions. But real apps need **custom actions** beyond CRUD — publish a post, archive an order, search products.

Rails divides custom actions into two categories:

| Type | Operates on | URL Pattern | Example |
|---|---|---|---|
| **Collection route** | The whole group | `/products/search` | Search all products |
| **Member route** | One specific item | `/products/42/publish` | Publish product #42 |

```ruby
resources :products do
  collection do
    get :search      # GET /products/search
  end

  member do
    post :publish    # POST /products/:id/publish
  end
end
```

### Why it exists

CRUD covers basic database operations. Real business logic needs more:

- **Publish/unpublish** a blog post (member)
- **Search/filter** a list (collection)
- **Bulk update** multiple records (collection)
- **Duplicate** a single record (member)
- **Export CSV** of all records (collection)

Member and collection blocks give you a clean, RESTful way to add these without breaking conventions.

### When to use which

| Ask yourself... | Route type |
|---|---|
| "Does this action target ONE record?" | **Member** |
| "Does this action target the COLLECTION or no specific record?" | **Collection** |
| "Does the URL need an `:id`?" | **Member** |
| "Is this a search, filter, or bulk operation?" | **Collection** |

### Common misconceptions

| Misconception | Reality |
|---|---|
| "Custom actions should be new controllers" | Simple actions fit fine as member/collection routes |
| "Member routes always use GET" | Use the correct HTTP verb — POST for state changes |
| "Collection routes can't have an :id" | Correct — they operate on `/products/action`, not `/products/:id/action` |
| "You can only add one custom action" | Add as many as needed inside the block |

## 2. Core Concepts

### Member Routes

Act on a **single resource instance**. Require `:id` in the URL.

```ruby
resources :products do
  member do
    post :publish
    post :archive
    get :preview
  end
end
```

Generated routes:

| Verb | Path | Action | Helper |
|---|---|---|---|
| POST | `/products/:id/publish` | publish | `publish_product_path(id)` |
| POST | `/products/:id/archive` | archive | `archive_product_path(id)` |
| GET | `/products/:id/preview` | preview | `preview_product_path(id)` |

Controller:

```ruby
class ProductsController < ApplicationController
  def publish
    @product = Product.find(params[:id])
    @product.update!(published: true)
    redirect_to @product
  end
end
```

### Collection Routes

Act on the **collection as a whole**. No `:id` in the URL.

```ruby
resources :products do
  collection do
    get :search
    post :bulk_update
    get :export
  end
end
```

Generated routes:

| Verb | Path | Action | Helper |
|---|---|---|---|
| GET | `/products/search` | search | `search_products_path` |
| POST | `/products/bulk_update` | bulk_update | `bulk_update_products_path` |
| GET | `/products/export` | export | `export_products_path` |

Controller:

```ruby
class ProductsController < ApplicationController
  def search
    @products = Product.where("name LIKE ?", "%#{params[:q]}%")
    render json: @products
  end
end
```

### Shorthand Syntax

For a single custom action, skip the block:

```ruby
resources :products do
  get :search, on: :collection     # GET /products/search
  post :publish, on: :member       # POST /products/:id/publish
end
```

### Multiple Actions in One Line

```ruby
resources :products do
  get :search, :export, on: :collection
  post :publish, :archive, on: :member
end
```

## 3. Internal Working

When Rails encounters `member` or `collection` blocks:

1. It creates routes **within the existing resource scope**
2. Member routes inherit the `/:id` segment from the parent resource
3. Collection routes sit at the collection path (before `/:id` would match)
4. Route names follow the pattern: `{action}_{resource}_path` (member) or `{action}_{resources}_path` (collection)
5. Journey places collection routes **before** member routes in the tree (more specific paths first)

```text
Route tree for resources :products with custom actions:

/products/search          ← collection (no :id)
/products/export          ← collection
/products/new             ← standard CRUD
/products/:id/publish     ← member (has :id)
/products/:id/preview     ← member
/products/:id             ← standard CRUD
/products                 ← standard CRUD
```

Order matters: `/products/search` must be recognized before `/products/:id` interprets "search" as an ID.

## 4. Architecture — Where Custom Actions Fit

```text
Standard REST Actions          Custom Actions
─────────────────────         ──────────────────
index    (collection)         search   (collection)
create   (collection)         bulk_update (collection)
show     (member)             publish  (member)
update   (member)             archive  (member)
destroy  (member)             preview  (member)
```

Custom actions extend REST — they don't replace it. Keep CRUD for database operations; use member/collection for business operations.

## 6. Common Mistakes

### Beginner

**1. Using GET for state-changing actions**

```ruby
# BAD — GET should never change data
get :publish, on: :member

# GOOD — POST for state changes
post :publish, on: :member
```

Browsers, crawlers, and CDNs cache GET requests. A GET that publishes a product is a bug waiting to happen.

**2. Confusing member and collection**

```ruby
# "search one product" — still a member route if it needs :id
# "search all products" — collection route

# BAD — search doesn't need an :id
resources :products do
  member do
    get :search  # Would be /products/:id/search — wrong!
  end
end
```

### Mid-Level

**3. Too many custom actions**

If you have 10+ custom actions, consider extracting a new controller:

```ruby
# Instead of 8 member actions on ProductsController
resources :products do
  resource :inventory, only: [:show, :update]
  resource :pricing, only: [:show, :update]
end
```

**4. Not using `on:` shorthand for single actions**

```ruby
# Verbose
resources :products do
  collection do
    get :search
  end
end

# Clean
resources :products do
  get :search, on: :collection
end
```

### Senior/Lead

**5. Custom actions that should be PATCH updates**

```ruby
# QUESTIONABLE — publish is really an attribute update
post :publish, on: :member

# MORE RESTful for APIs
PATCH /products/42  { product: { status: "published" } }
```

For APIs, prefer updating attributes over custom action endpoints. Custom actions are fine for complex multi-step operations.

**6. Missing authorization on custom actions**

Custom actions often have different permission requirements than standard CRUD. Always add specific authorization:

```ruby
before_action :authorize_publish!, only: [:publish]
```

## 7. Performance Considerations

- Collection routes like `export` that process all records need pagination or background jobs
- `search` collection routes should use database indexes, not Ruby filtering
- Bulk operations (`bulk_update`, `bulk_delete`) should use background jobs for large datasets

```ruby
def bulk_delete
  BulkDeleteJob.perform_later(params[:ids])
  redirect_to products_path, notice: "Deletion queued"
end
```

---

## 8. Security Considerations

- **CSRF protection** — POST member/collection routes are protected by Rails CSRF tokens in forms
- **Authorization** — custom actions often have different permissions than CRUD
- **Rate limiting** — collection search/export endpoints are common abuse targets
- **Input validation** — bulk operations must validate IDs arrays

```ruby
def bulk_update
  ids = params[:ids]
  return head :bad_request unless ids.is_a?(Array) && ids.all? { |id| id.to_i > 0 }
  # ...
end
```

## 10. Best Practices

1. **Use POST for state changes**, GET for read-only custom actions
2. **Member = one record**, Collection = many/no specific record
3. **Keep custom actions focused** — one action, one responsibility
4. **Prefer PATCH for simple attribute changes** in APIs
5. **Extract to new controllers** when custom actions outnumber CRUD
6. **Name actions as verbs** — `publish`, `archive`, `export` (not `do_publish`)
7. **Add authorization** specific to each custom action

---

## 11. Anti-Patterns

| Anti-Pattern | Better Approach |
|---|---|
| GET for publish/delete/archive | POST or DELETE |
| 15 custom actions on one controller | Extract sub-controllers |
| `member { get :search }` | `collection { get :search }` |
| Custom action for simple field update | PATCH with attribute change |
| `post :update_status, on: :member` | PATCH `/products/:id` with `{ status: "..." }` |

## 12. Interview Questions

### Basic

**Q: What is the difference between a member route and a collection route?**

**A:** A member route operates on a single resource instance and includes `:id` in the URL (e.g., `POST /products/42/publish`). A collection route operates on the collection without a specific ID (e.g., `GET /products/search`).

### Intermediate

**Q: Why should state-changing actions use POST, not GET?**

**A:** GET requests can be triggered by link prefetching, browser history, crawlers, and caching proxies. A GET that modifies data causes accidental state changes and CSRF vulnerabilities. POST requires intentional form submission with CSRF protection.

### Senior

**Q: When would you extract custom actions into a separate controller instead of member routes?**

**A:** When the action represents a distinct resource or complex domain concept — e.g., `ProductInventoryController` instead of `ProductsController#update_inventory`. Also when custom actions outnumber standard CRUD, or when authorization/validation logic is significantly different.

## 13. Practical Examples

### Complete Example

```ruby
# config/routes.rb
resources :articles do
  member do
    post :publish
    post :unpublish
  end

  collection do
    get :search
    get :drafts
  end
end
```

```ruby
# app/controllers/articles_controller.rb
class ArticlesController < ApplicationController
  before_action :set_article, only: [:show, :edit, :update, :destroy, :publish, :unpublish]

  def search
    @articles = Article.where("title LIKE ?", "%#{params[:q]}%")
  end

  def drafts
    @articles = Article.where(published: false)
    render :index
  end

  def publish
    @article.update!(published: true, published_at: Time.current)
    redirect_to @article, notice: "Published!"
  end

  def unpublish
    @article.update!(published: false)
    redirect_to @article, notice: "Unpublished"
  end

  private

  def set_article
    @article = Article.find(params[:id])
  end
end
```

### View Usage

```erb
<%= link_to "Publish", publish_article_path(@article), data: { turbo_method: :post } %>
<%= link_to "Search", search_articles_path(q: "rails") %>

<%= form_with url: bulk_update_products_path, method: :post do |f| %>
  <%# bulk update form %>
<% end %>
```

## 15. Summary

1. **Member routes** = action on ONE record (`/products/:id/action`)
2. **Collection routes** = action on the GROUP (`/products/action`)
3. Use **POST for state changes**, GET for read-only
4. Shorthand: `get :search, on: :collection`
5. Extract to new controllers when custom actions proliferate
6. Always add proper **authorization** on custom actions

resources :products do
