## 1. Overview

### What it is

**Nested routes** express parent-child relationships between resources by embedding one resource's path inside another.

```ruby
resources :products do
  resources :reviews
end
```

This creates routes like:

```
GET /products/42/reviews          → ReviewsController#index
POST /products/42/reviews         → ReviewsController#create
GET /products/42/reviews/7        → ReviewsController#show
```

The parent ID (`42`) appears in the URL because a review **belongs to** a product.

### Why it exists

Nested routes make relationships visible in the URL. They tell both humans and machines: *"This review exists in the context of this product."*

This is useful for:
- Authorization scoping (find review through product)
- RESTful hierarchy modeling
- API discoverability (HATEOAS links)

### When to use nested routes

| Use nested routes when... | Example |
|---|---|
| Child cannot exist without parent | Product → Reviews |
| You always access child through parent | Order → LineItems |
| URL context matters for authorization | Shop → Products |

| Avoid nesting when... | Example |
|---|---|
| Child is independently accessible | User → Posts (use shallow instead) |
| Nesting goes deeper than 1 level | Product → Review → Comment (too deep) |
| Parent context is in session/JWT | Cart items (parent is session, not URL) |

### Common misconceptions

| Misconception | Reality |
|---|---|
| "Nested routes create nested controllers" | Controllers are still flat (`ReviewsController`) — only URLs nest |
| "You must nest in the database" | Nesting is a routing choice, not a DB requirement |
| "Deep nesting is fine" | Max 1 level of nesting is the Rails convention |
| "Nested routes auto-load the parent" | You must load `@product` yourself in the controller |

## 2. Core Concepts

### Basic Nesting

```ruby
resources :products do
  resources :reviews
end
```

Generated routes:

| Verb | Path | Action | Helper |
|---|---|---|---|
| GET | `/products/:product_id/reviews` | index | `product_reviews_path(product)` |
| POST | `/products/:product_id/reviews` | create | `product_reviews_path(product)` |
| GET | `/products/:product_id/reviews/new` | new | `new_product_review_path(product)` |
| GET | `/products/:product_id/reviews/:id` | show | `product_review_path(product, review)` |
| GET | `/products/:product_id/reviews/:id/edit` | edit | `edit_product_review_path(product, review)` |
| PATCH | `/products/:product_id/reviews/:id` | update | `product_review_path(product, review)` |
| DELETE | `/products/:product_id/reviews/:id` | destroy | `product_review_path(product, review)` |

Note the param name: `:product_id` (not `:id`) for the parent.

### Params in the Controller

```ruby
class ReviewsController < ApplicationController
  def index
    @product = Product.find(params[:product_id])
    @reviews = @product.reviews
  end

  def show
    @product = Product.find(params[:product_id])
    @review = @product.reviews.find(params[:id])
  end
end
```

Both `params[:product_id]` and `params[:id]` are available.

### Singular Nesting

When the parent is a singular resource:

```ruby
resource :profile do
  resources :addresses
end

# GET /profile/addresses       → AddressesController#index
# params[:profile_id] is NOT present — singular parent has no :id
```

### Multiple Nesting

```ruby
resources :shops do
  resources :products do
    resources :variants
  end
end

# GET /shops/1/products/42/variants/3
# params: { shop_id: "1", product_id: "42", id: "3" }
```

This works but is **discouraged** beyond one level. URLs become long and controllers become complex.

## 3. Internal Working

When Rails processes nested `resources`:

1. The outer `resources :products` creates a scope with path prefix `/products/:product_id`
2. Inner `resources :reviews` inherits that prefix → `/products/:product_id/reviews`
3. Parent param name is auto-generated: `:product_id` (parent resource name + `_id`)
4. Named helpers are prefixed: `product_reviews_path`, `product_review_path`
5. Journey compiles these as branches in the route tree

```ruby
# Conceptual expansion
scope '/products/:product_id' do
  resources :reviews, as: 'product_reviews'
end
```

## 4. Architecture

```text
URL Hierarchy                    Controller (Flat)              Models
─────────────                    ─────────────────              ──────
/products/42/reviews        →    ReviewsController#index   →   Product.has_many :reviews
/products/42/reviews/7      →    ReviewsController#show    →   Review.belongs_to :product
```

The URL is nested. The controller and models follow their own structure. Nesting is a **routing concern**, not an architectural mandate.

## 5. Real Production Examples

### Example 1: Shopify Product Variants

```ruby
resources :products do
  resources :variants, only: [:index, :create, :update, :destroy]
end

# Admin: POST /admin/products/123/variants
# Creates a variant belonging to product 123
```

### Example 2: Order Line Items

```ruby
resources :orders, only: [:show] do
  resources :line_items, only: [:create, :destroy]
end

# POST /orders/456/line_items  — add item to order
# DELETE /orders/456/line_items/789 — remove item
```

### Example 3: Comments on Blog Posts

```ruby
resources :posts do
  resources :comments, except: [:new, :edit]
end

# API-only: no HTML form routes needed
# GET  /posts/1/comments
# POST /posts/1/comments
```

## 6. Common Mistakes

### Beginner

**1. Forgetting to scope queries to parent**

```ruby
# BAD — finds ANY review, not just this product's
@review = Review.find(params[:id])

# GOOD — scoped through parent
@product = Product.find(params[:product_id])
@review = @product.reviews.find(params[:id])
```

**2. Wrong helper parameter order**

```ruby
# WRONG
review_path(@review, @product)

# RIGHT — parent first
product_review_path(@product, @review)
```

### Mid-Level

**3. Nesting too deeply**

```ruby
# BAD — 3 levels deep
resources :shops do
  resources :products do
    resources :reviews do
      resources :comments  # /shops/1/products/2/reviews/3/comments/4 😱
    end
  end
end

# GOOD — flatten with shallow routing or direct associations
```

**4. Nesting when parent context isn't needed**

If you access reviews directly (`/reviews/7`), don't nest them under products.

### Senior/Lead

**5. Authorization gaps in nested controllers**

```ruby
# Attacker changes product_id in URL to access another user's reviews
# Always authorize BOTH parent and child
authorize @product
authorize @review
```

**6. Not using `shallow: true` when appropriate**

See the Shallow Routing chapter — it solves the deep URL problem elegantly.

## 7. Performance Considerations

- Nested URLs are longer but recognition speed is unaffected
- Controllers that load parent + child add an extra DB query — use eager loading
- Consider caching parent lookup if the same product is hit repeatedly

```ruby
# Avoid N+1 when listing nested resources
@product = Product.includes(:reviews).find(params[:product_id])
```

---

## 8. Security Considerations

### Insecure Direct Object Reference (IDOR)

```ruby
# Attacker: GET /products/1/reviews/999
# If review 999 belongs to product 2, this should 404

@review = @product.reviews.find(params[:id])  # Scoped — safe
@review = Review.find(params[:id])             # Unscoped — IDOR vulnerability
```

Always find children **through** the parent association.

### Mass Assignment of Parent ID

```ruby
# Attacker POSTs { review: { product_id: 999, ... } }
# Ignore product_id from params — use route param instead

def create
  @product = Product.find(params[:product_id])
  @review = @product.reviews.build(review_params)  # product_id from route, not params
end
```

## 10. Best Practices

1. **Nest only 1 level deep** — use shallow routing beyond that
2. **Always scope child queries through parent** — prevents IDOR
3. **Use `only:` to limit nested routes** — don't generate unused actions
4. **Prefer shallow routing** when child has its own identity
5. **Load parent once** — use `before_action :set_product`
6. **Test with wrong parent/child combos** — ensure 404, not data leak

---

## 11. Anti-Patterns

| Anti-Pattern | Better Approach |
|---|---|
| 3+ levels of nesting | Flatten with shallow routes or direct routes |
| `@model = Model.find(params[:id])` in nested controller | Scope through parent association |
| Nesting unrelated resources | Only nest true parent-child relationships |
| Nested routes for every `belongs_to` | Nest only when URL context adds value |

## 12. Interview Questions

### Basic

**Q: What params are available in a nested `ReviewsController#show` for `/products/5/reviews/10`?**

**A:** `params[:product_id]` = `"5"`, `params[:id]` = `"10"`, plus `params[:controller]` and `params[:action]`.

### Intermediate

**Q: How deep should nesting go in a Rails app?**

**A:** One level maximum in most cases. Deeper nesting creates long URLs, complex controllers, and harder authorization. Use shallow routing or direct routes for deeper associations.

### Senior

**Q: A nested controller has an IDOR vulnerability. How do you fix it?**

**A:** Replace `Review.find(params[:id])` with `@product.reviews.find(params[:id])` where `@product = Product.find(params[:product_id])`. Add authorization checks on both parent and child. Write tests that attempt cross-parent access.

## 13. Practical Examples

### Standard Nested Resource

```ruby
# config/routes.rb
resources :products do
  resources :reviews, except: [:new, :edit]
end

# app/controllers/reviews_controller.rb
class ReviewsController < ApplicationController
  before_action :set_product

  def index
    @reviews = @product.reviews
  end

  def create
    @review = @product.reviews.build(review_params)
    if @review.save
      redirect_to product_review_path(@product, @review)
    else
      render :new, status: :unprocessable_entity
    end
  end

  def show
    @review = @product.reviews.find(params[:id])
  end

  private

  def set_product
    @product = Product.find(params[:product_id])
  end

  def review_params
    params.require(:review).permit(:rating, :body)
  end
end
```

### View Helpers

```erb
<%= link_to "Reviews", product_reviews_path(@product) %>
<%= link_to review.title, product_review_path(@product, review) %>

<%= form_with model: [@product, @review] do |f| %>
  <%# Generates POST /products/:product_id/reviews %>
<% end %>
```

## 15. Summary

1. Nested routes embed child resources inside parent paths
2. Parent ID becomes `params[:product_id]` in the child controller
3. **Always scope queries through parent** — security critical
4. Max **1 level** of nesting recommended
5. Use **shallow routing** when child is independently accessible
6. Controllers remain flat — nesting is URL-only
