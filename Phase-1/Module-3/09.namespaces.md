> **Module:** Phase 1 — Module 3 (Routing)
> **Topic:** Namespaces
> **Target Audience:** Rails developers preparing for Senior/Lead roles

---

## 1. Overview

### What it is

A **namespace** groups related routes under a common URL prefix and Ruby module, keeping your app organized as it grows.

```ruby
namespace :admin do
  resources :products
end

# Creates:
# GET /admin/products      → Admin::ProductsController#index
# GET /admin/products/1    → Admin::ProductsController#show
# Helper: admin_products_path, admin_product_path(id)
```

Three things happen at once:
1. **URL prefix** — `/admin/` is prepended to all paths
2. **Module nesting** — controllers live in `Admin::` module
3. **Helper prefix** — route helpers start with `admin_`

### Why it exists

Imagine a Shopify-scale app with public storefront, admin panel, API, and internal tools — all in one Rails app. Without namespaces, you'd have:

```ruby
# Nightmare without namespaces
get '/admin/products', to: 'admin_products#index'
get '/api/v1/products', to: 'api_v1_products#index'
get '/products', to: 'products#index'
```

Namespaces give you clean separation:

```ruby
namespace :admin do
  resources :products
end

namespace :api do
  namespace :v1 do
    resources :products
  end
end

resources :products  # public
```

### When to use namespaces

| Use case | Example |
|---|---|
| Admin panel | `namespace :admin` |
| API versioning | `namespace :api { namespace :v1 }` |
| Internal tools | `namespace :internal` |
| Different user roles | `namespace :merchant`, `namespace :customer` |
| Engine boundaries | `mount MyEngine => '/my_engine'` |

### Common misconceptions

| Misconception | Reality |
|---|---|
| "Namespace creates a folder automatically" | You must create `app/controllers/admin/` and `Admin::ProductsController` yourself |
| "Namespace and scope are the same" | `namespace` adds module + path; `scope` only adds path or module (not both) |
| "Nested namespaces create nested folders forever" | Two levels (`Api::V1::`) is typical; deeper nesting gets unwieldy |
| "Each namespace needs its own routes.rb" | One `routes.rb` with multiple namespaces is fine for most apps |

## 2. Core Concepts

### Basic Namespace

```ruby
namespace :admin do
  resources :products
end
```

| What | Value |
|---|---|
| URL | `/admin/products` |
| Controller | `Admin::ProductsController` |
| File path | `app/controllers/admin/products_controller.rb` |
| Helper | `admin_products_path` |

### Nested Namespaces

```ruby
namespace :api do
  namespace :v1 do
    resources :products
  end
end

# URL:        /api/v1/products
# Controller: Api::V1::ProductsController
# File:       app/controllers/api/v1/products_controller.rb
# Helper:     api_v1_products_path
```

### Namespace vs Scope vs Module

Rails provides three similar tools. Here's when to use each:

| Method | URL prefix | Module prefix | Helper prefix | Use when |
|---|---|---|---|---|
| `namespace :admin` | `/admin/` | `Admin::` | `admin_` | Full separation (most common) |
| `scope module: :admin` | No prefix | `Admin::` | None (unless `as:`) | Same URLs, different controllers |
| `scope '/admin'` | `/admin/` | None | None (unless `as:`) | URL prefix only, same controllers |
| `scope module: :admin, as: 'admin'` | No prefix | `Admin::` | `admin_` | Module + helpers, no URL change |

```ruby
# Full namespace — most common for admin/API
namespace :admin do
  resources :products
end
# → /admin/products → Admin::ProductsController

# Scope with module — same URL, different controller
scope module: :admin do
  resources :products
end
# → /products → Admin::ProductsController

# Scope with path — same controller, different URL
scope '/admin' do
  resources :products
end
# → /admin/products → ProductsController
```

### The `path` Option

Override the URL prefix without changing the module name:

```ruby
namespace :admin, path: 'backoffice' do
  resources :products
end

# URL: /backoffice/products
# Controller: Admin::ProductsController (unchanged)
# Helper: admin_products_path (unchanged)
```

### The `as` Option

Override the helper prefix:

```ruby
namespace :admin, as: 'backoffice' do
  resources :products
end

# Helper: backoffice_products_path (not admin_products_path)
```

## 3. Internal Working

When Rails processes `namespace :admin`:

1. **Path prefix** — `/admin` is pushed onto the path stack
2. **Module scope** — `Admin` module is pushed onto the module stack
3. **Named scope** — `admin` is pushed onto the `as` (helper prefix) stack
4. Inner routes inherit all three scopes
5. Controller name is built by joining modules: `Admin::ProductsController`

```ruby
# Conceptual expansion of namespace :admin do resources :products end
scope path: 'admin', module: 'admin', as: 'admin' do
  resources :products, controller: 'products'
end
```

## 4. Architecture — Organizing a Large App

```text
config/routes.rb
├── Public routes
│   ├── resources :products
│   └── resources :orders
│
├── namespace :admin
│   ├── resources :products (full CRUD)
│   ├── resources :users
│   └── resources :orders (manage all)
│
├── namespace :api
│   ├── namespace :v1
│   │   ├── resources :products (read-only)
│   │   └── resources :orders
│   └── namespace :v2
│       └── resources :products
│
└── namespace :internal
    └── resources :reports
```

```text
app/controllers/
├── products_controller.rb          # Public
├── orders_controller.rb            # Public
├── admin/
│   ├── products_controller.rb      # Admin::ProductsController
│   └── users_controller.rb         # Admin::UsersController
├── api/
│   └── v1/
│       └── products_controller.rb  # Api::V1::ProductsController
└── internal/
    └── reports_controller.rb       # Internal::ReportsController
```

## 5. Real Production Examples

### Example 1: Shopify Admin vs Storefront

```ruby
# Storefront (public)
resources :products, only: [:index, :show]
resource :cart

# Admin (merchant dashboard)
namespace :admin do
  resources :products do
    member { post :publish }
  end
  resources :orders, only: [:index, :show, :update]
  resources :customers
end
```

### Example 2: API Versioning

```ruby
namespace :api do
  namespace :v1 do
    resources :products, only: [:index, :show]
  end

  namespace :v2 do
    resources :products, only: [:index, :show] do
      # v2 includes embedded variants
    end
  end
end
```

When v2 introduces breaking changes, v1 continues working unchanged.

### Example 3: Splitting Routes Files

For large apps, extract namespaces into separate files:

```ruby
# config/routes.rb
Rails.application.routes.draw do
  draw :admin     # loads config/routes/admin.rb
  draw :api        # loads config/routes/api.rb

  resources :products  # public routes stay here
end

# config/routes/admin.rb
namespace :admin do
  resources :products
  resources :users
end
```

## 6. Common Mistakes

### Beginner

**1. Forgetting to create the namespaced controller file**

```ruby
namespace :admin do
  resources :products
end

# MUST create: app/controllers/admin/products_controller.rb
class Admin::ProductsController < ApplicationController
  # ...
end

# Missing file → Zeitwerk::NameError
```

**2. Wrong controller inheritance**

```ruby
# BAD — not in Admin module
class ProductsController < ApplicationController
  # This is the PUBLIC controller, not admin
end

# GOOD
class Admin::ProductsController < ApplicationController
end
```

### Mid-Level

**3. Duplicating logic across namespaces**

```ruby
# BAD — copy-pasted CRUD in Admin::ProductsController and ProductsController
# GOOD — shared concern or service layer
class Admin::ProductsController < ApplicationController
  include ProductActions  # shared logic
end
```

**4. Too many namespace levels**

```ruby
# BAD
namespace :api do
  namespace :internal do
    namespace :v2 do
      namespace :admin do  # Api::Internal::V2::Admin::ProductsController 😱
        resources :products
      end
    end
  end
end
```

### Senior/Lead

**5. Not having a base controller per namespace**

```ruby
# app/controllers/admin/base_controller.rb
class Admin::BaseController < ApplicationController
  before_action :authenticate_admin!
  layout 'admin'
end

class Admin::ProductsController < Admin::BaseController
  # Inherits admin auth and layout
end
```

**6. Missing namespace in tests**

```ruby
# Request spec must use namespaced path
get admin_products_path  # NOT products_path
```

## 7. Performance Considerations

Namespaces don't affect routing performance — they're compile-time path/module prefixes. The total number of routes matters more than how they're organized.

Split large route files with `draw` for developer experience, not performance.

---

## 8. Security Considerations

- **Each namespace needs its own authentication** — admin namespace must verify admin role
- **Don't rely on URL obscurity** — `/admin/products` is not secure because it's hard to guess
- **API namespaces need token authentication** — separate from session-based admin auth
- **Audit all namespaces** — run `bin/rails routes` and verify no namespace lacks authorization

```ruby
class Admin::BaseController < ApplicationController
  before_action :require_admin!

  private

  def require_admin!
    redirect_to root_path unless current_user&.admin?
  end
end
```

```bash
# Filter by namespace
bin/rails routes -g admin
bin/rails routes -g api

# Filter by controller
bin/rails routes -c Admin::ProductsController
```

```ruby
# Verify recognition
Rails.application.routes.recognize_path("/admin/products")
# => { controller: "admin/products", action: "index" }
```

Zeitwerk errors:

```
expected file app/controllers/admin/products_controller.rb to define
constant Admin::ProductsController, but didn't
```

Fix: Ensure class name matches file path exactly.

## 10. Best Practices

1. **Create a base controller** for each namespace (`Admin::BaseController`)
2. **Use `draw` to split routes** when `routes.rb` exceeds ~200 lines
3. **Limit nesting to 2 levels** (`Api::V1::`, not deeper)
4. **Share logic via concerns/services**, not copy-paste
5. **Separate layouts** per namespace (admin layout vs public layout)
6. **Test each namespace independently** with request specs

---

## 11. Anti-Patterns

| Anti-Pattern | Better Approach |
|---|---|
| One flat controller directory | Namespace by role/context |
| Copy-paste controllers per namespace | Shared concerns + thin controllers |
| 4+ levels of namespace nesting | Flatten or use engines |
| No base controller per namespace | `Admin::BaseController` with shared auth |
| Same routes in multiple namespaces | Extract shared routes or use scopes |

## 12. Interview Questions

### Basic

**Q: What three things does `namespace :admin` do?**

**A:** Adds `/admin/` URL prefix, nests controllers in the `Admin::` module, and prefixes route helpers with `admin_`.

### Intermediate

**Q: When would you use `scope module:` instead of `namespace`?**

**A:** When you want controllers in a different module but the same URL structure. For example, `scope module: :admin` routes `/products` to `Admin::ProductsController` without adding `/admin/` to the URL.

### Senior

**Q: How would you organize routes for a Rails app with public, admin, API v1, and API v2 sections?**

**A:**
1. Public routes at the top level
2. `namespace :admin` with `Admin::BaseController` for auth
3. `namespace :api` with nested `v1` and `v2` namespaces
4. Split into files: `draw :admin`, `draw :api`
5. Each namespace has its own base controller, layout, and authorization
6. Shared business logic in service objects, not duplicated controllers

## 13. Practical Examples

### Admin Namespace

```ruby
# config/routes.rb
namespace :admin do
  root 'dashboard#index'
  resources :products
  resources :orders, only: [:index, :show, :update]
  resources :users
end
```

```ruby
# app/controllers/admin/base_controller.rb
class Admin::BaseController < ApplicationController
  before_action :authenticate_user!
  before_action :require_admin!
  layout 'admin'
end

# app/controllers/admin/products_controller.rb
class Admin::ProductsController < Admin::BaseController
  def index
    @products = Product.all
  end
end
```

### API Versioning

```ruby
namespace :api do
  namespace :v1 do
    resources :products, only: [:index, :show]
    resources :orders, only: [:create, :show]
  end
end
```

```ruby
# app/controllers/api/v1/base_controller.rb
class Api::V1::BaseController < ActionController::API
  before_action :authenticate_api_token!
end

# app/controllers/api/v1/products_controller.rb
class Api::V1::ProductsController < Api::V1::BaseController
  def index
    render json: Product.all
  end
end
```

### Split Routes Files

```ruby
# config/routes.rb
Rails.application.routes.draw do
  draw :admin
  draw :api

  root 'home#index'
  resources :products, only: [:index, :show]
end

# config/routes/admin.rb
namespace :admin do
  root 'dashboard#index'
  resources :products
end
```

## 15. Summary

1. `namespace` adds URL prefix + module + helper prefix
2. Controllers go in matching directories (`admin/products_controller.rb` → `Admin::ProductsController`)
3. Use **base controllers** per namespace for shared auth/layout
4. Split large route files with **`draw`**
5. **`scope module:`** vs **`namespace`** — know the difference
6. Limit nesting to **2 levels** maximum
