> **Module:** Phase 1 — Module 3 (Routing)
> **Topic:** Concerns
> **Target Audience:** Rails developers preparing for Senior/Lead roles

---

## 1. Overview

### What it is

**Route concerns** are reusable chunks of route definitions that you can include in multiple places — just like Ruby modules for routes.

```ruby
# Define once
concern :commentable do
  resources :comments, except: [:new, :edit]
end

# Use many times
resources :articles, concerns: :commentable
resources :photos, concerns: :commentable
resources :videos, concerns: :commentable
```

Each resource gets identical comment routes without copy-pasting:

```
/articles/1/comments       → CommentsController#index
/photos/5/comments         → CommentsController#index
/videos/3/comments         → CommentsController#index
```

### Why it exists

Large Rails apps repeat the same route patterns:

- Commentable resources (articles, photos, videos)
- Publishable resources (posts, products, pages)
- Taggeable resources (everything needs tags)
- Auditable resources (track changes on many models)

Without concerns, you copy-paste the same block into every resource. With concerns, you define once and mix in anywhere.

### When to use route concerns

| Scenario | Concern |
|---|---|
| Multiple resources share nested routes | `:commentable`, `:taggable` |
| Common member/collection actions | `:publishable`, `:archivable` |
| Shared API patterns | `:paginatable`, `:searchable` |
| Engine route reuse | Concerns shared across engines |

### Common misconceptions

| Misconception | Reality |
|---|---|
| "Route concerns are controller concerns" | Different feature — route concerns are in `routes.rb`, controller concerns are in `app/controllers/concerns/` |
| "Concerns create shared controllers" | They create **duplicate routes** pointing to the same (or different) controllers |
| "Concerns affect route helpers" | Helpers are generated per resource — `article_comments_path` vs `photo_comments_path` |
| "You can only include one concern" | Pass an array: `concerns: [:commentable, :taggable]` |

## 2. Core Concepts

### Defining a Concern

```ruby
# config/routes.rb
concern :commentable do
  resources :comments, except: [:new, :edit]
end
```

The `concern` method defines a template. It does **not** create routes by itself — routes are created only when a resource `concerns:` it.

### Using a Concern

```ruby
resources :articles, concerns: :commentable
resources :photos, concerns: :commentable
```

This expands to:

```ruby
resources :articles do
  resources :comments, except: [:new, :edit]
end

resources :photos do
  resources :comments, except: [:new, :edit]
end
```

### Multiple Concerns

```ruby
concern :commentable do
  resources :comments
end

concern :taggable do
  resources :tags, only: [:index, :create, :destroy]
end

resources :articles, concerns: [:commentable, :taggable]
# Gets BOTH nested comment and tag routes
```

### Concerns with Member/Collection Actions

```ruby
concern :publishable do
  member do
    post :publish
    post :unpublish
  end
end

concern :searchable do
  collection do
    get :search
  end
end

resources :articles, concerns: [:publishable, :searchable]
resources :products, concerns: [:publishable, :searchable]
```

Both articles and products get publish/unpublish and search routes.

### Callable Concerns (Advanced)

Concerns can accept the parent resource name for dynamic routing:

```ruby
concern :reviewable do |options|
  resources :reviews, options.merge(except: [:new, :edit])
end

resources :products, concerns: :reviewable
resources :services, concerns: :reviewable do
  concerns :reviewable, shallow: true  # override options
end
```

### Extending Concerns in Place

You can combine concerns with additional routes:

```ruby
resources :articles, concerns: :commentable do
  member do
    post :feature  # article-specific action
  end
end
```

## 3. Internal Working

When Rails processes `concerns: :commentable`:

1. Looks up the concern block in the `RouteSet`'s concern registry
2. Evaluates the concern block within the current resource's scope
3. Generates routes as if you had written the block inline
4. Each inclusion creates **independent routes** with resource-specific helpers

```ruby
# Internal equivalent
resources :articles do
  # concern :commentable block evaluated here
  resources :comments, except: [:new, :edit]
end
```

Concerns are expanded at **route compile time** (boot), not at request time.

## 4. Architecture — DRY Routes in Large Apps

```text
config/routes.rb (or config/routes/concerns.rb)
│
├── concern :commentable    ──┐
├── concern :taggable       ──┤
├── concern :publishable    ──┤  Reusable templates
├── concern :searchable      ──┤
│                              │
├── resources :articles    ────┤ concerns: [:commentable, :publishable]
├── resources :photos      ────┤ concerns: [:commentable, :taggable]
├── resources :products     ────┤ concerns: [:publishable, :searchable]
└── resources :videos       ────┘ concerns: [:commentable]
```

At Shopify scale, route concerns prevent `routes.rb` from becoming thousands of lines of duplication.

## 5. Real Production Examples

### Example 1: Commentable Everything

```ruby
concern :commentable do
  resources :comments, only: [:index, :create, :destroy]
end

resources :articles, concerns: :commentable
resources :products, concerns: :commentable
resources :orders, concerns: :commentable
```

One `CommentsController` handles comments on any commentable resource, using `params[:article_id]`, `params[:product_id]`, etc.

### Example 2: Publishable Content

```ruby
concern :publishable do
  member do
    post :publish
    post :unpublish
    get :preview
  end
end

namespace :admin do
  resources :articles, concerns: :publishable
  resources :pages, concerns: :publishable
  resources :products, concerns: :publishable
end
```

### Example 3: Extracting Concerns to Separate Files

```ruby
# config/routes/concerns.rb
def commentable_routes
  concern :commentable do
    resources :comments, except: [:new, :edit]
  end
end

def publishable_routes
  concern :publishable do
    member do
      post :publish
      post :unpublish
    end
  end
end

# config/routes.rb
Rails.application.routes.draw do
  commentable_routes
  publishable_routes

  resources :articles, concerns: [:commentable, :publishable]
end
```

## 6. Common Mistakes

### Beginner

**1. Defining concern after using it**

```ruby
# BAD — concern not yet defined
resources :articles, concerns: :commentable

concern :commentable do
  resources :comments
end

# GOOD — define concerns first
concern :commentable do
  resources :comments
end

resources :articles, concerns: :commentable
```

**2. Expecting one controller to magically handle all concerns**

Each nested resource still needs a controller. Comments on articles and photos both hit `CommentsController`, which must handle different parent types.

### Mid-Level

**3. Over-using concerns for one-off routes**

```ruby
# BAD — only used once, no reuse benefit
concern :special_export do
  collection { get :export }
end

resources :reports, concerns: :special_export
# Just write the route inline instead
```

**4. Concerns that are too specific**

```ruby
# BAD — too specific to reuse
concern :article_feature do
  member { post :feature_on_homepage }
end
```

Concerns should capture **genuinely repeated patterns**.

### Senior/Lead

**5. Shared controller without polymorphic handling**

When a concern creates nested routes for different parents, the controller needs polymorphic logic:

```ruby
class CommentsController < ApplicationController
  before_action :set_commentable

  def index
    @comments = @commentable.comments
  end

  private

  def set_commentable
    @commentable = if params[:article_id]
      Article.find(params[:article_id])
    elsif params[:product_id]
      Product.find(params[:product_id])
    end
  end
end
```

Consider a polymorphic `Commentable` concern in the controller too.

## 7. Performance Considerations

Concerns have zero runtime performance impact — they're expanded at boot time. The number of generated routes is the same as if you wrote them inline.

Use concerns for **maintainability**, not performance.

---

## 8. Security Considerations

- Each concern inclusion creates real routes — audit them with `bin/rails routes`
- Shared controllers handling multiple parent types need authorization for each parent
- Don't use concerns to hide admin routes — they're still exposed in the route table

---

## 9. Debugging

```bash
# See all routes from a concern
bin/rails routes -g comments
bin/rails routes -g publish

# Verify concern expanded correctly
bin/rails routes -c CommentsController
```

If routes aren't appearing, check:
1. Is the concern defined **before** the resource?
2. Is the concern name spelled correctly in `concerns:`?
3. Did you use a symbol (`:commentable`) not a string?

---

## 10. Best Practices

1. **Define concerns at the top** of routes.rb (or in a separate file)
2. **Only extract genuinely repeated patterns** — 3+ uses minimum
3. **Name concerns as adjectives** — `:commentable`, `:publishable`, `:taggable`
4. **Extract to separate files** when you have 5+ concerns
5. **Document which resources use which concerns**
6. **Pair with controller concerns** for shared controller logic

---

## 11. Anti-Patterns

| Anti-Pattern | Better Approach |
|---|---|
| Concern used only once | Inline route definition |
| God concern with 10 actions | Split into focused concerns |
| Concern without controller support | Add matching controller concern |
| String instead of symbol | `concerns: :commentable` not `'commentable'` |

## 12. Interview Questions

### Basic

**Q: What are route concerns in Rails?**

**A:** Reusable route definition blocks that can be mixed into multiple resources. Define once with `concern :name`, include with `concerns: :name` on any resource.

### Intermediate

**Q: How do route concerns differ from controller concerns?**

**A:** Route concerns DRY up route definitions in `routes.rb`. Controller concerns DRY up controller logic in `app/controllers/concerns/`. They solve the same "reuse" problem in different layers and are often used together.

### Senior

**Q: You have 15 resources that all need comments, tags, and publish/unpublish. How do you organize the routes?**

**A:**
1. Define three concerns: `:commentable`, `:taggable`, `:publishable`
2. Include on each resource: `concerns: [:commentable, :taggable, :publishable]`
3. Extract concern definitions to `config/routes/concerns.rb`
4. Use a polymorphic `CommentsController` with a controller concern for shared logic
5. Audit with `bin/rails routes` to verify no unexpected routes

## 13. Practical Examples

### Basic Concern

```ruby
# config/routes.rb
Rails.application.routes.draw do
  concern :commentable do
    resources :comments, only: [:index, :create, :destroy]
  end

  resources :articles, concerns: :commentable
  resources :photos, concerns: :commentable
end
```

### Multiple Concerns

```ruby
concern :commentable do
  resources :comments, only: [:index, :create, :destroy]
end

concern :publishable do
  member do
    post :publish
    post :unpublish
  end
end

concern :searchable do
  collection do
    get :search
  end
end

resources :articles, concerns: [:commentable, :publishable, :searchable]
resources :products, concerns: [:commentable, :publishable, :searchable]
```

### Concerns in Separate File

```ruby
# config/routes/concerns.rb
def shared_concerns
  concern :commentable do
    resources :comments, only: [:index, :create, :destroy]
  end

  concern :publishable do
    member do
      post :publish
      post :unpublish
    end
  end
end

# config/routes.rb
Rails.application.routes.draw do
  shared_concerns

  resources :articles, concerns: [:commentable, :publishable]
  resources :products, concerns: [:commentable, :publishable]
end
```

## 15. Summary

1. Route concerns = **reusable route blocks** in `routes.rb`
2. Define with `concern :name`, include with `concerns: :name`
3. Expanded at **boot time** — zero runtime cost
4. Use for patterns repeated across **3+ resources**
5. Pair with **controller concerns** for full DRY
6. Not the same as controller concerns — different layer
