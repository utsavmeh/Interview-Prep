# Mastering ActionController

## 1. Overview
*   **What it is:** `ActionController` is the core component of Rails that handles HTTP requests, interacts with models, and delegates the response rendering to views. It acts as the "C" in the MVC (Model-View-Controller) architecture.
*   **Why it exists:** It provides a structured, predictable way to translate incoming web requests (like a user clicking a link or submitting a form) into application logic.
*   **When to use it:** Always. Every request that reaches your Rails application is ultimately processed by an instance of a controller (usually inheriting from `ApplicationController`).
*   **Common Misconceptions:**
    *   *"Controllers should contain business logic."* (False: Controllers should be thin. They should only orchestrate the flow between Models and Views. Business logic belongs in Models or Service Objects).
    *   *"A single controller instance handles multiple requests."* (False: A new controller instance is created for *every single request* and garbage-collected afterward. State is not preserved between requests in the controller object itself).

## 2. Core Concepts

### The Request Lifecycle
When an HTTP request hits a Rails app, the router (`config/routes.rb`) determines which controller and action (method) should handle it.
1.  **Routing:** Matches `GET /articles` to `ArticlesController#index`.
2.  **Instantiation:** Rails creates a new instance of `ArticlesController`.
3.  **Before Filters:** Any `before_action` callbacks are executed.
4.  **Action Execution:** The `index` method is run.
5.  **After Filters:** Any `after_action` callbacks are executed (rarely used compared to before_action).
6.  **Response:** The controller renders a template or returns data (like JSON), sending it back through the Rack middleware stack to the client.

### ActionController::Base vs ActionController::API
Modern Rails applications often act as APIs for frontend frameworks (React/Vue) or mobile apps.
*   **`ActionController::Base`**: The default. Includes everything needed to render HTML templates, manage session cookies, and protect against CSRF attacks.
*   **`ActionController::API`**: A stripped-down version. It removes modules like `ActionView`, `Cookies`, and `Flash`, making it significantly faster and lighter for JSON-only API endpoints.

## 3. Best Practices for Lead Engineers (Shopify Standard)

### 1. Keep Controllers "Skinny"
A controller action should ideally do only three things:
1.  Gather data (e.g., find a record).
2.  Perform an action (e.g., save a record, usually delegating to a Model or Service).
3.  Return a response (e.g., redirect or render).
If your action is longer than 5-10 lines, it's likely doing too much.

### 2. Embrace REST
Stick to the standard 7 RESTful actions. If you find yourself adding custom actions like `publish_article` or `activate_user`, you probably need a new controller.
*   **Bad:** `ArticlesController#publish`
*   **Good:** `ArticlePublicationsController#create`

### 3. Controller Concerns
For logic shared across *some* (but not all) controllers, use `ActiveSupport::Concern`. For example, if both `OrdersController` and `InvoicesController` need PDF generation logic, extract it into `app/controllers/concerns/pdf_renderable.rb`.

### 4. Dependency Injection & Service Objects
For complex operations that involve multiple models or external APIs, don't put the logic in the controller. Extract it into a Service Object.
```ruby
# Good: Controller is clean
def create
  result = ProcessOrderService.call(current_user, order_params)
  if result.success?
    redirect_to result.order, notice: 'Order placed!'
  else
    render :new, status: :unprocessable_entity
  end
end
```

## 4. Interview Preparation

### Q: Why does Rails create a new controller instance for every request?
**A:** To ensure thread safety and prevent state leakage between requests. If controllers were singletons, instance variables (`@user`) from User A's request could accidentally be served to User B if the server processes requests concurrently.

### Q: How would you refactor a controller action that is 50 lines long and handles payment processing?
**A:** I would extract the logic into a Service Object (e.g., `ProcessPaymentService`). The controller's only responsibility should be passing the parameters to the service and handling the success/failure response. This makes the code testable in isolation, adheres to the Single Responsibility Principle, and keeps the controller thin.
