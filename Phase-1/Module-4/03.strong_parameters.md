# Mastering Strong Parameters

## 1. Overview
*   **What it is:** A security feature in Rails that forces developers to explicitly whitelist which parameters are allowed to be used for mass-assignment (updating or creating records).
*   **Why it exists:** To prevent Mass Assignment vulnerabilities. Without it, a malicious user could submit unexpected data (like `is_admin=true`) via a form, and if the controller blindly passed that data to the model, the user could grant themselves admin privileges.
*   **When to use it:** Always, whenever you are creating or updating an Active Record model using data from the `params` object.
*   **Common Misconceptions:**
    *   *"Strong parameters validate data."* (False: They only filter *keys*. Validating the actual data format/content is the job of Model Validations).

---

## 2. Core Concepts

### The Mass Assignment Problem
Imagine a `User` model with attributes: `name`, `email`, and `is_admin`.
If a controller did this:
```ruby
# EXTREMELY DANGEROUS - Pre Rails 4 pattern
def update
  @user = User.find(params[:id])
  @user.update(params[:user]) 
end
```
A hacker could send a request with `<input name="user[is_admin]" value="1">`. Even though the form on your website only has `name` and `email` fields, the hacker bypassed the form and sent the raw HTTP request. The model would blindly update `is_admin` to true.

### The Solution: Require and Permit
Strong parameters use two main methods on the `params` object:
1.  **`require`**: Ensures that a specific key is present in the params hash. If it's missing, it throws an error.
2.  **`permit`**: Returns a new `ActionController::Parameters` object containing *only* the explicitly listed keys. Any unpermitted keys are silently dropped (and optionally logged).

```ruby
def update
  @user = User.find(params[:id])
  @user.update(user_params) # Safe!
end

private

def user_params
  # Requires the params to look like { user: { name: '...', email: '...' } }
  # and strictly drops :is_admin if it is sent.
  params.require(:user).permit(:name, :email)
end
```

## 3. Best Practices for Lead Engineers

### 1. Abstracting Params Logic
Always keep your parameter whitelisting in a private helper method at the bottom of the controller (e.g., `user_params`). This keeps the main actions clean and allows you to reuse the logic in both `create` and `update` actions.

### 2. Permitting Nested Attributes
When dealing with `accepts_nested_attributes_for` in models, you must permit the nested keys explicitly.
```ruby
def article_params
  params.require(:article).permit(
    :title, 
    :body,
    # Permitting an array of primitive values
    tag_ids: [], 
    # Permitting an array of nested hashes
    comments_attributes: [:id, :body, :_destroy] 
  )
end
```

### 3. Context-Aware Permitting (Role-Based)
At scale (like at Shopify), not all users are allowed to update all attributes. A lead engineer knows to dynamically adjust permitted parameters based on the current user's roles.
```ruby
def user_params
  permitted = [:name, :email]
  permitted << :role if current_user.admin?
  params.require(:user).permit(permitted)
end
```

## 4. Interview Preparation

### Q: What happens if a parameter is passed that isn't explicitly permitted? Does the app crash?
**A:** No, the app does not crash. `permit` simply filters the hash. The unpermitted parameter is silently dropped from the returned hash. However, in development/test environments, Rails will log a warning: `"Unpermitted parameter: :is_admin"`. You can configure Rails to raise an error on unpermitted parameters using `ActionController::Parameters.action_on_unpermitted_parameters = :raise`, which is highly recommended to catch typos during development.

### Q: Why do we use Strong Parameters in the Controller instead of the Model?
**A:** Security is a context-dependent concern. The Model shouldn't care *who* is updating it; it only cares that the data is valid (format, presence). The Controller knows the context (e.g., Is this an admin making the request? Is this a public API?). Therefore, deciding *what* attributes are allowed to be changed in a specific HTTP request is strictly a controller responsibility.
