# Redirecting in Rails

## 1. Overview
*   **What it is:** Instructing the user's browser to make a brand new HTTP request to a different URL.
*   **Why it exists:** Crucial for web navigation, particularly after state-changing actions (POST, PUT, DELETE) to prevent the "Form Resubmission" warning if a user hits the back/refresh button. (This is known as the Post/Redirect/Get or PRG pattern).
*   **When to use it:** After successfully creating, updating, or deleting a resource, or when enforcing authentication constraints (e.g., redirecting an unauthenticated user to the login page).
*   **Common Misconceptions:**
    *   *"Redirecting passes data to the next view."* (False: A redirect triggers a *completely new HTTP request*. Instance variables like `@user` from the first request are lost. To pass data across a redirect, you must use the `session` or `flash`).
    *   *"Render and Redirect are interchangeable."* (False: See the deep dive below).

## 2. Core Concepts

### `redirect_to`
The primary method for issuing redirects. It returns an HTTP `302 Found` (temporary redirect) response by default.
```ruby
def create
  @article = Article.new(article_params)
  if @article.save
    # Tells the browser: Make a new GET request to /articles/:id
    redirect_to article_path(@article) 
  else
    render :new
  end
end
```

### Hotwire and `303 See Other`
If you are building a modern Rails app using Turbo (Hotwire), a standard 302 redirect after a form submission (POST/PUT/PATCH/DELETE) will cause Turbo to fail. You must explicitly tell the browser to change the HTTP method to GET using the `303 See Other` status.
```ruby
# The modern Rails 7+ standard for form submission redirects
redirect_to @article, status: :see_other
```

### `redirect_back`
Redirects the user to the page they just came from (using the HTTP `Referer` header). You must provide a `fallback_location` in case the header is missing.
```ruby
def destroy
  @comment.destroy
  redirect_back(fallback_location: root_path)
end
```

### Render vs. Redirect (The Most Important Distinction)
*   **`render`**: Does *not* change the URL. Does *not* create a new request. It uses the data gathered in the *current* action to build HTML and sends it back. (Used when form validations fail so you don't lose the user's input).
*   **`redirect_to`**: Changes the URL. Forces the browser to make a *new* request to that URL. The server processes that new request from scratch. (Used after a successful save).

## 3. Best Practices for Lead Engineers

### 1. The Post/Redirect/Get (PRG) Pattern
Never render a view directly after a successful POST/PATCH/DELETE request. Always redirect. If you render HTML directly from a POST request, and the user hits "Refresh" in their browser, the browser will attempt to re-submit the POST data, potentially creating duplicate records or causing errors.

### 2. Using `return` with Redirects
Like `render`, `redirect_to` does not stop the execution of the action. If you conditionally redirect early in a method, you must explicitly `return`.
```ruby
def show
  # Good: execution halts
  redirect_to(new_system_path) and return if params[:id] == 'legacy'
  
  @item = Item.find(params[:id])
end
```

### 3. Open Redirect Vulnerabilities
A severe security flaw occurs if you allow a user to specify the redirect URL via params without sanitizing it.
*   **Dangerous:** `redirect_to params[:return_to]`
*   **Exploit:** A hacker sends a phishing link to your user: `https://your-bank.com/login?return_to=http://hacker-bank.com`. The user logs in to your legitimate site, and your code redirects them to the hacker's site, which looks identical.
*   **Rails 7+ Fix:** Rails now blocks redirects to external hosts by default. If you *must* redirect externally, explicitly allow it: `redirect_to params[:url], allow_other_host: true`.

## 4. Interview Preparation

### Q: A user submits a signup form with an invalid email. Should you `render :new` or `redirect_to new_user_path`? Why?
**A:** You must `render :new` (with an unprocessable entity status). If you `redirect_to new_user_path`, the browser makes a fresh GET request. The `@user` instance variable containing the user's typed data and the validation error messages is lost. The form would appear completely blank, frustrating the user. `render` keeps the state of the current request and draws the form around the invalid object.

### Q: Why do Hotwire/Turbo form submissions require `status: :see_other` (303)?
**A:** When Turbo intercepts a form submission (e.g., a POST request) and receives a standard 302 redirect, standard `fetch` behavior attempts to follow the redirect using the *same HTTP method* (POST) to the new URL. This causes routing errors. A 303 status explicitly instructs the browser to drop the POST method and follow the redirect using a GET request.
