# ActionController Filters (Callbacks)

## 1. Overview
*   **What it is:** Filters (also called Controller Callbacks) are methods that are run "before", "after", or "around" a controller action.
*   **Why it exists:** To DRY up (Don't Repeat Yourself) controller code by extracting common logic that needs to run across multiple actions (like checking authentication or finding a record).
*   **When to use it:** When multiple actions in a controller require identical setup or teardown logic.
*   **Common Misconceptions:**
    *   *"Filters only apply to the whole controller."* (False: You can specifically target or exclude actions using `only:` and `except:`).
    *   *"Filters shouldn't modify the response."* (False: A `before_action` can render or redirect, completely halting the request before it even reaches the main action).

---

## 2. Core Concepts

### 1. `before_action`
The most common filter. It runs before the action executes. If a `before_action` calls `render` or `redirect_to`, the filter chain is halted, and the actual action is never executed.

### 2. `after_action`
Runs *after* the action has executed, but *before* the response is sent back to the client. It has access to the response object but cannot alter the fact that rendering/redirecting has already occurred. Mostly used for modifying headers or logging.

### 3. `around_action`
Wraps the action. The filter method must `yield` to execute the actual action. If you don't yield, the action never runs. Useful for measuring performance or wrapping actions in database transactions.
```ruby
around_action :time_request

def time_request
  start_time = Time.now
  yield # The actual controller action runs here
  elapsed = Time.now - start_time
  Rails.logger.info("Request took #{elapsed} seconds")
end
```

### 4. Skipping and Prepending Filters
If a parent class defines a filter, but a child controller doesn't need it, use `skip_before_action`.
If you need a filter to run *before* any other filters inherited from a parent class (like authentication checks), use `prepend_before_action`.
```ruby
class WebhooksController < ApplicationController
  # Skip the standard login check
  skip_before_action :require_login
  
  # Ensure the signature is verified before ANY other filter runs
  prepend_before_action :verify_webhook_signature
end
```

## 3. Best Practices for Lead Engineers

### 1. The Security Trap of `except:` vs `only:`
Lead engineers strongly prefer `only:` over `except:` when applying filters like authentication or authorization.
*   **Dangerous:** `before_action :require_login, except: [:index, :show]`
    *   *Why:* If a junior developer adds a new action `def search` 6 months later, it is *implicitly* unprotected because it's not in the `except` array. This is a severe security vulnerability.
*   **Safe:** `before_action :require_login, only: [:edit, :update, :destroy]`
    *   *Why:* It fails securely. If a new action is added, it defaults to running the filter unless explicitly whitelisted. (Better yet, define the filter globally in ApplicationController and explicitly `skip` it where public access is needed).

### 2. The Rule of Three (Don't Prematurely Abstract)
Don't create a `before_action` to set an instance variable just because two actions use it. Only abstract it to a `before_action :set_record` if three or more actions require it (like standard scaffold CRUD: `show`, `edit`, `update`, `destroy`). Premature abstraction makes the controller harder to read because the dependencies of an action are hidden.

### 3. Keep Logic Private
Filter methods should almost always be declared as `private`. They are internal routing mechanics, not public endpoints.

## 4. Interview Preparation

### Q: How do you halt a request in a `before_action`?
**A:** By calling `render` or `redirect_to` inside the filter. In older versions of Rails, returning `false` would halt the chain, but this was deprecated. Now, only rendering or redirecting halts the execution chain.

### Q: What is the architectural downside of heavy reliance on `before_action`?
**A:** It obscures the code. When you look at an action like `def show; end`, you don't immediately know what data is available. You have to scroll up, check the `before_actions`, check `only/except` arrays, and mentally trace the state. Lead engineers prefer explicit dependency injection or service objects over deeply nested inheritance chains of `before_actions` that just set instance variables.
