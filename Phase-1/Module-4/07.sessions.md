# Sessions in Rails

## 1. Overview
*   **What it is:** The Session is a mechanism that allows a Rails application to store state (data) for a specific user across multiple HTTP requests.
*   **Why it exists:** HTTP is a stateless protocol. Every request is completely independent. Without sessions, a web server wouldn't know if the person requesting the "checkout" page is the same person who just added an item to the "cart" page.
*   **When to use it:** Storing the current logged-in user's ID, shopping cart contents, or temporary multi-step wizard data.
*   **Common Misconceptions:**
    *   *"Sessions and Cookies are the same thing."* (False: A cookie is the transport mechanism. A session is the logical state. Rails *defaults* to storing session data *inside* a cookie, but sessions can also be stored in databases or Redis).

---

## 2. Core Concepts

### Accessing the Session
Inside controllers and views, you have access to a hash-like object called `session`.
```ruby
# Writing to the session
session[:user_id] = @user.id

# Reading from the session
current_user_id = session[:user_id]

# Deleting from the session (logging out)
session.delete(:user_id)
# or clear everything: reset_session
```

### The CookieStore (Rails Default)
By default, Rails uses `ActionDispatch::Session::CookieStore`. This means that whatever you put into the `session` hash is serialized (converted to a string), encrypted, cryptographically signed, and sent back to the browser as a Cookie.
On the next request, the browser sends the cookie back. Rails decrypts and verifies the signature, and reconstitutes the `session` hash.

### Server-Side Session Stores
If you store large amounts of data in the session, you will hit the browser's 4KB cookie size limit, and significantly bloat HTTP request sizes. In that case, you change the storage engine.
*   **CacheStore (Redis/Memcached):** Stores session data in memory. Highly recommended for enterprise applications. It is incredibly fast and allows for centralized session revocation (e.g., logging a user out of all their active devices).
*   **ActiveRecordStore:** Stores session data in a database table. (Slower, but infinite size and easy to query).
When using these stores, Rails only puts a unique 32-character "Session ID" in the browser cookie. The server uses that ID to look up the data payload in Redis/Database.

## 3. Best Practices for Lead Engineers

### 1. Store IDs, Not Objects
Never store full ActiveRecord objects in the session.
*   **Bad:** `session[:user] = @user`
*   **Why:** If the user's data changes in the database, the session data will be stale. Also, it causes `CookieOverflow` errors.
*   **Good:** `session[:user_id] = @user.id`. Always fetch the fresh object from the database using the ID.

### 2. Guard Against Session Fixation Attacks
Session Fixation is a severe vulnerability where an attacker forces a user to use a known session ID, waits for them to log in, and then hijacks the authenticated session.
**The Fix:** You must *always* call `reset_session` immediately before or immediately after changing a user's privilege level (e.g., logging in or logging out). This issues a brand new cryptographic session ID to the browser, invalidating the one the attacker possessed.

### 3. Session Replay Attacks (CookieStore specific)
If a user's session cookie is stolen, the attacker can use it indefinitely. Because CookieStore data lives entirely on the client, you cannot "delete" a session from the server (there is no database record to delete). To mitigate this in CookieStore, you must store a `session_token` in the database, add it to the session, and verify it on every request. If the user changes their password, rotate the database token, which instantly invalidates all existing CookieStore sessions.

## 4. Interview Preparation

### Q: How does Rails secure the default session cookie? Can a user modify their `user_id` to become an admin?
**A:** No, they cannot modify it. Rails encrypts and cryptographically signs the session cookie using the application's `secret_key_base`. If a user attempts to alter the cookie payload, the cryptographic signature will become invalid. When Rails attempts to read the cookie on the next request, the signature verification will fail, and Rails will discard the cookie, treating the user as having an empty session.

### Q: Why might a high-traffic app like Shopify choose Redis over the default CookieStore for sessions?
**A:** While CookieStore requires zero infrastructure, it increases network payload size drastically if session data grows. Redis allows for virtually unlimited session data size, keeps network payloads minimal (only sending a tiny Session ID cookie), and crucially, provides centralized session management. With Redis, an admin can "revoke all active sessions" for a compromised account by deleting the keys in Redis, which is impossible with CookieStore since the data lives on the user's physical device.
