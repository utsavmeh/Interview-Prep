# Cookies in Rails

## 1. Overview
*   **What it is:** A small piece of data sent from a web server and stored on the user's computer by the user's web browser. Rails provides a `cookies` hash-like object to easily manage them.
*   **Why it exists:** To store long-term state on the client-side that persists even after the browser is closed (unlike standard sessions).
*   **When to use it:** "Remember Me" functionality, tracking user preferences (like Dark Mode vs Light Mode), or storing tracking/analytics IDs.
*   **Common Misconceptions:**
    *   *"Sessions and Cookies are the same."* (False: Sessions are a server-side concept that often *utilizes* cookies for transport. The `cookies` object in Rails is for direct, raw cookie manipulation).
    *   *"Cookies are secure."* (False: By default, plain cookies can be read and modified by the end-user. You must explicitly use signed or encrypted cookies for sensitive data).

---

## 2. Core Concepts

### Accessing Cookies
The `cookies` object behaves much like the `session` and `params` hashes.
```ruby
# Writing a simple plaintext cookie
cookies[:theme] = "dark_mode"

# Reading a cookie
current_theme = cookies[:theme]

# Deleting a cookie
cookies.delete(:theme)
```

### Cookie Expiration and Domain
By default, plain cookies expire when the browser is closed (a "session cookie"). You can define explicit expiration dates.
```ruby
# Shorthand for setting a cookie that expires in 20 years
cookies.permanent[:user_preference] = "grid_view"
```

### Security Layers (Encryption and Signing)
Because plain cookies are readable and writable by the user, Rails provides security wrappers:
1.  **Signed Cookies:** `cookies.signed[:user_id] = 42`. 
    *   *Result:* The user can read the value (42), but cannot modify it. If they change it, the cryptographic signature fails, and Rails reads it as `nil`.
2.  **Encrypted Cookies:** `cookies.encrypted[:secret] = "classified"`. 
    *   *Result:* The user cannot read the value, nor can they modify it. It looks like random garbage text to the browser.

## 3. Best Practices for Lead Engineers

### 1. Implement "Remember Me" Securely
Never store the user's database ID directly in a long-lived cookie, even if signed. If the cookie is stolen, the thief has access forever.
Instead, use the "Token" pattern: Generate a random string, hash it in the database (`users.remember_digest`), and store the plain string in a signed cookie. If compromised, you invalidate the token in the database, rendering the stolen cookie useless.

### 2. Mind the Flags: HttpOnly, Secure, and SameSite
Modern web security relies heavily on cookie configuration flags:
*   **HttpOnly:** Ensures the cookie cannot be read by JavaScript (`document.cookie`). This mitigates Cross-Site Scripting (XSS) attacks. Rails sets this to `true` by default for the session cookie.
*   **Secure:** Ensures the cookie is only sent over HTTPS, never over plain HTTP.
*   **SameSite:** Crucial for preventing Cross-Site Request Forgery (CSRF). 
    *   `Strict`: The cookie is only sent if the request originates from your exact domain.
    *   `Lax` (Rails default): The cookie is sent on top-level navigation (like a user clicking a link to your site), but withheld on cross-site POST requests.
    *   `None`: The cookie is always sent (requires the `Secure` flag). Required for building third-party embedded apps (like a Shopify App embedded in an iframe).

### 3. CSRF Protection (`protect_from_forgery`)
Rails automatically includes `protect_from_forgery with: :exception` in ApplicationController. This drops a special CSRF token in a cookie and the HTML `<head>`. When a form is submitted via POST/PUT/DELETE, Rails verifies the token in the params matches the token in the cookie. If a malicious site tricks a logged-in user into submitting a POST request to your bank app, the tokens won't match, and the request is rejected.

## 4. Interview Preparation

### Q: What is the difference between `cookies.signed` and `cookies.encrypted`?
**A:** `cookies.signed` appends a cryptographic signature to the plain text value. The user can decode and read the data, but any tampering will invalidate the signature. `cookies.encrypted` uses AES encryption. The data is entirely obfuscated so the user cannot read the contents at all, nor can they tamper with it.

### Q: You are building a Rails API that serves a separate React frontend on a different domain. Authentication uses cookies. Why are your POST requests failing with 401 Unauthorized?
**A:** This is likely a CORS and `SameSite` issue. Browsers block sending cookies across different domains via AJAX by default to prevent CSRF attacks. To fix this, your API must set the session/authentication cookie with `SameSite: :none` and `Secure: true`. Additionally, the frontend must be configured to send credentials (`withCredentials: true` in Axios or Fetch), and the Rails CORS configuration must explicitly allow the frontend domain and allow credentials.
