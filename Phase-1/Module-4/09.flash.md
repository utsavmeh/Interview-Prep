# The Flash Hash in Rails

## 1. Overview
*   **What it is:** A specialized part of the session used to pass temporary messages (like "Item saved successfully" or "Invalid password") from one request to the very next request.
*   **Why it exists:** When you successfully submit a form, you redirect the user (PRG pattern). Since HTTP is stateless, the new request has no idea the previous action was a success. The flash bridges this gap, persisting a message for exactly one request.
*   **When to use it:** Success notifications, error warnings, and informational alerts presented to the user after an action.
*   **Common Misconceptions:**
    *   *"The flash is a permanent database record."* (False: It lives in the session cookie and vanishes almost instantly).
    *   *"You only use it after redirects."* (False: You can use it with `render` via `flash.now`).

---

## 2. Core Concepts

### Setting the Flash
The `flash` is a hash-like object available in controllers and views. Standard keys are `:notice` (for success/info) and `:alert` (for errors).
```ruby
def create
  @article = Article.new(article_params)
  if @article.save
    # Persists for the NEXT request
    flash[:notice] = "Article successfully created."
    redirect_to @article
  end
end
```
*Rails Shorthand:* You can pass notice and alert directly in the redirect:
`redirect_to @article, notice: "Article successfully created."`

### `flash.now`
If an action fails (e.g., validation fails), you typically `render :new` rather than redirecting. If you use the standard `flash[:alert]`, the message will appear on the current rendered page, but *it will also incorrectly persist to the next page the user visits*. 
To solve this, use `flash.now`. It makes the message available to the *current* request's view, but immediately deletes it so it won't appear on the next request.
```ruby
def create
  if @article.save
    redirect_to @article, notice: "Success"
  else
    # Displays on the rendered form, doesn't persist to next click
    flash.now[:alert] = "Please fix the errors below."
    render :new
  end
end
```

### `flash.keep`
If you set a flash message, but the current request ends up issuing *another* redirect (e.g., passing through a middleware or an intermediate controller), the flash will be lost before it reaches the final rendered view. You can use `flash.keep` to tell Rails to preserve the current flash messages for one more request lifecycle.

## 3. Best Practices for Lead Engineers

### 1. Don't Store Complex Objects in the Flash
Because the flash is stored in the session (which is usually a 4KB cookie), do not put ActiveRecord models or large arrays in it. Use it exclusively for short strings.
*   **Bad:** `flash[:failed_object] = @user`
*   **Good:** `flash[:error] = "User failed to save."`

### 2. Standardize Flash Keys
Stick to `:notice` and `:alert`. If you need custom levels (like `:warning` or `:success`), map them to standard CSS classes (like Bootstrap's alerts or Tailwind components) in a dedicated helper method. Consistency prevents UI bugs where a message is set in the controller but not handled in the layout loop.

### 3. Flash and Hotwire (Turbo)
In modern Rails with Hotwire, standard redirects following form submissions require the HTTP status to be `303 See Other`. Also, if you use Turbo Streams to update parts of a page, the global flash in the layout won't automatically update because there is no full page reload. Lead engineers implement specialized Turbo Stream responses to explicitly append flash messages to a dedicated flash container in the DOM.

## 4. Interview Preparation

### Q: A user submits a form with missing data. The page re-renders, showing a red banner: "Validation failed". The user clicks the "Home" link. The homepage loads, but the red "Validation failed" banner is still there! Why?
**A:** The developer used `flash[:alert] = "Validation failed"` instead of `flash.now[:alert] = "Validation failed"`. Because they called `render :new` instead of redirecting, the standard `flash` persisted the message into the session cookie for the *next* request. When the user clicked "Home", that constituted the next request, so the flash was finally displayed and cleared on the homepage.
