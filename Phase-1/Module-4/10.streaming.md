# Streaming in Rails Controllers

## 1. Overview
*   **What it is:** The ability of a Rails controller to send data to the client in chunks over an open connection, rather than waiting for the entire response to be generated before sending anything.
*   **Why it exists:** To handle long-running requests without timing out, to process massive file downloads efficiently without consuming gigabytes of server RAM, and to push real-time events to the browser.
*   **When to use it:** Generating large CSV exports, sending Server-Sent Events (SSE) for real-time notifications, or playing large media files.
*   **Common Misconceptions:**
    *   *"Streaming is just for WebSockets."* (False: WebSockets (ActionCable) are bidirectional. HTTP Streaming (like `ActionController::Live`) is primarily unidirectional (server to client) over standard HTTP).

---

## 2. Core Concepts

### `ActionController::Live`
To enable streaming in a controller, you must include the `ActionController::Live` module.
```ruby
class ExportsController < ApplicationController
  include ActionController::Live

  def download
    response.headers['Content-Type'] = 'text/event-stream'
    
    10.times do |i|
      response.stream.write "Data chunk #{i}\n"
      sleep 1 # Simulating slow work
    end
  ensure
    # CRITICAL: You must always close the stream!
    response.stream.close
  end
end
```
In this example, the browser receives a chunk of data every second, rather than waiting 10 seconds for the whole file.

### Server-Sent Events (SSE)
SSE is a standard for pushing notifications from the server to the browser over HTTP. Rails provides `ActionController::Live::SSE` to format the data correctly.

### File Streaming (`send_file` and `send_data`)
For simple file downloads, you don't need `ActionController::Live`. Rails has built-in methods:
*   `send_file`: Efficiently streams a file from the server's hard drive directly to the client. It often hands the work off to the underlying web server (like NGINX via `X-Sendfile`), freeing up the Ruby process entirely.
*   `send_data`: Streams binary data generated in memory (like a dynamically created PDF) to the client.

## 3. Best Practices for Lead Engineers

### 1. Thread Safety is Mandatory
When you include `ActionController::Live`, Rails spawns a new thread to handle the request. This means your controller code *must* be thread-safe. Avoid mutating global state or class variables, as multiple streams might be executing simultaneously.

### 2. Always Close the Stream
Notice the `ensure { response.stream.close }` blocks. If you fail to close the stream, the thread on the server remains open forever. Eventually, your web server (e.g., Puma) will run out of worker threads, and your entire application will freeze and go offline. This is a common and catastrophic mistake.

### 3. Database Connection Pool Exhaustion (The Silent Killer)
Because `ActionController::Live` spawns a thread, it checks out a database connection from the ActiveRecord pool. If you hold a stream open for a long time (like a real-time notification feed), you are holding that database connection hostage. If you have 50 active streams and a database pool size of 20, the app will crash. 
**The Fix:** Lead engineers ensure the database connection is yielded back to the pool explicitly inside the thread if the stream doesn't continuously need it.
```ruby
def stream
  # Yields connection back to the pool while the stream waits
  ActiveRecord::Base.connection_pool.with_connection do
    @data = User.all.to_a
  end
  # Do non-database streaming work here...
end
```

## 4. Interview Preparation

### Q: What is the difference between `ActionCable` (WebSockets) and `ActionController::Live` (SSE)?
**A:** ActionCable provides a persistent, full-duplex (two-way) connection. The client can send data to the server, and the server can push to the client simultaneously. It's ideal for chat apps. `ActionController::Live` (using SSE) is half-duplex (one-way). The client opens the connection, and the server continuously pushes data down. It is simpler, uses standard HTTP, and is ideal for live dashboards or progress bars where the client only needs to listen.

### Q: Why is `send_file` considered highly optimized compared to reading a file in Ruby and using `render`?
**A:** When configured correctly with a web server like NGINX, `send_file` sets an `X-Sendfile` (or `X-Accel-Redirect`) HTTP header. NGINX intercepts this header, takes over the file transfer directly from the filesystem, and immediately releases the Ruby Puma worker. Ruby does exactly zero work to transfer the file, allowing the Rails app to handle other incoming requests instantly.
