# Exception Handling in Controllers

## 1. Overview
*   **What it is:** The strategy for intercepting errors (Exceptions) that occur during a web request and translating them into friendly, predictable HTTP responses (like 404 Not Found or 500 Internal Server Error).
*   **Why it exists:** If an unhandled exception occurs in Ruby, the application crashes and the user sees an ugly stack trace (in development) or a generic server failure screen (in production). Proper exception handling ensures graceful degradation and proper API responses.
*   **When to use it:** Dealing with missing database records, unauthorized access attempts, external API timeouts, or invalid parameter structures.
*   **Common Misconceptions:**
    *   *"You should use `begin/rescue` blocks in every controller action."* (False: This is an anti-pattern. You should handle exceptions globally using `rescue_from` to keep actions clean).
    *   *"Controllers are the only place errors are handled."* (False: The `ActionDispatch::ShowExceptions` middleware sits above the controllers and acts as the ultimate safety net).

## 2. Core Concepts

### Global Handling with `rescue_from`
Rails provides the `rescue_from` macro to define how specific exceptions should be handled at the controller class level. It is typically defined in `ApplicationController` so it applies to all controllers.

```ruby
class ApplicationController < ActionController::Base
  # Intercept ActiveRecord::RecordNotFound exceptions globally
  rescue_from ActiveRecord::RecordNotFound, with: :render_not_found

  private

  def render_not_found(exception)
    # Log the error internally
    Rails.logger.error(exception.message)
    
    # Respond based on the request format
    respond_to do |format|
      format.html { render file: "#{Rails.root}/public/404.html", status: :not_found, layout: false }
      format.json { render json: { error: 'Resource not found' }, status: :not_found }
    end
  end
end
```
Now, if *any* controller does `User.find(params[:id])` and the ID doesn't exist, it automatically renders a 404 instead of crashing with a 500.

### Built-in Rails Rescues (ActionDispatch::ShowExceptions)
Even if you don't write `rescue_from`, your app won't crash the server. A middleware called `ActionDispatch::ShowExceptions` catches unhandled errors and maps them to HTTP status codes in production (rendering the files in the `public/` directory, like `public/404.html`):
*   `ActiveRecord::RecordNotFound` -> `404 Not Found`
*   `ActionController::RoutingError` -> `404 Not Found`
*   `ActionController::ParameterMissing` -> `400 Bad Request`
*   `ActionController::InvalidAuthenticityToken` -> `422 Unprocessable Entity`

## 3. Best Practices for Lead Engineers

### 1. Avoid Rescue-Driven Flow Control
Do not use exceptions for expected business logic. Exceptions are for *exceptional* circumstances.
*   **Bad:**
    ```ruby
    begin
      @user = User.find_by!(email: params[:email])
    rescue ActiveRecord::RecordNotFound
      redirect_to signup_path
    end
    ```
*   **Good:**
    ```ruby
    @user = User.find_by(email: params[:email])
    if @user
      # login
    else
      redirect_to signup_path
    end
    ```

### 2. Order of `rescue_from` Matters
`rescue_from` handlers are evaluated from bottom to top (the last one defined takes precedence).
```ruby
class ApplicationController < ActionController::Base
  # 1. This acts as a catch-all for any StandardError
  rescue_from StandardError, with: :handle_500 
  
  # 2. This overrides the one above if the error is specifically a Timeout
  rescue_from Net::ReadTimeout, with: :handle_timeout 
end
```

### 3. Don't Swallow StandardError Silently
If you rescue `StandardError` globally to render a custom 500 API response, make absolutely sure you report the error to an error tracking service (like Sentry, Honeybadger, or Datadog) before rendering. If you rescue it and don't report it, your app will fail silently, and you will have zero visibility into production bugs.

## 4. Interview Preparation

### Q: What is the difference between `User.find(id)` and `User.find_by(id: id)` regarding exception handling?
**A:** `User.find(id)` raises an `ActiveRecord::RecordNotFound` exception if the record does not exist. This is useful when you absolutely expect the record to be there (e.g., showing a specific profile based on a URL parameter) and want Rails to automatically return a 404. `User.find_by` returns `nil` if the record is missing. It does not raise an exception. This is useful when checking for existence is part of the standard logic flow.

### Q: Why shouldn't you rescue `Exception` in Ruby?
**A:** In Ruby, `Exception` is the root of the exception hierarchy. It includes system-level errors like `NoMemoryError`, `SyntaxError`, and `SignalException` (like when you press Ctrl+C to stop the server). If you `rescue Exception`, you might accidentally prevent the application server from shutting down gracefully or swallow fatal syntax errors. You should always rescue `StandardError` (which is the default if you just write `rescue`), as it encompasses all application-level errors.
