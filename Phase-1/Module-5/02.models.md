# Mastering Models

## 1. Overview
*   **What it is:** In the MVC (Model-View-Controller) architecture, the Model represents the data and the business logic of the application. In Rails, models are typically classes that inherit from `ApplicationRecord`.
*   **Why it exists:** To encapsulate data validation, associations, interactions with the database, and domain-specific logic in a single, coherent place.
*   **When to use it:** Whenever you need to represent a core business entity (like a User, Order, or Product) and persist it to a database, or encapsulate complex business rules.
*   **Common Misconceptions:**
    *   *"Models must always map to a database table."* (False: Models can be Plain Old Ruby Objects (POROs) or include `ActiveModel::Model` for validation/conversion without database persistence).

## 2. Core Concepts

### ApplicationRecord vs ActiveRecord::Base
`ApplicationRecord` is an abstract class introduced in Rails 5 that sits between your models and `ActiveRecord::Base`. It allows you to add application-wide model methods without monkey-patching `ActiveRecord::Base`.
```ruby
class ApplicationRecord < ActiveRecord::Base
  self.abstract_class = true
  # Add globally available methods here
end

class User < ApplicationRecord
end
```

### Migrations and Schema Management
Migrations are a DSL for managing database schema changes over time. `schema.rb` represents the current state of the database using Ruby DSL, while `structure.sql` uses raw database SQL (useful for DB-specific features like triggers or views).

### Attributes and Custom Accessors
ActiveRecord dynamically defines attribute accessors based on database columns. You can also define custom accessors or override existing ones, but be careful to use `read_attribute` and `write_attribute` (or `self[:attr]`) to avoid infinite recursion.
```ruby
class User < ApplicationRecord
  def name=(val)
    write_attribute(:name, val.strip.downcase)
  end
end
```

### Abstract Classes and Multi-Database
Abstract classes are used to share logic or establish different database connections without creating a corresponding table for the abstract class itself.
```ruby
class AnalyticsRecord < ApplicationRecord
  self.abstract_class = true
  connects_to database: { writing: :analytics, reading: :analytics_replica }
end
```

## 3. Best Practices for Lead Engineers

### 1. Avoid Fat Models
The "Fat Model, Skinny Controller" mantra often leads to massive, 1000+ line model files. Lead engineers refactor these into specialized objects: Service Objects for complex business workflows, Query Objects for complex database queries, and Concerns for shared behavioral traits.

### 2. Strictly Manage schema.rb vs structure.sql
If your application relies on database-specific constraints, triggers, or custom data types (like Postgres arrays or Ltree), switch from `schema.rb` to `structure.sql` to ensure these elements are properly captured and loaded in test environments.

### 3. Use Plain Old Ruby Objects (POROs)
Not everything needs to inherit from `ApplicationRecord`. If an entity doesn't need persistence but participates in the domain logic, make it a PORO. Include `ActiveModel::Model` if you need validations and form builder support.

## 4. Interview Preparation

### Q: What is the difference between ApplicationRecord and ActiveRecord::Base?
**A:** `ActiveRecord::Base` is the core Rails class that provides ORM functionality. `ApplicationRecord` is an abstract class generated by Rails (in `app/models/application_record.rb`) that inherits from `ActiveRecord::Base`. All your app's models inherit from `ApplicationRecord`. This provides a convenient place to define methods that should be available to all models in your app, without modifying Rails' core classes.

### Q: When would you use structure.sql over schema.rb?
**A:** `schema.rb` is database-agnostic and uses Rails' Ruby DSL. However, it cannot represent database-specific features like PostgreSQL views, triggers, check constraints (prior to Rails 6.1), or specialized extensions. You use `structure.sql` when you need your schema dump to accurately reflect these database-specific structures.

### Q: How do you handle "Fat Models"?
**A:** I break down the model's responsibilities. If the logic is a complex business process involving multiple models, I extract it into a Service Object. If it's a complex query, I use a Query Object. If it's shared behavior across multiple models (like tagging or archiving), I extract it into an `ActiveSupport::Concern`. View-specific formatting should go into Presenters or Decorators.

### Q: How do you setup a multi-database connection in a Rails Model?
**A:** You configure the databases in `database.yml`. Then, you create an abstract class that specifies the connection using `connects_to`, providing the role (e.g., `writing`, `reading`) and the database configuration name. Models inheriting from this abstract class will route their queries to the specified databases.
