# Mastering CRUD Operations

## 1. Overview
*   **What it is:** Create, Read, Update, Delete (CRUD) are the four basic functions of persistent storage. Active Record provides a rich API for performing these operations.
*   **Why it exists:** To provide a standard, readable, and safe way to manipulate database records without writing boilerplate SQL inserts, selects, updates, and deletes.
*   **When to use it:** Throughout your application lifecycle whenever data needs to be instantiated, retrieved, modified, or destroyed.
*   **Common Misconceptions:**
    *   *"`delete` and `destroy` are interchangeable."* (False: `destroy` instantiates objects and runs callbacks; `delete` fires a raw SQL delete statement, skipping callbacks).

---

## 2. Core Concepts

### Create Operations
*   `new`: Instantiates an object in memory without saving it.
*   `create`: Instantiates and attempts to save. Returns the object (whether saved or not).
*   `create!`: Instantiates and attempts to save. Raises `ActiveRecord::RecordInvalid` if validations fail.
```ruby
user = User.new(name: "Bob")
user.save # returns true/false

User.create!(name: "Alice") # Raises exception if invalid
```

### Read Operations
Active Record provides numerous ways to fetch data.
*   `find(id)`: Expects an ID. Raises `ActiveRecord::RecordNotFound` if missing.
*   `find_by(attr: value)`: Returns the first matching record or `nil`.
*   `where(...)`: Returns an `ActiveRecord::Relation` (a collection), not a single object.
*   `find_each`: Fetches records in batches (default 1000) and yields them one by one. Crucial for memory management on large tables.

### Update Operations
*   `update(attr: val)`: Updates attributes and saves. Runs validations and callbacks.
*   `update_column(attr, val)`: Executes a direct SQL UPDATE for a single column. **Skips validations, callbacks, and `updated_at` modification.**
*   `update_all(attr: val)`: Updates multiple records with a single SQL query. Skips callbacks and validations.
```ruby
# Runs callbacks/validations
user.update(status: 'active') 

# Direct SQL, fast, skips logic
User.where(status: 'pending').update_all(status: 'active') 
```

### Delete Operations
*   `destroy`: Removes the record and triggers `before_destroy` and `after_destroy` callbacks. Slower.
*   `delete`: Executes a direct SQL DELETE statement. Fast, but leaves orphaned associated records if you rely on callbacks for cleanup.

## 3. Best Practices for Lead Engineers

### 1. Know When to Use Bang (!) Methods
Use bang methods (`create!`, `save!`, `update!`) when a failure to persist is an exceptional state that should halt execution (often within a transaction). Use non-bang methods when you expect failures and plan to handle them gracefully (e.g., re-rendering a form with validation errors).

### 2. Optimize Bulk Operations
When dealing with thousands of records, `User.all.each(&:destroy)` is catastrophic for memory and performance. Use `User.delete_all` or `destroy_all` depending on whether callbacks are strictly necessary. For bulk inserts, use `insert_all` or `upsert_all` (Rails 6+).

### 3. count vs length vs size
Understand the difference: `count` always executes a SQL `COUNT()` query. `length` always loads the entire collection into memory and counts the array. `size` is smart: it uses `length` if the collection is already loaded, otherwise it executes a SQL `COUNT()`. Always prefer `size`.

## 4. Interview Preparation

### Q: What is the difference between `destroy` and `delete`?
**A:** `destroy` instantiates the Active Record object and runs all associated callbacks (like destroying dependent associations). `delete` translates directly to a SQL `DELETE` statement, completely bypassing validations, callbacks, and any Ruby-level logic.

### Q: What is the difference between `save` and `save!`?
**A:** `save` will attempt to persist the object and return `true` on success or `false` on failure (usually due to validations). `save!` will persist the object or raise an `ActiveRecord::RecordInvalid` exception if it fails.

### Q: When would you use `update_column` instead of `update`?
**A:** You use `update_column` when you need to make a quick database update and explicitly want to bypass model validations, callbacks, and the automatic updating of the `updated_at` timestamp. It is faster because it fires a direct SQL update.

### Q: When processing 1 million records, why must you use `find_each`?
**A:** If you use `User.all.each`, Rails will attempt to load all 1 million records into memory at once as Active Record objects, which will likely cause an Out Of Memory (OOM) crash. `find_each` loads records in manageable batches (default 1000), yields them to the block, and then garbage collects them before loading the next batch.
