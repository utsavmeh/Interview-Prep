# Mastering Validations

## 1. Overview
*   **What it is:** Validations are rules defined in Active Record models that ensure only valid data is saved to the database.
*   **Why it exists:** To maintain data integrity, enforce business rules, and provide meaningful error messages to users when inputs are incorrect.
*   **When to use it:** Before any data is persisted to the database. They run automatically on methods like `save`, `create`, and `update`.
*   **Common Misconceptions:**
    *   *"Active Record uniqueness validation guarantees unique data in the database."* (False: It is subject to race conditions. You must also have a unique index at the database level).

---

## 2. Core Concepts

### When Validations Run
Validations run *before* the database operation is executed. 
*   Triggers validations: `create`, `create!`, `save`, `save!`, `update`, `update!`.
*   Skips validations: `decrement`, `increment`, `toggle`, `update_all`, `update_column`, `update_columns`, `insert_all`.

### Built-in Validators
Rails provides numerous helpers:
*   `presence`: Ensures the attribute is not empty (`nil` or blank string).
*   `uniqueness`: Ensures no other record has the same value.
*   `format`: Uses a regular expression to validate the format (e.g., email).
*   `inclusion` / `exclusion`: Validates that a value is or is not within a specified set.
*   `numericality`: Ensures only numbers, with options for `greater_than`, `only_integer`, etc.

### Conditional Validations and Contexts
Validations can be scoped to run only when certain conditions are met, or only during specific actions.
```ruby
# Runs only if the user is an admin
validates :admin_token, presence: true, if: :admin?

# Runs only when calling user.save(context: :publish)
validates :title, presence: true, on: :publish 
```

### The Errors Object
When validations fail, Rails populates the `errors` object on the model. You can check `model.valid?` (which runs validations and returns true/false) and inspect `model.errors.full_messages`.

## 3. Best Practices for Lead Engineers

### 1. Database Constraints are Mandatory, Validations are UI
Active Record validations provide a good user experience by returning helpful error messages. However, they are NOT a substitute for database integrity. Always pair `validates_uniqueness_of` with a unique index in the database. Pair `presence: true` with a `NOT NULL` constraint in the database schema.

### 2. Extract Complex Validations to Custom Validators
If a validation requires complex logic spanning multiple attributes or external services, do not clutter the model. Extract it into a custom validator class (`ActiveModel::Validator` or `ActiveModel::EachValidator`).

### 3. Handle the Uniqueness Race Condition
If two requests try to create a user with the same email at the exact same millisecond, both will pass the `validates_uniqueness_of` check in Ruby, and both will attempt to insert. Without a DB-level unique index, you will get duplicate data. With a DB index, one will raise an `ActiveRecord::RecordNotUnique` exception, which you must catch and handle gracefully.

## 4. Interview Preparation

### Q: Why is `validates :email, uniqueness: true` not enough to guarantee unique emails?
**A:** Because of concurrent web requests (race conditions). Two processes can check the database simultaneously, both see that the email doesn't exist, and both proceed to `INSERT` the record. To guarantee uniqueness, you absolutely must add a unique constraint/index at the database level.

### Q: How do you handle validation errors when building an API?
**A:** Instead of crashing, an API should gracefully return a `422 Unprocessable Entity` status code. I would rescue `ActiveRecord::RecordInvalid` (or check `if model.save`) and render the `model.errors.messages` as a JSON payload, so the frontend can display specific errors next to the corresponding fields.

### Q: What is the difference between database constraints and model validations?
**A:** Model validations run in Ruby memory *before* the SQL query is constructed; they are easy to write, great for business logic, and generate user-friendly error messages. Database constraints (NOT NULL, foreign keys, unique indices) are enforced by the database engine itself; they are the ultimate safeguard against bad data, regardless of whether the data comes from Rails, a raw SQL query, or another application.

### Q: How do you write a custom validator?
**A:** For validating a single attribute, I create a class inheriting from `ActiveModel::EachValidator` and implement the `validate_each(record, attribute, value)` method. If the value is invalid, I add an error to `record.errors.add(attribute, "message")`. Then I use it in the model like: `validates :field, my_custom: true`.
