# Mastering Callbacks

## 1. Overview
*   **What it is:** Methods that get called at certain moments of an object's lifecycle. With callbacks it is possible to write code that will run whenever an Active Record object is created, saved, updated, deleted, validated, or loaded from the database.
*   **Why it exists:** To allow hooking into the ActiveRecord lifecycle to execute logic related to data consistency, data transformation, or dependent state changes.
*   **When to use it:** Use sparingly for internal model state management (e.g., stripping whitespace, setting a default internal token) where the logic is inextricably linked to the valid state of the record itself.
*   **Common Misconceptions:**
    *   *"Callbacks are great for triggering emails or background jobs."* (False: This couples domain boundaries, makes testing hard, and risks phantom writes if transactions roll back. Use service objects or `after_commit`).

## 2. Core Concepts

### The Callback Lifecycle
The order of callbacks is strict. For a typical `save` operation on a new record: `before_validation`, `after_validation`, `before_save`, `before_create`, `after_create`, `after_save`, `after_commit`.
```ruby
class User < ApplicationRecord
  before_validation :normalize_email, on: :create
  
  private
  
  def normalize_email
    self.email = email.downcase.strip if email.present?
  end
end
```

### Halting Execution (`throw :abort`)
If a `before_*` callback throws `:abort`, the entire callback chain is halted, and the database transaction is rolled back. Returning `false` no longer halts the chain (as of Rails 5).
```ruby
class Order < ApplicationRecord
  before_destroy :prevent_if_shipped
  
  private
  
  def prevent_if_shipped
    if status == 'shipped'
      errors.add(:base, "Cannot delete a shipped order")
      throw :abort
    end
  end
end
```

### `after_save` vs `after_commit`
`after_save` runs *inside* the database transaction. If the transaction rolls back, side effects triggered in `after_save` (like enqueuing a Redis job) cannot be rolled back, leading to inconsistencies. `after_commit` runs *after* the transaction has successfully been committed to the database.
```ruby
class Purchase < ApplicationRecord
  # DANGEROUS: Job might execute before DB transaction commits or if it rolls back
  # after_save :trigger_fulfillment
  
  # SAFE: Job only enqueued if DB commit succeeds
  after_commit :trigger_fulfillment, on: :create
end
```

### Callback Classes
For complex callback logic, encapsulate it into a separate class to adhere to the Single Responsibility Principle.
```ruby
class EmailNormalizer
  def before_validation(record)
    record.email = record.email.downcase.strip if record.email.present?
  end
end

class User < ApplicationRecord
  before_validation EmailNormalizer.new
end
```

## 3. Best Practices for Lead Engineers

### 1. Avoid Cross-Domain Side Effects
Never use callbacks for external API calls, sending emails, or touching unrelated models. Use Service Objects, Interactors, or the Publish-Subscribe (Pub/Sub) pattern (e.g., using `ActiveSupport::Notifications` or a message broker) to handle cross-boundary concerns. This keeps models cohesive and tests fast.

### 2. Always Prefer `after_commit` Over `after_save` for Async Work
Whenever you enqueue a background job (Sidekiq, Resque), always use `after_commit`. If you use `after_save`, the job might be picked up by a worker before the database transaction is fully committed, leading to a `RecordNotFound` error in the worker.

### 3. Use Conditional Callbacks to Prevent Unnecessary Execution
Use `if:` or `unless:` to limit when callbacks run. This prevents expensive or unnecessary operations when relevant attributes haven't changed. Use ActiveModel::Dirty methods like `saved_change_to_email?`.
```ruby
after_commit :sync_to_crm, if: :saved_change_to_email?
```

### 4. Skip Callbacks Wisely in Bulk Operations
Methods like `update_all`, `insert_all`, `delete_all` bypass callbacks (and validations) for performance. If your application relies heavily on callbacks for data integrity, bypassing them can lead to corrupted state. Be fully aware of which ActiveRecord methods trigger callbacks and which don't.

## 4. Interview Preparation

### Q: What is the difference between `after_save` and `after_commit`?
**A:** `after_save` executes *inside* the database transaction, meaning if the transaction subsequently rolls back, any external side effects (like API calls or background jobs) triggered in `after_save` will still have occurred but shouldn't have. `after_commit` executes only *after* the transaction has successfully committed to the database, making it the safe place for external side effects.

### Q: How do you halt a callback chain in Rails?
**A:** You use `throw :abort` inside a `before_*` callback. In older versions of Rails (prior to Rails 5), returning `false` would halt the chain, but this was error-prone if a method coincidentally evaluated to `false`. Now, only an explicit `throw :abort` halts execution and rolls back the transaction.

### Q: Why are callbacks often considered an anti-pattern for large codebases?
**A:** Callbacks implicitly couple lifecycle events to side effects, violating the Single Responsibility Principle. They make testing difficult because setting up a simple test object triggers a cascade of unintended behavior (like sending emails). They hide control flow, making it hard to trace what happens when a record is saved.

### Q: How do you safely test logic that is meant to run after a model is saved without using callbacks?
**A:** Move the logic into a Service Object (e.g., `CreateUserAndNotify`). The controller calls the service object, which explicitly saves the model and then calls the notification logic. This makes the flow explicit, easily testable in isolation, and keeps the model focused solely on data persistence and internal state.
