# Mastering Scopes

## 1. Overview
*   **What it is:** Scopes are custom queries defined in an Active Record model that return an `ActiveRecord::Relation` object, allowing them to be chained together.
*   **Why it exists:** To encapsulate complex query logic into descriptive, reusable, and chainable methods directly on the model.
*   **When to use it:** Use for common `where`, `joins`, or `order` queries that are used in multiple places across the application (e.g., `published`, `active`, `recent`).
*   **Common Misconceptions:**
    *   *"Scopes are fundamentally different from class methods."* (False: Internally, Rails converts scopes into class methods. They are practically identical in behavior).

---

## 2. Core Concepts

### Defining and Chaining Scopes
Scopes must always be defined using a `lambda` (or `->`). This ensures the scope is evaluated every time it is called, not just once when the class is loaded. Because they return an `ActiveRecord::Relation`, they can be chained.
```ruby
class Article < ApplicationRecord
  scope :published, -> { where(published: true) }
  scope :recent, -> { order(created_at: :desc) }
  scope :by_author, ->(author_id) { where(author_id: author_id) }
  
  # Usage: Article.published.recent.by_author(1)
end
```

### The Lambda Requirement for Time
If you don't use a lambda, time-based queries evaluate at boot time (when the server starts).
```ruby
class Post < ApplicationRecord
  # WRONG: 1.week.ago is evaluated when the server starts.
  # scope :recent, where('created_at > ?', 1.week.ago)
  
  # RIGHT: Evaluated dynamically on every invocation.
  scope :recent, -> { where('created_at > ?', 1.week.ago) }
end
```

### `default_scope` and `unscoped`
`default_scope` applies a scope to *all* queries on the model by default. It can be removed temporarily using `.unscoped`.
```ruby
class Comment < ApplicationRecord
  default_scope { where(deleted: false) }
end

# To get deleted comments, you must explicitly remove the default scope
Comment.unscoped.where(deleted: true)
```

### Scopes vs Class Methods
Scopes implicitly return an `ActiveRecord::Relation` even if the condition is false (it returns `all`). Class methods might return `nil` if you aren't careful, breaking chainability.
```ruby
class User < ApplicationRecord
  # Scope guarantees a Relation is returned
  scope :admins, -> { where(admin: true) if has_admin_table? }
  
  # Class method might return nil, breaking chaining like User.admins.active
  def self.admins
    where(admin: true) if has_admin_table?
  end
end
```

## 3. Best Practices for Lead Engineers

### 1. Avoid `default_scope` at All Costs
`default_scope` is notorious for introducing hard-to-debug issues. It bleeds into associations, breaks initialization logic (e.g., `Comment.new` might auto-set `deleted: false`), and requires cumbersome `.unscoped` calls that also strip out associations' conditions. Use explicit scopes (e.g., `Post.active`) instead.

### 2. Prefer Class Methods for Complex Queries
While scopes are great for simple `where` or `order` clauses, class methods are preferable for complex queries involving conditional logic, multiple joins, or heavy Ruby processing. Class methods are easier to format across multiple lines and test. Just ensure they always return an `ActiveRecord::Relation` or `self.all` to maintain chainability.

### 3. Keep Scopes Composable and Single-Purpose
A scope should do one thing (e.g., `published`, `ordered_by_title`). Don't create monolithic scopes like `published_and_ordered_and_recent`. Instead, compose them at the call site: `Article.published.ordered_by_title.recent`. This maximizes reusability and makes the intent clear.

## 4. Interview Preparation

### Q: What is the difference between a scope and a class method?
**A:** Under the hood, Rails converts scopes to class methods. The primary behavioral difference is that a scope is guaranteed to return an `ActiveRecord::Relation`, making it safely chainable. If a scope's lambda returns `nil` or `false`, Rails automatically returns `all`. A class method must explicitly return a relation or `all` to be safely chainable.

### Q: Why is `default_scope` considered dangerous?
**A:** `default_scope` affects *every* query on the model, including queries through associations and even object instantiation (`Model.new`). It requires using `.unscoped` to bypass, which strips *all* conditions, not just the default scope, potentially exposing unauthorized data. It creates hidden behavior that violates the principle of least astonishment.

### Q: Why do scopes require a `lambda` (or `->`)?
**A:** Scopes are evaluated when the class is loaded into memory (boot time), not when the scope is called. If you pass an expression directly (especially time-based like `Time.current`), it freezes at boot time. A lambda ensures the block is evaluated dynamically every time the scope is invoked.

### Q: Can you chain scopes? How does it work?
**A:** Yes, scopes are chainable because they always return an `ActiveRecord::Relation` object. ActiveRecord uses lazy loading; it accumulates the query conditions from the chained scopes and only executes a single SQL query against the database when the data is actually needed (e.g., by calling `.each`, `.to_a`, or rendering).
