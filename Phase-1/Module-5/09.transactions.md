# Mastering Transactions

## 1. Overview
*   **What it is:** A transaction is a protective block around SQL statements to ensure they either all succeed or all fail together.
*   **Why it exists:** To maintain database integrity by enforcing ACID properties (Atomicity, Consistency, Isolation, Durability), preventing partial data updates if an error occurs midway through a process.
*   **When to use it:** Whenever you are making changes to multiple records or multiple tables that logically depend on each other (e.g., transferring funds, creating a user and their initial profile).
*   **Common Misconceptions:**
    *   *"Using `rescue` inside a transaction is safe."* (False: If you rescue the exception and don't re-raise it or raise `ActiveRecord::Rollback`, the transaction will silently commit the partial changes).

---

## 2. Core Concepts

### `ActiveRecord::Base.transaction`
Wraps a block of database operations. If an exception is raised within the block, the database rolls back all changes.
```ruby
ActiveRecord::Base.transaction do
  account_from.withdraw(100)
  account_to.deposit(100)
  # If deposit fails and raises an error, the withdrawal is rolled back.
end
```

### Triggering Rollbacks (`ActiveRecord::Rollback`)
Transactions only roll back if an exception is raised. Using methods that return `false` (like `.save` instead of `.save!`) will *not* trigger a rollback. You can raise `ActiveRecord::Rollback` to cleanly abort without crashing the application.
```ruby
ActiveRecord::Base.transaction do
  user = User.create!(user_params)
  unless profile.save
    raise ActiveRecord::Rollback # Silently rolls back the transaction
  end
end
```

### Nested Transactions and Savepoints
By default, nested `transaction` blocks in Rails don't map to true nested database transactions. An exception in an inner block will roll back the outer block. To use real nested transactions (savepoints), you must pass `requires_new: true`.
```ruby
User.transaction do
  User.create(name: 'Alice')
  
  User.transaction(requires_new: true) do # Creates a database SAVEPOINT
    User.create(name: 'Bob')
    raise ActiveRecord::Rollback # Rolls back Bob, but Alice is still saved
  end
end
```

### Transaction Callbacks
`after_commit` and `after_rollback` are callbacks tied to the transaction lifecycle, ensuring side-effects (like enqueuing jobs) only happen if the data is permanently saved.

## 3. Best Practices for Lead Engineers

### 1. Keep Transactions Fast and Short
Transactions hold database locks. Doing HTTP requests, complex Ruby calculations, or writing to external files inside a transaction can block other database queries, leading to timeouts and degraded performance. Only put database write operations inside the transaction block.

### 2. Use `save!` and `update!` Inside Transactions
A common mistake is using `save` (which returns a boolean) inside a transaction. If `save` fails, it doesn't raise an exception, so the transaction *commits* whatever succeeded previously. Always use bang methods (`save!`, `update!`, `create!`) so failures raise exceptions and trigger rollbacks.

### 3. Handle Deadlocks Gracefully
In high-concurrency systems, two transactions might lock resources each other needs, causing a deadlock. PostgreSQL and MySQL will kill one transaction. You should rescue `ActiveRecord::Deadlocked` and implement a retry mechanism for critical operations.

## 4. Interview Preparation

### Q: What are the ACID properties in database transactions?
**A:** 
*   **Atomicity:** All operations in the transaction succeed, or none do (all-or-nothing).
*   **Consistency:** The database moves from one valid state to another, enforcing constraints.
*   **Isolation:** Concurrent transactions don't interfere with each other (controlled via isolation levels).
*   **Durability:** Once committed, the changes are permanent, even in the event of a crash.

### Q: How do nested transactions work in Rails?
**A:** By default, Rails ignores nested `transaction` calls; it just groups them into the single parent transaction. An exception anywhere rolls back everything. To achieve true partial rollbacks, you must use `requires_new: true` on the inner transaction, which utilizes database `SAVEPOINT`s.

### Q: What happens if you catch an exception inside a transaction?
**A:** If you use a `rescue` block inside a transaction and swallow the exception, the transaction block finishes successfully and *commits* the changes. To rescue an error but still roll back, you must raise `ActiveRecord::Rollback` within the rescue block.

### Q: Why should you avoid 3rd-party API calls inside a transaction block?
**A:** API calls are slow and prone to timeouts. While the API call is waiting, the database transaction is held open, retaining row or table locks. This drastically reduces database concurrency and can quickly exhaust the database connection pool, taking down the application.
