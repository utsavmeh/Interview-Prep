# Mastering Optimistic Locking

## 1. Overview
*   **What it is:** A concurrency control strategy that allows multiple users to read the same record, but prevents them from overwriting each other's changes by checking if the record was modified before saving.
*   **Why it exists:** To solve the "Lost Update Problem" where User A and User B load a record, User A saves, and User B saves immediately after, silently destroying User A's changes.
*   **When to use it:** When data collisions are possible but infrequent, and you want to maintain high read concurrency without holding database locks (e.g., wiki page editing, basic profile updates).
*   **Common Misconceptions:**
    *   *"Optimistic locking uses database locks."* (False: It doesn't lock anything at the database level. It uses application-level version checking via a specific column).

---

## 2. Core Concepts

### The `lock_version` Column
Rails implements optimistic locking simply by adding an integer column named `lock_version` with a default of `0` to a table. When you include this column, ActiveRecord automatically enables optimistic locking.
```ruby
# Migration
add_column :products, :lock_version, :integer, default: 0, null: false
```

### How the Version Check Works
When a record is loaded, Rails remembers its `lock_version`. When saving, it issues an `UPDATE` query that explicitly checks if the version is still the same.
```sql
-- Rails issues this internally on save:
UPDATE products SET name = 'New Name', lock_version = 2
WHERE id = 1 AND lock_version = 1;
```
If the query updates `0` rows (meaning someone else incremented the version to 2), Rails raises an `ActiveRecord::StaleObjectError`.

### Handling `StaleObjectError`
You must explicitly handle collisions in your application code. You can rescue the error and either retry the operation, merge changes, or notify the user.
```ruby
begin
  product = Product.find(1)
  # ... user spends time editing ...
  product.update!(name: 'New Product Name')
rescue ActiveRecord::StaleObjectError
  # Reload the record and handle the conflict
  product.reload
  errors.add(:base, "This record was changed while you were editing.")
end
```

### Form Integration
In web applications, the `lock_version` must be passed back and forth through hidden form fields so the server knows which version the user was looking at when they hit "submit".
```erb
<%= form_with model: @product do |form| %>
  <%= form.hidden_field :lock_version %>
  <!-- other fields -->
<% end %>
```

## 3. Best Practices for Lead Engineers

### 1. Use for Low-Contention, High-Latency Edits
Optimistic locking shines for user-driven UI edits (like CMS articles or settings pages) where users spend minutes editing a form. Holding a pessimistic database lock for minutes is impossible on the web, making optimistic locking the only viable concurrency control for long-lived edits.

### 2. Implement Automated Retries for Background Jobs
If a background job hits a `StaleObjectError`, it is usually safe to reload the record and retry the operation automatically, as background jobs usually perform deterministic state changes rather than manual user edits.
```ruby
def perform(product_id)
  retry_count = 0
  begin
    product = Product.find(product_id)
    product.update!(inventory_count: product.inventory_count - 1)
  rescue ActiveRecord::StaleObjectError
    retry_count += 1
    retry if retry_count < 3
    raise
  end
end
```

### 3. Graceful UI Recovery
When a `StaleObjectError` occurs in a controller, do not just render a 500 error. Rescue the exception, reload the `@record`, merge the user's attempted params so they don't lose their typing, and re-render the form with a clear flash message explaining that someone else modified the record.

## 4. Interview Preparation

### Q: How does optimistic locking differ from pessimistic locking?
**A:** Optimistic locking doesn't lock rows in the database; it allows concurrent reads and checks for a version mismatch on write, failing if the data changed. Pessimistic locking explicitly locks the row in the database via `SELECT FOR UPDATE`, forcing other processes to wait until the transaction completes.

### Q: What is the "Lost Update Problem" and how does `lock_version` solve it?
**A:** The lost update occurs when two processes read a record (e.g., balance = 100). Both calculate a new value (P1: 100-10=90, P2: 100-50=50). P1 saves 90, then P2 saves 50, wiping out P1's transaction. `lock_version` solves this by adding `WHERE lock_version = X` to the update query. P2's update will fail because P1 already incremented the version to `X+1`.

### Q: How do you handle an `ActiveRecord::StaleObjectError` in a web application?
**A:** You rescue the exception in the controller. Since the user submitted form data, you should retain their input, apply it to a fresh copy of the record (via `.reload`), and re-render the form, displaying an error message that the record was modified by someone else so they can review the merged state before saving again.

### Q: Can you use a column name other than `lock_version`?
**A:** Yes. You can configure a different column name in your model by setting `self.locking_column = :custom_version_column`.
