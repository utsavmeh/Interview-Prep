# Mastering Pessimistic Locking

## 1. Overview
*   **What it is:** A concurrency control strategy that actively locks database rows during a transaction, preventing other processes from reading (sometimes) or writing to those rows until the lock is released.
*   **Why it exists:** To guarantee data integrity in high-contention environments where concurrent transactions are likely to clash over the same exact rows, particularly in financial or inventory systems.
*   **When to use it:** When processing payments, reserving inventory, or any scenario where the cost of a transaction failing and rolling back is higher than the cost of forcing processes to wait in line.
*   **Common Misconceptions:**
    *   *"Pessimistic locking locks the whole table."* (False: When used correctly with `find`, it leverages row-level locks via `SELECT ... FOR UPDATE`).

---

## 2. Core Concepts

### `SELECT FOR UPDATE`
The foundation of pessimistic locking is the SQL `SELECT FOR UPDATE` clause. It tells the database to lock the rows returned by the query. No other transaction can modify (and sometimes read, depending on isolation level) these rows until the current transaction commits or rolls back.

### The `lock!` Method
You can acquire a lock on an object you already have in memory using `lock!`. This must be done inside a transaction block.
```ruby
ActiveRecord::Base.transaction do
  account = Account.find(1)
  account.lock! # Issues: SELECT * FROM accounts WHERE id = 1 FOR UPDATE
  account.balance -= 100
  account.save!
end
```

### The `with_lock` Method
A cleaner abstraction provided by Rails. It automatically starts a transaction, acquires the lock on the record, yields to the block, and commits the transaction.
```ruby
account = Account.find(1)
# Begins transaction, locks record, executes block, commits.
account.with_lock do
  account.balance -= 100
  account.save!
end
```

### Deadlocks
When Transaction A locks Row 1 and needs Row 2, while Transaction B locks Row 2 and needs Row 1. They wait indefinitely. The database engine eventually detects this and kills one transaction (raising an `ActiveRecord::Deadlocked` exception).

## 3. Best Practices for Lead Engineers

### 1. Always Order Locks Consistently to Prevent Deadlocks
The most effective way to prevent deadlocks when locking multiple records is to always acquire the locks in the exact same order (e.g., by primary key).
```ruby
# SAFE: Always lock lowest ID first
accounts = [account_a, account_b].sort_by(&:id)
Account.transaction do
  accounts.each(&:lock!)
  # perform transfers
end
```

### 2. Keep the Lock Duration Extremely Short
Row locks bottleneck your application. Do not perform external HTTP requests, heavy rendering, or complex Ruby loops inside a `with_lock` block. Load necessary data *before* the lock, acquire the lock, perform the simple math/state change, and release it immediately.

### 3. Consider Advisory Locks for Non-Row Operations
If you need to prevent concurrent execution of a process that doesn't neatly map to a single database row (e.g., generating a nightly report), use Database Advisory Locks (via gems like `with_advisory_lock`). These are application-defined application-level locks managed by the database.

## 4. Interview Preparation

### Q: What SQL command does Rails use for pessimistic locking, and what does it do?
**A:** Rails uses `SELECT ... FOR UPDATE`. It acquires an exclusive lock on the queried rows. Other transactions that attempt to `SELECT FOR UPDATE` or `UPDATE` those same rows will pause and wait until the first transaction finishes (commits or rolls back).

### Q: Compare `lock!` and `with_lock`.
**A:** `lock!` requires you to manually wrap the code in an `ActiveRecord::Base.transaction` block. If you call `lock!` outside a transaction, it is virtually useless as the lock releases immediately. `with_lock` is a convenience method that combines starting the transaction, locking the record, and yielding the block in one concise method call.

### Q: How do you prevent deadlocks when pessimistically locking multiple rows?
**A:** Deadlocks occur when transactions lock resources in different orders. The primary prevention strategy is to enforce a consistent locking order across the entire application, usually by sorting the records by their primary key (ID) before acquiring the locks.

### Q: When would you choose pessimistic locking over optimistic locking?
**A:** Choose pessimistic locking for high-contention, high-stakes operations where conflicts are expected, such as deducting from a limited inventory during a flash sale or processing financial ledger entries. Optimistic locking relies on retries, which fail under heavy concurrent load. Pessimistic locking forces sequential processing via the database queue.
