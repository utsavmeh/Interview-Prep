# Mastering Single Table Inheritance (STI)

## 1. Overview
*   **What it is:** A database design pattern where multiple subclasses (models) inherit from a single base class, and all their data is stored in one single database table.
*   **Why it exists:** To allow polymorphism and shared behavior among related models without the performance hit of complex SQL `JOIN`s required by multiple tables.
*   **When to use it:** When you have models that share identical or nearly identical database columns, but have different Ruby behavior or validations (e.g., `Vehicle` -> `Car`, `Truck`, `Motorcycle`).
*   **Common Misconceptions:**
    *   *"STI is good for any polymorphic relationship."* (False: If the subclasses require significantly different columns, STI leads to sparse tables full of NULLs. Use polymorphic associations or delegated types instead).

---

## 2. Core Concepts

### The `type` Column
Rails relies on a string column specifically named `type` in the base table. When a record is saved, Rails stores the subclass name (e.g., `"Car"`) in this column. When queried, Rails uses this column to instantiate the correct Ruby object.
```ruby
# Migration for vehicles table
create_table :vehicles do |t|
  t.string :type, null: false # Critical for STI
  t.string :color
  t.integer :payload_capacity # Only relevant for Trucks
end
```

### Implementing the Models
The base class inherits from `ApplicationRecord`. The subclasses inherit from the base class.
```ruby
class Vehicle < ApplicationRecord
  # Shared behavior
end

class Car < Vehicle
  validates :color, presence: true
end

class Truck < Vehicle
  validates :payload_capacity, presence: true
end
```

### Automatic Scope and Querying
When you query a subclass, Rails automatically appends a `WHERE type = 'SubclassName'` clause.
```ruby
# Executes: SELECT * FROM vehicles WHERE type = 'Truck'
Truck.all 

# Instantiates a Car object, setting type = 'Car' automatically
Car.create(color: 'Red') 
```

### Overriding the Type Column
If you have a legacy database where `type` is a reserved word or used differently, you can change the STI column name.
```ruby
class Vehicle < ApplicationRecord
  self.inheritance_column = :vehicle_type
end
```

## 3. Best Practices for Lead Engineers

### 1. Watch Out for the "Sparse Table" Problem
The biggest pitfall of STI is table bloat. If `Car` needs 10 specific columns, and `Truck` needs 15 different columns, your `vehicles` table will have 25 columns where half are always `NULL` for any given row. If subclasses diverge in data schema, abandon STI for Delegated Types (introduced in Rails 6.1) or Polymorphic Associations.

### 2. Index the Type Column
If you frequently query the base class to find specific subclasses (or just query subclasses directly), ensure the `type` column is indexed. Often, a composite index like `[type, created_at]` is highly effective.

### 3. Handle Validations Carefully
Since all data lives in one table, database-level constraints (like `NOT NULL`) cannot be used for columns that only belong to a specific subclass. You must rely purely on application-level ActiveRecord validations.

## 4. Interview Preparation

### Q: How does Rails know which object to instantiate when querying an STI table?
**A:** Rails looks at the `type` string column in the database table. If a row has `type = "AdminUser"`, ActiveRecord reads that string, constantizes it, and instantiates an `AdminUser` object instead of the base `User` object.

### Q: What are the primary drawbacks of Single Table Inheritance?
**A:** 
1. **Sparse Columns:** Subclass-specific attributes result in columns that are `NULL` for all other subclasses.
2. **Weak Database Integrity:** You cannot use strict database constraints (like `NOT NULL`) for attributes specific to a subclass.
3. **Large Tables:** The single table can grow massively large, impacting query performance if not indexed correctly.

### Q: When should you use STI vs. Polymorphic Associations?
**A:** Use STI when models share the exact same data schema (columns) but differ in behavior (methods, validations). Use Polymorphic Associations when models have completely different data schemas (e.g., `Image` and `TextPost`) but share a common interface (e.g., they can both be "commentable").

### Q: What is Delegated Types in Rails, and how does it relate to STI?
**A:** Delegated Types (Rails 6.1+) is an alternative to STI. It solves the sparse table problem by storing shared attributes in a central `messages` table, but stores subclass-specific attributes in separate tables (`emails`, `sms_messages`). It uses standard associations and delegation to tie them together, offering the behavior of STI without the messy database structure.
