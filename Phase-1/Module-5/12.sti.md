# Single Table Inheritance (STI) in Rails — A Beginner-Friendly Guide

Single Table Inheritance, usually called **STI**, lets several Rails models share one database table while still having their own behavior.

This sounds complicated, but the idea is simple:

> **One table, one parent model, and several child models.**

We will use vehicles as an example:

- Every vehicle has a color.
- A car has doors.
- A truck has a payload capacity.
- A motorcycle has an engine size.

All of these records can live in one `vehicles` table.

---

## 1. The Basic Idea

Without STI, you might create separate tables:

```text
cars
trucks
motorcycles
```

With STI, you create only one table:

```text
vehicles
```

The table has a special column called `type`. This column tells Rails which Ruby class each row belongs to.

| id | type       | color | doors | payload_capacity |
|----|------------|-------|-------|------------------|
| 1  | Car        | Red   | 4     | NULL             |
| 2  | Truck      | Blue  | NULL  | 1000             |

Rails reads the `type` value and creates the right object:

- `type = "Car"` becomes a `Car` object.
- `type = "Truck"` becomes a `Truck` object.

The `NULL` values are normal in this example. A truck does not need a `doors` value, and a car does not need a `payload_capacity` value.

---

## 2. Creating the Table

Create one table for the parent model. The important part is the `type` column.

```ruby
class CreateVehicles < ActiveRecord::Migration[7.0]
  def change
    create_table :vehicles do |t|
      t.string :type # Rails uses this column for STI
      t.string :color
      t.integer :doors
      t.integer :payload_capacity
      t.integer :engine_size

      t.timestamps
    end

    add_index :vehicles, :type
  end
end
```

### Important: do not use `null: false` automatically

A row created as a plain `Vehicle` has no subclass, so its `type` value can be `NULL`. Also, the `type` column is what Rails uses to decide which subclass to create. Keep this behavior in mind before adding a database constraint.

Run the migration after creating it:

```bash
bin/rails db:migrate
```

---

## 3. Creating the Models

The parent model inherits from `ApplicationRecord`. The child models inherit from the parent model.

```ruby
# app/models/vehicle.rb
class Vehicle < ApplicationRecord
end

# app/models/car.rb
class Car < Vehicle
  validates :color, presence: true
  validates :doors, presence: true
end

# app/models/truck.rb
class Truck < Vehicle
  validates :color, presence: true
  validates :payload_capacity, presence: true
end

# app/models/motorcycle.rb
class Motorcycle < Vehicle
  validates :color, presence: true
  validates :engine_size, presence: true
end
```

Because `Car`, `Truck`, and `Motorcycle` inherit from `Vehicle`, they all get the columns and behavior defined on `Vehicle`.

You can also add shared behavior to the parent:

```ruby
class Vehicle < ApplicationRecord
  def description
    "This is a #{color} vehicle."
  end
end
```

Every child model can now call `description`.

---

## 4. Creating Records

Create a record through the child class:

```ruby
car = Car.create!(color: "Red", doors: 4)
truck = Truck.create!(color: "Blue", payload_capacity: 1000)
```

Rails saves them in the same table:

```text
vehicles

id | type  | color | doors | payload_capacity
---|-------|-------|-------|------------------
1  | Car   | Red   | 4     | NULL
2  | Truck | Blue  | NULL  | 1000
```

You do not need to set `type` yourself. Rails sets it automatically:

```ruby
car.type   # => "Car"
truck.type # => "Truck"
```

The objects have the expected Ruby classes too:

```ruby
car.class   # => Car
truck.class # => Truck
```

---

## 5. Querying Records

When you query a child model, Rails automatically filters by `type`.

```ruby
Car.all
```

This is similar to running:

```sql
SELECT * FROM vehicles WHERE type = 'Car';
```

Other examples:

```ruby
Truck.where(color: "Blue")
Motorcycle.count
Vehicle.all
```

`Vehicle.all` returns every vehicle. Rails looks at the `type` value for each row and creates the correct object for each one.

```ruby
vehicles = Vehicle.all
vehicles.first.class # Could be Car, Truck, or Motorcycle
```

---

## 6. A Simple Way to Remember STI

Think of the `type` column as a label on each row:

```text
Vehicle table

row 1: type = Car
row 2: type = Truck
row 3: type = Motorcycle
```

The table stores the data. The `type` label tells Rails which Ruby class should represent that data.

> **Table = where the data is stored.**
>
> **`type` = which model should be used.**

---

## 7. When Should You Use STI?

STI is a good choice when:

- The models represent the same general kind of thing.
- Most of their columns are shared.
- The models mainly differ in behavior, methods, or a few validations.
- You often want to work with all of them as one group.

For example, STI can work well for:

```text
Payment -> CreditCardPayment, BankTransferPayment
User    -> AdminUser, Customer
Vehicle -> Car, Truck, Motorcycle
```

---

## 8. When Should You Avoid STI?

STI may be a poor choice when every child needs many completely different columns.

For example:

```text
Product -> Book, Car, House
```

A book, a car, and a house probably need very different data. One table would contain many columns that are `NULL` for most rows. This is called a **sparse table**.

A large sparse table can be difficult to understand and maintain. In that situation, consider separate tables, normal associations, or Rails' delegated types instead.

### A useful rule

> Use STI when the classes are mostly the same data with different behavior.
>
> Do not use STI just because the classes sound related.

---

## 9. Common Problems and Good Practices

### Too many unused columns

If each child model needs many unique columns, the table may become full of `NULL` values. Reconsider whether STI is the right design.

### Validations are still important

Database constraints such as `NOT NULL` are difficult to use for subclass-only columns. For example, `doors` cannot be `NOT NULL` for every vehicle if trucks do not use that column. Put subclass-specific rules in the child model:

```ruby
class Car < Vehicle
  validates :doors, presence: true
end
```

### Add an index to `type`

Rails frequently uses `type` when querying subclasses, so an index can help:

```ruby
add_index :vehicles, :type
```

For a very large table, check the queries your application actually runs before adding more complex indexes.

### Be careful when renaming classes

Rails stores the class name in the database. If you rename `Truck` to `DeliveryTruck`, existing rows still contain `"Truck"` unless you migrate those values too.

---

## 10. Changing the STI Column Name

Rails expects the column to be called `type`. If an existing database uses another name, tell Rails which column to use:

```ruby
class Vehicle < ApplicationRecord
  self.inheritance_column = :vehicle_type
end
```

The table must then contain a `vehicle_type` column instead of `type`.

## 11. A Complete Small Example

```ruby
# Migration
create_table :vehicles do |t|
  t.string :type
  t.string :color
  t.integer :doors
  t.integer :payload_capacity
end

# Models
class Vehicle < ApplicationRecord
  def electric?
    false
  end
end

class Car < Vehicle
  validates :doors, presence: true
end

class Truck < Vehicle
  validates :payload_capacity, presence: true
end

# Usage
car = Car.create!(color: "Red", doors: 4)
truck = Truck.create!(color: "Blue", payload_capacity: 1000)

car.type       # => "Car"
truck.type     # => "Truck"
Vehicle.count  # => 2
Car.count      # => 1
Truck.count    # => 1
```

## 12. Interview Questions

### How does Rails know which object to create?

Rails reads the value in the STI column. If the row contains `type = "Car"`, Rails creates a `Car` object. If it contains `type = "Truck"`, Rails creates a `Truck` object.

### What is the main advantage of STI?

Related models share one table and can still have different Ruby behavior. Querying all of them together is also simple because they are stored in one place.

### What is the main disadvantage of STI?

The table can contain many columns that are unused by particular subclasses. This creates `NULL` values and can make the table harder to maintain.

### What is the difference between STI and polymorphic associations?

STI is for several Ruby classes that share one table and a similar data structure.

A polymorphic association is for one model that can belong to different kinds of models, even when those models use different tables. For example, a `Comment` could belong to a `Post` or a `Photo`.

### What should I choose: STI or delegated types?

Use STI when the child models share most of their columns. Consider delegated types when the models share some common information but each type needs its own separate fields and table.

---

## Final Summary

STI means:

1. Create one table for the parent model.
2. Add a `type` column.
3. Make child models inherit from the parent.
4. Create records through the child classes.
5. Rails uses `type` to save and restore the correct class.

The easiest example to remember is:

```ruby
class Vehicle < ApplicationRecord
end

class Car < Vehicle
end
```

Both models use the `vehicles` table. A car row has `type = "Car"`, and Rails uses that value to turn the row back into a `Car` object.
