# Mastering Polymorphic Associations

## 1. Overview
*   **What it is:** A database modeling pattern in Active Record where a model can belong to more than one other model, on a single association, using two columns: `[name]_id` and `[name]_type`.
*   **Why it exists:** To DRY up the database and code. Instead of having separate `article_id`, `photo_id`, and `video_id` columns on a `Comment` model, polymorphism lets you link a comment to any of these via `commentable_id` and `commentable_type`.
*   **When to use it:** When you have cross-cutting entities that apply to many different models—most commonly tags, comments, images, or activity feeds.
*   **Common Misconceptions:**
    *   *"Polymorphic associations maintain database-level integrity."* (False: Because the `_id` column can reference multiple tables, standard database foreign key constraints cannot be applied directly).

---

## 2. Core Concepts

### The _type and _id columns
To set up polymorphism, the child model requires two columns. The `_type` column stores the model class name as a string, and the `_id` stores the primary key.

```ruby
class CreateComments < ActiveRecord::Migration[7.0]
  def change
    create_table :comments do |t|
      t.text :body
      # Creates commentable_id (integer) and commentable_type (string)
      t.references :commentable, polymorphic: true, index: true
      t.timestamps
    end
  end
end
```

### belongs_to and has_many :as
The model containing the polymorphic columns uses `belongs_to ..., polymorphic: true`. The parent models use `has_many ..., as: :...`.

```ruby
class Comment < ApplicationRecord
  belongs_to :commentable, polymorphic: true
end

class Article < ApplicationRecord
  has_many :comments, as: :commentable
end

class Video < ApplicationRecord
  has_many :comments, as: :commentable
end
```

### Querying Polymorphic Associations
Because `commentable` isn't a single table, you can't easily perform a direct SQL `JOIN` across all commentables. You must query based on the specific type.

```ruby
# Finding all comments for Articles
Comment.where(commentable_type: 'Article')

# Joining requires specifying the parent table
Article.joins(:comments).where(comments: { body: 'Great!' })
```

### Polymorphic Associations with STI (Single Table Inheritance)
When combining Polymorphism with STI, the `_type` column by default stores the base class name, not the subclass, unless configured otherwise. Active Record handles this via `ActiveRecord::Base.store_full_sti_class`.

## 3. Best Practices for Lead Engineers

### 1. Database Indexing (Composite Index)
Always use a composite index on both the `_type` and `_id` columns. Querying a polymorphic relation almost always filters by both. `t.references :commentable, polymorphic: true` in migrations does this automatically, but manually added columns need `add_index :comments, [:commentable_type, :commentable_id]`.

### 2. Managing Referential Integrity
Since you lack Foreign Key constraints, orphaned records are a massive risk. Enforce `dependent: :destroy` on all parent models. For large-scale apps, consider background jobs or soft-deletes to clean up polymorphic children rather than blocking web requests with cascading deletes.

### 3. Consider Alternatives at Scale (Join Tables / Specialized Tables)
If a table grows to hundreds of millions of rows, polymorphic queries can become bottlenecks. Sometimes, separate tables (`article_comments`, `video_comments`) or explicit join tables provide better performance, tighter types, and foreign key safety.

## 4. Interview Preparation

### Q: How do polymorphic associations work internally at the database level?
**A:** They use two columns in the child table: a string column storing the parent's class name (e.g., `commentable_type`) and an integer column storing the parent's primary key (e.g., `commentable_id`). Active Record dynamically builds SQL queries using both columns to fetch the associated parent record.

### Q: What is the biggest limitation of polymorphism in relational databases?
**A:** The lack of Foreign Key constraints. Because the `_id` column maps to IDs in multiple different tables depending on the `_type`, the database engine cannot enforce referential integrity. This can lead to orphaned records if application-level callbacks fail.

### Q: When would you choose STI over a Polymorphic association?
**A:** Use STI when models share the same data fields and database structure but have different behavior or validations. Use Polymorphism when completely different models (different tables and structures, like `User` and `Post`) need to share a common functional concern (like `Image` or `Comment`).

### Q: How do you prevent N+1 queries with polymorphic associations?
**A:** You can use eager loading with `includes`. However, because the parent records come from different tables, Rails performs separate queries for each parent type. Example: `Comment.includes(:commentable).all` will do one query for comments, one for all related Articles, one for related Videos, etc.
