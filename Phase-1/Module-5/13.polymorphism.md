# Polymorphic Associations in Rails (Beginner-Friendly Guide)

A polymorphic association lets **one Rails model belong to different kinds of models** through the same relationship.

A simple example is a comment system:

- An `Article` can have comments.
- A `Video` can have comments.
- A `Photo` can have comments.

Instead of creating a separate association and foreign key for every possible commentable model, we create **one flexible association** called `commentable`.

> Think of `commentable` as a label on a comment that says: “This comment belongs to **this record**, and that record can be an article, video, photo, or another supported model.”

---

## 1. The Problem Polymorphism Solves

Imagine we do **not** use a polymorphic association. The `comments` table might look like this:

```text
comments
+----+----------------+------------+----------+----------+
| id | body           | article_id | video_id | photo_id |
+----+----------------+------------+----------+----------+
|  1 | Great article! |     10     |   NULL   |   NULL   |
|  2 | Nice video!    |    NULL    |    4     |   NULL   |
|  3 | Beautiful!     |    NULL    |   NULL   |    7     |
+----+----------------+------------+----------+----------+
```

This has some problems:

- The table needs a new column every time we add a new commentable model.
- Most rows contain unnecessary `NULL` values.
- The code becomes repetitive.
- It is easy to accidentally set more than one foreign key.

With polymorphism, the same data can be represented like this:

```text
comments
+----+----------------+-----------------+------------------+
| id | body           | commentable_id  | commentable_type |
+----+----------------+-----------------+------------------+
|  1 | Great article! |       10        | Article          |
|  2 | Nice video!    |        4        | Video            |
|  3 | Beautiful!     |        7        | Photo            |
+----+----------------+-----------------+------------------+
```

The two columns work together:

- `commentable_id` tells us **which record** to use.
- `commentable_type` tells us **which table/model** to use.

For example:

```text
commentable_id:   10
commentable_type: Article

Meaning: find the Article whose id is 10.
```

```text
commentable_id:   4
commentable_type: Video

Meaning: find the Video whose id is 4.
```

The ID alone is not enough because an `Article` with ID `10` and a `Video` with ID `10` could both exist. The type tells Rails where to look.

## 2. The Complete Example: Comments on Articles and Videos

We will build this relationship:

```text
Article 1 ─── has many ─── Comment 1
                             |
                             └── commentable_type = "Article"

Video 1 ───── has many ─── Comment 2
                             |
                             └── commentable_type = "Video"
```

One `Comment` belongs to one `commentable`, while an `Article` or `Video` can have many comments.

### Step 1: Create the migration

```ruby
class CreateComments < ActiveRecord::Migration[7.0]
  def change
    create_table :comments do |t|
      t.text :body, null: false

      # Creates these two columns:
      # commentable_id   - the ID of the parent record
      # commentable_type - the model name of the parent record
      t.references :commentable, polymorphic: true, null: false, index: true

      t.timestamps
    end
  end
end
```

The migration creates columns similar to these:

```text
comments
- id
- body
- commentable_id
- commentable_type
- created_at
- updated_at
```

`polymorphic: true` is the important part. It tells Rails to create both the `_id` and `_type` columns.

### Step 2: Add the association to the child model

The model that stores the two polymorphic columns uses `belongs_to`:

```ruby
class Comment < ApplicationRecord
  belongs_to :commentable, polymorphic: true
end
```

This tells Rails:

> “A comment belongs to one record, but the record may be an `Article`, `Video`, `Photo`, or another model that opts into this association.”

### Step 3: Add the association to each parent model

Each model that can receive comments uses `has_many` with `as:`:

```ruby
class Article < ApplicationRecord
  has_many :comments, as: :commentable, dependent: :destroy
end
```

```ruby
class Video < ApplicationRecord
  has_many :comments, as: :commentable, dependent: :destroy
end
```

The value `:commentable` must match the association name in `Comment`:

```ruby
# Comment
belongs_to :commentable, polymorphic: true

# Article and Video
has_many :comments, as: :commentable
```

### The relationship in one picture

```text
Comment model                         Parent models

belongs_to :commentable               Article
polymorphic: true                     has_many :comments, as: :commentable
       |                              |
       |                              Video
       +------------------------------+-- has_many :comments, as: :commentable
```

## 3. Creating and Reading Records

### Create a comment on an article

```ruby
article = Article.find(1)
comment = article.comments.create(body: "This is very helpful!")
```

Rails saves something like this:

```text
comments
+----+-----------------------+-----------------+------------------+
| id | body                  | commentable_id  | commentable_type |
+----+-----------------------+-----------------+------------------+
|  1 | This is very helpful! |        1        | Article          |
+----+-----------------------+-----------------+------------------+
```

You can also assign the parent directly:

```ruby
comment = Comment.create(
  body: "I learned something new.",
  commentable: article
)
```

### Create a comment on a video

```ruby
video = Video.find(1)
video.comments.create(body: "The explanation was clear.")
```

Rails stores the same two-column structure, but the type is now `Video`:

```text
commentable_id:   1
commentable_type: Video
```

### Read the parent from a comment

```ruby
comment = Comment.first
comment.commentable
```

Rails checks `commentable_type` and then uses `commentable_id`:

```text
If type = "Article" and id = 1:
  Article.find(1)

If type = "Video" and id = 1:
  Video.find(1)
```

The result might be an `Article` or a `Video`—the code does not need to know which one in advance.

### Read comments from a parent

```ruby
article.comments
video.comments
```

Both calls return `Comment` records, but Rails automatically uses the correct type and ID in the query.

You can also ask for the comments from any supported parent:

```ruby
article.comments.create(body: "Comment on the article")
video.comments.create(body: "Comment on the video")
```

## 4. What Rails Queries Behind the Scenes

When you run:

```ruby
article.comments
```

Rails effectively needs to find comments matching both values:

```sql
SELECT * FROM comments
WHERE commentable_type = 'Article'
  AND commentable_id = 1;
```

When you run:

```ruby
comment.commentable
```

Rails reads the stored type and ID, then runs a query similar to one of these:

```sql
-- If commentable_type is "Article"
SELECT * FROM articles WHERE id = 1;

-- If commentable_type is "Video"
SELECT * FROM videos WHERE id = 1;
```

This is why the pair `commentable_type` and `commentable_id` must be considered together.

---

## 5. Querying Polymorphic Associations

### Find comments belonging to one type

```ruby
Comment.where(commentable_type: "Article")
```

This finds comments whose parent is an `Article`, regardless of the article ID.

### Find comments for one specific article

Prefer using the association because Rails adds both the type and ID:

```ruby
article.comments
```

You can also write the conditions explicitly:

```ruby
Comment.where(
  commentable_type: "Article",
  commentable_id: article.id
)
```

### Search through a specific parent table

Because `commentable` can point to different tables, Rails cannot make one universal SQL join for every possible parent type. Join through the specific model instead:

```ruby
Article
  .joins(:comments)
  .where(comments: { body: "Great!" })
```

This means:

> “Find articles that have a comment whose body is `Great!`.”

For videos, use the `Video` model:

```ruby
Video
  .joins(:comments)
  .where(comments: { body: "Great!" })
```

## 6. Avoiding N+1 Queries

Suppose we display the parent of every comment:

```ruby
comments = Comment.all

comments.each do |comment|
  puts comment.commentable.title
end
```

This can cause an N+1 query problem:

```text
1 query to load all comments
+ 1 query for each comment's Article or Video
= many database queries
```

Use eager loading instead:

```ruby
comments = Comment.includes(:commentable)

comments.each do |comment|
  puts comment.commentable.title
end
```

Rails may issue one query for comments and separate queries for each parent type, such as one for `articles` and one for `videos`. That is expected because the parents live in different tables.

```text
Without includes:
comments query + article query + video query + ...

With includes:
comments query + one query for each parent type
```

## 7. Deleting Parent Records Safely

Polymorphic associations do not create a normal database foreign key because one ID can refer to different tables. This means the database may not automatically protect us from orphaned comments.

An orphaned comment looks like this:

```text
Comment says: commentable_type = "Article", commentable_id = 10
But Article 10 has been deleted.
```

Use `dependent: :destroy` when the child records should be deleted with the parent:

```ruby
class Article < ApplicationRecord
  has_many :comments, as: :commentable, dependent: :destroy
end

class Video < ApplicationRecord
  has_many :comments, as: :commentable, dependent: :destroy
end
```

Now deleting an article also deletes its comments:

```ruby
article.destroy
```

Choose the dependent behavior based on the business rule. For example, `dependent: :nullify` may be appropriate when comments should remain but their parent reference should be removed. Remember that polymorphic foreign keys cannot be enforced by a standard database foreign key constraint in the same way as a normal `belongs_to` relationship.

## 8. Indexing for Performance

A polymorphic lookup usually checks both columns:

```sql
WHERE commentable_type = 'Article'
  AND commentable_id = 1
```

Therefore, an index on both columns is useful:

```ruby
t.references :commentable,
  polymorphic: true,
  null: false,
  index: true
```

If you create the columns manually, add a composite index:

```ruby
add_index :comments, [:commentable_type, :commentable_id]
```

The index helps the database quickly find the comments for one specific parent instead of scanning every comment.

> Note: Rails versions and migration options can differ in the exact index generated by `t.references`. Check the generated migration or schema when performance is important, and make sure the composite index you need exists.

## 9. When Should You Use a Polymorphic Association?

Polymorphism is a good fit when several different models share the same kind of relationship.

Common examples:

```text
Comment    -> Article, Video, Photo
Image      -> User, Product, Article
Activity   -> User, Order, Payment
Tagging    -> Article, Video, Book
Attachment -> Message, Invoice, Profile
```

Use it when:

- The child model behaves similarly regardless of its parent type.
- You want one shared table and one shared piece of code.
- The list of supported parent types is reasonably stable.

Avoid it or reconsider it when:

- Each parent type has very different rules and behavior.
- You need strict database-level foreign key constraints.
- The table is extremely large and cross-type queries are becoming difficult to optimize.
- The relationship needs many type-specific columns or validations.

At that point, separate tables or explicit join tables may be clearer:

```text
article_comments
video_comments
photo_comments
```

There is no universal “best” design. Choose the simpler design that matches the data and the rules of your application.

## 10. Polymorphism Compared with STI

Polymorphic associations and Single Table Inheritance (STI) solve different problems.

### Polymorphic associations

Use polymorphism when one record can belong to different model types stored in different tables:

```text
Comment -> Article
Comment -> Video
Comment -> Photo
```

### Single Table Inheritance (STI)

Use STI when related model types share the same table and mostly the same fields:

```text
vehicles table
+----+-------------+---------+
| id | type        | wheels  |
+----+-------------+---------+
|  1 | Car         |    4    |
|  2 | Motorcycle  |    2    |
+----+-------------+---------+
```

In this example, `Car` and `Motorcycle` are different Ruby classes, but both records live in the `vehicles` table.

A quick comparison:

```text
Polymorphism:  one child -> many possible parent tables
STI:           many child classes -> one shared table
```

---

## 11. A Note About Polymorphism and STI Together

Combining polymorphic associations with STI requires care. Rails may store the base class name in the polymorphic `_type` column rather than the subclass name, depending on the configuration.

For example, if `Car` and `Truck` inherit from `Vehicle`, the type stored for a vehicle association may be `Vehicle`. This allows Rails to use the `vehicles` table correctly.

Before using both patterns together:

1. Understand which class name Rails stores in the `_type` column.
2. Test creating, loading, and deleting records.
3. Avoid manually changing `_type` values unless you fully understand the consequences.

## 12. A Small End-to-End Example

### Models

```ruby
class Comment < ApplicationRecord
  belongs_to :commentable, polymorphic: true
end

class Article < ApplicationRecord
  has_many :comments, as: :commentable, dependent: :destroy
end

class Video < ApplicationRecord
  has_many :comments, as: :commentable, dependent: :destroy
end
```

### Create records

```ruby
article = Article.create!(title: "Ruby Basics")
video = Video.create!(title: "Rails Associations")

article.comments.create!(body: "Very useful article")
video.comments.create!(body: "Excellent explanation")
```

### Read records

```ruby
article.comments.first.body
# => "Very useful article"

video.comments.first.body
# => "Excellent explanation"

comment = Comment.first
comment.commentable
# => an Article or Video object, depending on the stored type
```

### Visualize the database rows

```text
articles                         videos
+----+-------------+             +----+------------------+
| id | title       |             | id | title            |
+----+-------------+             +----+------------------+
|  1 | Ruby Basics |             |  1 | Rails Associations|
+----+-------------+             +----+------------------+

comments
+----+----------------------+-----------------+------------------+
| id | body                 | commentable_id  | commentable_type |
+----+----------------------+-----------------+------------------+
|  1 | Very useful article  |        1        | Article          |
|  2 | Excellent explanation|        1        | Video            |
+----+----------------------+-----------------+------------------+
```

Notice that both comments use `commentable_id = 1`, but they belong to different records because their types are different.

## 13. Common Mistakes

### Mistake 1: Forgetting `polymorphic: true`

This is incomplete:

```ruby
belongs_to :commentable
```

Use this instead:

```ruby
belongs_to :commentable, polymorphic: true
```

### Mistake 2: Forgetting `as:` on the parent

This is also incomplete:

```ruby
has_many :comments
```

Use this instead:

```ruby
has_many :comments, as: :commentable
```

### Mistake 3: Using different association names

These names must match:

```ruby
# Child
belongs_to :commentable, polymorphic: true

# Parent
has_many :comments, as: :commentable
```

If the child uses `:commentable` but the parent uses `as: :commentable_record`, Rails will not connect them automatically.

### Mistake 4: Changing only the ID

Do not update only `commentable_id`. The type and ID belong together:

```ruby
comment.update!(
  commentable: another_article
)
```

Assigning the object lets Rails update both columns correctly.

## 14. Interview Questions and Answers

### What is a polymorphic association?

It is a Rails association where one model can belong to more than one model type through one association. Rails uses an ID column and a type column, such as `commentable_id` and `commentable_type`.

### How does it work in the database?

The child table stores:

```text
commentable_id    -> the parent's ID
commentable_type  -> the parent's model name
```

Together, they tell Rails which table and record to load.

### What is its biggest limitation?

A standard database foreign key cannot point to multiple possible tables. Therefore, database-level referential integrity is limited, and the application must carefully handle deleted parents and orphaned records.

### How do you prevent N+1 queries?

Use eager loading:

```ruby
Comment.includes(:commentable)
```

Rails will still use separate queries for different parent types, but it avoids one query per individual comment.

### When would you choose STI instead?

Choose STI when related classes share one table and the same general data structure. Choose polymorphism when the possible parents are different models, usually stored in different tables.

## 15. Final Mental Model

Remember this sentence:

> A polymorphic association is one relationship with two labels: **what record?** (`_id`) and **what kind of record?** (`_type`).

For our comment example:

```text
Comment
  |
  | commentable_id = 1
  | commentable_type = "Article"
  v
Article with id 1
```

or:

```text
Comment
  |
  | commentable_id = 1
  | commentable_type = "Video"
  v
Video with id 1
```

Once you understand that the type chooses the table and the ID chooses the row, polymorphic associations become much easier to design, query, and explain.
