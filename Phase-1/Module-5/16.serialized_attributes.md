# Mastering Serialized Attributes

## 1. What are serialized attributes?

A serialized attribute stores a Ruby structure such as a hash or array inside one database column.

For example, instead of creating three columns for display preferences, you might store one document:

```text
settings: { "theme": "dark", "email_alerts": true }
```

This is convenient for flexible data, but it is not a replacement for normal relational columns and tables.

## 2. JSON columns and `store_accessor`

For PostgreSQL, prefer a native `jsonb` column:

```ruby
# Migration
add_column :users, :settings, :jsonb, default: {}, null: false
```

Then define convenient accessors:

```ruby
class User < ApplicationRecord
  store_accessor :settings, :theme, :email_alerts
end

user = User.new
user.theme = "dark"
user.email_alerts = true
user.save!
```

The Ruby object feels like it has `theme` and `email_alerts` attributes, while the database stores them inside `settings`:

```text
users.settings
└── { "theme": "dark", "email_alerts": true }
```

For MySQL, use its native JSON type where appropriate.

## 3. Legacy `serialize`

Rails can serialize a normal text column, historically using YAML:

```ruby
class User < ApplicationRecord
  serialize :preferences, type: Array
end
```

This is mainly useful when working with an existing schema. For new work, native JSON/JSONB columns are usually better because the database understands their structure.

Do not deserialize untrusted YAML or arbitrary Ruby objects. Use safe, supported types and native JSON whenever possible.

## 4. Querying JSONB

A JSONB column can be queried, but the syntax is database-specific:

```ruby
User.where("settings ->> 'theme' = ?", "dark")
```

If the application frequently searches JSONB data, add an appropriate index. A GIN index is commonly useful for containment queries:

```ruby
add_index :users, :settings, using: :gin
```

An index is not a substitute for good data modeling. Test the actual query and query plan.

## 5. When should you use it?

Good candidates:

- Preferences that belong only to one record.
- Optional metadata from an external API.
- Data whose keys change frequently and is rarely filtered.

Prefer regular columns or related tables when a value is:

- Frequently searched, sorted, grouped, or joined.
- Required for database constraints or uniqueness.
- Important to reporting or analytics.
- Shared by multiple records.

Visual comparison:

```text
Flexible metadata       -> JSONB document
Frequently queried name -> users.name column
Many line items          -> order_items table
```

## 6. Quick interview answers

**What is serialization?**  Converting a Ruby structure to a storable database representation and converting it back when reading.

**Why prefer JSONB over YAML text?**  JSONB is structured, queryable, indexable, and understood by the database.

**When should data be normalized?**  When the data is central to the domain or frequently queried, validated, joined, or aggregated.

**How do I expose keys as model methods?**  Use `store_accessor :column, :key1, :key2`.
