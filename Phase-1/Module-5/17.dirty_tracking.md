# Mastering Dirty Tracking

## 1. What is dirty tracking?

Dirty tracking tells you which attributes have changed on an Active Record object and whether those changes have been saved.

Think of a record as having two versions:

```text
Database:  name = "Ada"
Memory:    name = "Grace"
           ^ unsaved change
```

Rails uses this information to run conditional logic and avoid updating columns that did not change.

> Dirty state belongs to one Ruby object in memory. It does not survive reloading the object or a new web request.

## 2. Before saving: unsaved changes

```ruby
user = User.find(1) # name is "Ada"
user.name = "Grace"

user.changed?          # true
user.name_changed?     # older Rails API; version-dependent
user.name_was          # "Ada" (older Rails API)
user.name_change       # ["Ada", "Grace"] (older Rails API)
user.changes            # { "name" => ["Ada", "Grace"] }
```

For current Rails code, prefer the explicit mutation API:

```ruby
user.will_save_change_to_name? # true
user.name_change_to_be_saved   # ["Ada", "Grace"]
user.changes_to_save            # changes that will be saved
```

The exact helper names vary across Rails versions, so check the API for the version used by the application.

## 3. After saving: saved changes

After the save succeeds, ask what was actually persisted:

```ruby
user.save!

user.saved_change_to_name? # true
user.saved_change_to_name  # ["Ada", "Grace"]
user.saved_changes         # { "name" => ["Ada", "Grace"] }
```

Inside an `after_commit` callback, use saved-change methods:

```ruby
class User < ApplicationRecord
  after_commit :send_name_change_email,
    if: :saved_change_to_name?

  private

  def send_name_change_email
    UserMailer.name_changed(self).deliver_later
  end
end
```

This sends the email only after the database transaction commits successfully.

## 4. The most important timing rule

Use the API that matches the callback timing:

```text
Before save / validation  -> will_save_change_to_status?
After save / after commit  -> saved_change_to_status?
```

Do not use `changed?` in `after_commit` to decide what was persisted. At that point, the pending changes have already been saved.

## 5. Partial writes

If only `name` changes, Rails can generate an update like this:

```sql
UPDATE users SET name = 'Grace' WHERE id = 1;
```

It does not need to rewrite every column. This is called a **partial write**. It reduces unnecessary database work and lowers the risk of overwriting values changed elsewhere.

## 6. Common uses

```ruby
class Order < ApplicationRecord
  after_commit :publish_event, if: :saved_change_to_status?

  private

  def publish_event
    Events.publish("order.status_changed", saved_changes)
  end
end
```

Typical uses include audit logs, cache invalidation, search indexing, webhooks, and notifications. Keep expensive side effects in `after_commit` so they are not triggered by a transaction that later rolls back.

## 7. Quick interview answers

**What is dirty tracking?**  Active Record’s in-memory record of attribute mutations and the values before and after them.

**What do I use before saving?**  `will_save_change_to_attribute?` and `changes_to_save`.

**What do I use after saving?**  `saved_change_to_attribute?`, `saved_change_to_attribute`, and `saved_changes`.

**What are partial writes?**  Updating only columns whose values changed instead of writing every column on every save.
