# Mastering Dirty Tracking

## 1. Overview
*   **What it is:** A feature of `ActiveModel::Dirty` that allows an object to track unsaved changes to its attributes. It knows what changed, what the original value was, and what the new value is.
*   **Why it exists:** To enable conditional logic before and after database commits (e.g., sending an email only if the `email` column was changed) and to optimize SQL queries by only updating changed columns (partial writes).
*   **When to use it:** Inside callbacks (`before_save`, `after_commit`) for audit logging, webhooks, side-effects, and cache invalidation.
*   **Common Misconceptions:**
    *   *"Dirty tracking works across HTTP requests."* (False: Dirty state is entirely in-memory for the current Ruby object instance and is lost once the object is destroyed or reloaded).

---

## 2. Core Concepts

### Pre-Save Methods (Before object is saved)
These methods track changes currently residing in memory but not yet committed to the database.

```ruby
user = User.find(1)
user.name = "New Name"

user.changed?           # true
user.name_changed?      # true
user.name_was           # "Old Name"
user.name_change        # ["Old Name", "New Name"]
user.changes            # {"name" => ["Old Name", "New Name"]}
```

### Post-Save Methods (After object is saved)
In Rails 5.1+, the tracking methods changed for `after_save` / `after_commit` callbacks. Previously, `_changed?` methods worked; now you must use `saved_change_to_` or `previously_changed?`.

```ruby
# Inside an after_save or after_commit callback:
user.saved_change_to_name?         # true
user.saved_change_to_name          # ["Old Name", "New Name"]
user.name_previously_changed?      # true
user.previous_changes              # {"name" => ["Old Name", "New Name"]}
```

### Callback-Specific Predictors
In `before_save` callbacks, use `will_save_change_to_<attribute>?` to see what is about to hit the database.

```ruby
before_save :trigger_webhook, if: :will_save_change_to_status?
```

### Partial Writes
Because Active Record knows exactly which columns are dirty, it automatically generates `UPDATE` SQL statements that only include the changed columns. This reduces network overhead and prevents overwriting data from concurrent processes.

## 3. Best Practices for Lead Engineers

### 1. Master Post-Commit State
The number one bug with dirty tracking is using `changed?` inside an `after_commit` block. Because the database transaction is closed, the object is no longer "dirty." You must use `saved_change_to_<attribute>?` or `previous_changes` when pushing updates to background jobs or external services.

### 2. Audit Logging via Changes Hash
Pass `user.saved_changes` or `user.previous_changes` to background workers to create audit trails (e.g., PaperTrail-lite). Because the hash holds the `[before, after]` state, it’s the perfect payload for history tables.

### 3. Avoid Expensive State Re-calculations
Don't fire heavy API calls or caching recalculations blindly on save. Wrap them in `if saved_change_to_X?` so you only incur the performance penalty when the relevant data actually mutates.

## 4. Interview Preparation

### Q: How does Dirty Tracking work internally?
**A:** `ActiveModel::Dirty` maintains internal mutation hashes (e.g., `@mutations_from_database`, `@previously_changed`). When an attribute writer is called (e.g., `name=`), it compares the new value to the original value stored in memory. If they differ, it records the change in these hashes.

### Q: What is the difference between `changed?` and `previously_changed?`
**A:** `changed?` is used *before* the record is saved to the database to check if there are unsaved mutations in memory. `previously_changed?` is used *after* the record is saved (e.g., in `after_save` or `after_commit`) to check what mutated during the last save operation.

### Q: How do you correctly trigger an email only if a user's email address is updated in an `after_commit` callback?
**A:** You use `saved_change_to_email?`. Example:
`after_commit :send_confirmation, if: :saved_change_to_email?`

### Q: What are "partial writes" in Active Record?
**A:** By default, when you save an Active Record model, Rails looks at the dirty tracking data and only includes the columns that actually changed in the generated SQL `UPDATE` statement. This improves database performance and helps prevent race conditions where two processes are updating different columns on the same row.
