# Mastering ActiveModel

## 1. Overview
*   **What it is:** A library inside Rails containing the interfaces and modules that allow plain Ruby objects to interact with Action Pack (controllers/views) as if they were Active Record models.
*   **Why it exists:** To separate database functionality from model behavior. It provides validations, callbacks, and dirty tracking without tying the object to an SQL table.
*   **When to use it:** For Form Objects, Search Objects, Service Objects, or API consumers where you need validations and form_helpers but don't persist to a relational database.
*   **Common Misconceptions:**
    *   *"ActiveModel is the parent class of ActiveRecord."* (False: ActiveModel is a collection of mixins/modules. `ActiveRecord::Base` includes these modules).

## 2. Core Concepts

### ActiveModel::Model (and ActiveModel::API)
Including `ActiveModel::Model` (or `ActiveModel::API` in Rails 7+) instantly gives a plain Ruby object initialization via hashes, validations, and view integration (`form_with`).

```ruby
class ContactForm
  include ActiveModel::Model

  attr_accessor :name, :email, :message

  validates :name, :message, presence: true
  validates :email, format: { with: URI::MailTo::EMAIL_REGEXP }

  def deliver
    return false unless valid?
    ContactMailer.send_message(self).deliver_now
  end
end
```

### ActiveModel::Attributes
Brings Active Record's type casting to POROs (Plain Old Ruby Objects).

```ruby
class SearchFilter
  include ActiveModel::Model
  include ActiveModel::Attributes

  attribute :start_date, :date
  attribute :limit, :integer, default: 20
end

filter = SearchFilter.new(limit: "50", start_date: "2023-01-01")
filter.limit      # 50 (Integer, not String)
filter.start_date # Date object
```

### ActiveModel Modules Breakdown
`ActiveRecord` achieves its power by including discrete AM modules:
*   `ActiveModel::Validations`: `validates`, `errors`
*   `ActiveModel::Callbacks`: `define_callbacks`, `before_validation`
*   `ActiveModel::Serialization`: JSON serialization interfaces
*   `ActiveModel::Naming`: allows `form_with` to guess route names and element IDs

## 3. Best Practices for Lead Engineers

### 1. Extract Complex Forms into Form Objects
If a single HTML form updates multiple models (e.g., User, Profile, and Settings at once) or requires complex conditional validation, do not use `accepts_nested_attributes_for`. Instead, create an `ActiveModel` Form Object. It acts as the orchestrator, keeping the Active Record models thin and focused purely on persistence.

### 2. Standardize Service Objects
While you can write Service Objects as pure POROs, including `ActiveModel::Validations` allows you to validate inputs cleanly before execution and return standard Rails `errors` back to the controller, keeping the controller API uniform.

### 3. Prefer ActiveModel::API in Rails 7+
Rails 7 extracted `ActiveModel::API` from `ActiveModel::Model`. `Model` contains `API` but also assumes the class is somewhat similar to a database record. For pure interface compliance without assumptions, `include ActiveModel::API` is the leanest, most modern approach.

## 4. Interview Preparation

### Q: What is the difference between ActiveModel and ActiveRecord?
**A:** `ActiveRecord` is an Object-Relational Mapper (ORM) that connects classes to relational database tables. `ActiveModel` is a library of modules (like validations, callbacks, and naming) that `ActiveRecord` relies on. `ActiveModel` provides framework features without any database coupling.

### Q: When would you use an ActiveModel Form Object?
**A:** When a user interface requires a form that doesn't map 1-to-1 with a database table. Examples include a "Contact Us" form that sends an email, a "Checkout" form that charges a credit card and updates multiple records, or a complex search filter.

### Q: How does `ActiveModel` allow a pure Ruby object to work with `form_with`?
**A:** By including `ActiveModel::Naming` and `ActiveModel::Conversion`. These modules provide methods like `model_name` and `to_param` that Action View helpers rely on to generate HTML form tags, input names (like `contact[email]`), and routing URLs automatically.

### Q: What does `ActiveModel::Attributes` provide?
**A:** It provides robust type casting for plain Ruby objects. It automatically converts form inputs (which are always strings) into native Ruby types like Dates, Booleans, and Integers based on the defined attribute schema, mimicking how ActiveRecord casts data based on database column types.
