# Mastering SQL Fundamentals

## 1. Overview
*   **What it is:** SQL (Structured Query Language) is the declarative language used to define, manipulate, query, and control data in relational databases.
*   **Why it exists:** It provides a standardized, set-based interface for interacting with relational data, abstracting away storage and retrieval mechanics so engineers describe *what* data they want, not *how* to get it.
*   **When to use it:** Whenever you need to read, write, or transform structured data in a relational database—which in practice means nearly every backend request.
*   **Common Misconceptions:**
    *   *"ORM-generated SQL is always good enough."* (False: ORMs frequently produce N+1 queries, unnecessary columns via `SELECT *`, and suboptimal joins. Understanding raw SQL lets you audit, override, and optimize.)
    *   *"NULL means empty string or zero."* (False: `NULL` represents the *absence of a value*. It is not equal to anything, not even itself—`NULL = NULL` evaluates to `NULL`, not `TRUE`.)
    *   *"HAVING and WHERE are interchangeable."* (False: `WHERE` filters rows *before* aggregation; `HAVING` filters groups *after* aggregation. Using the wrong one changes semantics and performance.)

## 2. Core Concepts

### 2.1 SQL Sub-Language Categories (DDL / DML / DCL / TCL)

Understanding these categories clarifies what each statement *does* to the database and its transactional behavior.

| Category | Purpose | Key Statements | Auto-Commits? |
|---|---|---|---|
| **DDL** – Data Definition Language | Schema changes | `CREATE`, `ALTER`, `DROP`, `TRUNCATE` | Yes (implicit commit in most RDBMS; PostgreSQL allows transactional DDL) |
| **DML** – Data Manipulation Language | Row-level data ops | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | No – must be explicitly committed |
| **DCL** – Data Control Language | Permissions | `GRANT`, `REVOKE` | Yes |
| **TCL** – Transaction Control Language | Transaction mgmt | `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT` | N/A – *controls* commit behavior |

```sql
-- PostgreSQL supports transactional DDL (a major differentiator)
BEGIN;
  CREATE TABLE experiments (id SERIAL PRIMARY KEY, name TEXT NOT NULL);
  INSERT INTO experiments (name) VALUES ('control');
ROLLBACK; -- Both the table creation AND the insert are rolled back
```

### 2.2 CRUD Operations & Filtering

```sql
-- INSERT with RETURNING (PostgreSQL-specific, extremely useful)
INSERT INTO users (email, role, created_at)
VALUES ('ada@example.com', 'admin', NOW())
RETURNING id, email;

-- UPDATE with FROM clause (PostgreSQL extension for multi-table updates)
UPDATE orders
SET    status = 'archived'
FROM   users
WHERE  orders.user_id = users.id
  AND  users.deactivated_at IS NOT NULL;

-- DELETE with USING (PostgreSQL's multi-table delete syntax)
DELETE FROM line_items
USING  orders
WHERE  line_items.order_id = orders.id
  AND  orders.status = 'cancelled';
```

### 2.3 SELECT Clauses: ORDER BY, GROUP BY, HAVING, DISTINCT, LIMIT/OFFSET

The logical execution order of a SELECT is critical for interviews: `FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT/OFFSET`.

```sql
-- Aggregation with HAVING and aliases
SELECT   u.role,
         COUNT(*)        AS user_count,
         MAX(u.created_at) AS newest_signup
FROM     users u
WHERE    u.confirmed_at IS NOT NULL          -- filter rows BEFORE grouping
GROUP BY u.role
HAVING   COUNT(*) > 10                       -- filter groups AFTER aggregation
ORDER BY user_count DESC
LIMIT    5 OFFSET 10;                        -- pagination (but see keyset note below)
```

> **Production tip:** `LIMIT/OFFSET` scans and discards `OFFSET` rows every time. For large datasets, prefer **keyset (cursor) pagination**: `WHERE id > :last_seen_id ORDER BY id LIMIT 20`.

### 2.4 PostgreSQL Data Types Worth Knowing

| Type | Notes |
|---|---|
| `SERIAL` / `BIGSERIAL` | Auto-incrementing integers (syntactic sugar for a sequence + default). Prefer `BIGSERIAL` or `GENERATED ALWAYS AS IDENTITY`. |
| `TEXT` vs `VARCHAR(n)` | In PostgreSQL, `TEXT` and `VARCHAR` are stored identically. `VARCHAR(n)` only adds a check constraint. Prefer `TEXT` unless you need an explicit length limit. |
| `TIMESTAMPTZ` | Always use over `TIMESTAMP`—stores instants in UTC, converts on display. |
| `UUID` | Native 128-bit type; use `gen_random_uuid()` (PG 13+) for primary keys in distributed systems. |
| `JSONB` | Binary JSON with indexing support (GIN). Prefer over `JSON` for almost all use cases. |
| `BOOLEAN` | True three-valued logic: `TRUE`, `FALSE`, `NULL`. |
| `NUMERIC(p,s)` | Arbitrary-precision; use for money/financial data instead of `FLOAT`. |
| `INET` / `CIDR` | Native IP address types with operators like `<<` (contained within). |

### 2.5 NULL Handling: IS NULL, COALESCE, NULLIF

Three-valued logic means every comparison involving `NULL` yields `NULL` (not `FALSE`). This trips up even experienced engineers.

```sql
-- IS NULL / IS NOT NULL (the ONLY safe NULL comparisons)
SELECT * FROM users WHERE deleted_at IS NULL;

-- COALESCE: returns first non-NULL argument (variadic)
SELECT COALESCE(u.display_name, u.email, 'Anonymous') AS label
FROM   users u;

-- NULLIF: returns NULL if both args are equal (useful for avoiding division-by-zero)
SELECT total_revenue / NULLIF(total_orders, 0) AS avg_order_value
FROM   merchant_stats;

-- Gotcha: NOT IN with NULLs silently returns no rows
SELECT * FROM orders WHERE user_id NOT IN (1, 2, NULL);
-- Evaluates to: user_id != 1 AND user_id != 2 AND user_id != NULL
-- The last condition is always NULL → entire WHERE is never TRUE
-- Fix: use NOT EXISTS or filter NULLs from the subquery
```

### 2.6 CASE Expressions

`CASE` is an *expression* (returns a value), not a control-flow statement. It can appear in `SELECT`, `WHERE`, `ORDER BY`, and even inside aggregate functions.

```sql
-- Conditional aggregation (pivot-style query)
SELECT
  DATE_TRUNC('month', o.created_at)                         AS month,
  COUNT(*) FILTER (WHERE o.status = 'completed')            AS completed,  -- PG-specific
  COUNT(*) FILTER (WHERE o.status = 'refunded')             AS refunded,
  SUM(CASE WHEN o.status = 'completed' THEN o.total ELSE 0 END) AS revenue
FROM orders o
GROUP BY 1
ORDER BY 1;
```

## 3. Best Practices for Lead Engineers

### 1. Prefer Explicit Column Lists Over SELECT *
`SELECT *` pulls unnecessary data across the wire, breaks if columns are added/removed, and prevents covering-index-only scans. Always enumerate the columns you need—this also documents your query's contract with the caller.

### 2. Use RETURNING and CTEs to Reduce Round-Trips
PostgreSQL's `RETURNING` clause lets you get affected rows in a single statement instead of a follow-up `SELECT`. Combine with `INSERT ... ON CONFLICT` (upsert) and writable CTEs to perform complex multi-step mutations atomically in one query.

### 3. Treat NULL Semantics as a First-Class Design Decision
Decide at schema-design time which columns are nullable and why. Use `NOT NULL` constraints aggressively—they reduce ambiguity, improve query planner estimates, and prevent entire classes of bugs (e.g., the `NOT IN` with NULL pitfall above).

### 4. Default to TIMESTAMPTZ, BIGSERIAL, and TEXT
These safe defaults avoid the most common PostgreSQL regrets: timezone-unaware timestamps, integer-overflow on high-volume id columns, and arbitrary `VARCHAR` length limits that provide no performance benefit in PostgreSQL.

## 4. Interview Preparation

### Q: Explain the logical execution order of a SQL SELECT statement. Why does it matter?
**A:** The logical order is `FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`. This matters because it determines which clauses can reference aliases (only `ORDER BY` and `HAVING` can reference `SELECT` aliases in PostgreSQL), why you cannot use `WHERE` on aggregates (grouping hasn't happened yet), and helps predict query behavior when debugging.

### Q: What is the difference between WHERE and HAVING?
**A:** `WHERE` filters individual rows before any grouping or aggregation occurs—it cannot reference aggregate functions. `HAVING` filters the result of `GROUP BY` after aggregation, so it *can* use aggregates like `COUNT(*)` or `SUM(amount)`. Putting a non-aggregate condition in `HAVING` instead of `WHERE` forces the engine to group first, harming performance.

### Q: Why does `SELECT * FROM t WHERE col NOT IN (SELECT x FROM s)` return no rows when `s` contains a NULL?
**A:** `NOT IN` expands to `col != v1 AND col != v2 AND ... AND col != NULL`. Since any comparison with `NULL` yields `NULL` (not `TRUE`), the entire `AND` chain can never be `TRUE`. The fix is to use `NOT EXISTS (SELECT 1 FROM s WHERE s.x = t.col)`, which handles NULLs correctly because `EXISTS` evaluates to a boolean, not a three-valued comparison.

### Q: When would you choose JSONB over a normalized relational schema in PostgreSQL?
**A:** Use `JSONB` for semi-structured, schema-less data where the shape varies per row (e.g., event metadata, feature flags, third-party webhook payloads). PostgreSQL can index `JSONB` with GIN indexes for fast containment queries (`@>`). However, if you need referential integrity, frequent joins, or aggregate queries on the data, normalize it into proper columns and tables—`JSONB` sacrifices type safety and query-planner statistics for flexibility.
