# Mastering SQL Joins

## 1. Overview
*   **What it is:** Joins combine rows from two or more tables based on a related column, producing a single result set that spans multiple entities.
*   **Why it exists:** Relational databases normalize data across tables; joins are the mechanism to reassemble that data for queries without denormalization.
*   **When to use it:** Whenever a query needs columns or filtering logic that spans more than one table—which is the majority of real-world queries.
*   **Common Misconceptions:**
    *   *"LEFT JOIN always returns more rows than INNER JOIN"* (False: If every row in the left table has a match, both return the same number of rows. LEFT JOIN only adds rows when there are *unmatched* left-side rows).
    *   *"Joins are inherently slow"* (False: With proper indexes on join keys, joins are highly optimized by the query planner and often faster than application-level data stitching).
    *   *"Venn diagrams perfectly represent joins"* (False: Venn diagrams illustrate which rows survive filtering, but joins operate on row-pairing logic, not set intersection of identical elements. They are a useful mental shortcut, not a precise model).

## 2. Core Concepts

### INNER JOIN
Returns only rows where the join condition is satisfied in *both* tables. This is the most common join and the default when you write `JOIN` without a qualifier.
```sql
-- Find all orders with their customer details (only customers who have orders)
SELECT c.name, o.id AS order_id, o.total
FROM customers c
INNER JOIN orders o ON o.customer_id = c.id
WHERE o.created_at >= NOW() - INTERVAL '30 days';
```

### LEFT JOIN (LEFT OUTER JOIN)
Returns all rows from the left table, plus matched rows from the right table. Unmatched right-side columns are filled with `NULL`. Essential for "find all X, even those without Y" queries.
```sql
-- Find all customers and their most recent order, including customers who never ordered
SELECT c.name, c.email, o.id AS last_order_id, o.created_at
FROM customers c
LEFT JOIN LATERAL (
    SELECT id, created_at FROM orders
    WHERE customer_id = c.id
    ORDER BY created_at DESC LIMIT 1
) o ON TRUE;
```

### RIGHT JOIN and FULL OUTER JOIN
`RIGHT JOIN` is the mirror of `LEFT JOIN`—all rows from the right table are preserved. In practice, most engineers rewrite RIGHT JOINs as LEFT JOINs by swapping table order for readability. `FULL OUTER JOIN` preserves unmatched rows from *both* sides.
```sql
-- Reconciliation query: find orders or payments that don't match
SELECT o.id AS order_id, p.id AS payment_id, o.total, p.amount
FROM orders o
FULL OUTER JOIN payments p ON p.order_id = o.id
WHERE o.id IS NULL   -- payment with no order
   OR p.id IS NULL;  -- order with no payment
```

### CROSS JOIN
Produces the Cartesian product—every row from the left table paired with every row from the right table. Rarely used accidentally, but powerful for generating combinations or pairing with `generate_series`.
```sql
-- Generate a report skeleton: every product × every month in 2025
SELECT p.name, m.month
FROM products p
CROSS JOIN generate_series(
    '2025-01-01'::date, '2025-12-01'::date, '1 month'
) AS m(month);
```

### Self-Joins
A table joined to itself, typically to model hierarchical or comparative relationships. Always alias both references distinctly.
```sql
-- Find employees and their managers from the same table
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;

-- Find duplicate emails
SELECT a.id, b.id, a.email
FROM users a
INNER JOIN users b ON a.email = b.email AND a.id < b.id;
```

### NATURAL JOIN and Implicit Joins
`NATURAL JOIN` automatically joins on all columns sharing the same name—dangerous in production because schema changes silently alter join logic. Implicit joins (comma-separated `FROM` with `WHERE` conditions) are the legacy SQL-89 syntax; explicit `JOIN ... ON` is always preferred for clarity.
```sql
-- AVOID in production: natural join
SELECT * FROM orders NATURAL JOIN customers;

-- AVOID: implicit join (SQL-89 style)
SELECT c.name, o.total
FROM customers c, orders o
WHERE o.customer_id = c.id;

-- PREFER: explicit join (SQL-92 style)
SELECT c.name, o.total
FROM customers c
INNER JOIN orders o ON o.customer_id = c.id;
```

### Multi-Table Joins
Chain joins to traverse relationships. Order matters for readability and can influence the planner's initial join strategy, though PostgreSQL's optimizer usually reorders joins for efficiency.
```sql
-- Order details with customer and product info
SELECT c.name AS customer, p.name AS product,
       li.quantity, li.unit_price, o.created_at
FROM orders o
INNER JOIN customers c      ON c.id = o.customer_id
INNER JOIN line_items li     ON li.order_id = o.id
INNER JOIN products p        ON p.id = li.product_id
WHERE o.status = 'completed'
ORDER BY o.created_at DESC;
```

## 3. Best Practices for Lead Engineers

### 1. Always Use Explicit JOIN Syntax
Explicit `JOIN ... ON` separates join logic from filter logic (`WHERE`), making queries easier to review, debug, and modify. Implicit comma-joins risk accidental cross joins when a `WHERE` condition is forgotten.

### 2. Index Your Join Columns
Every foreign key used in an `ON` clause should have a B-tree index. PostgreSQL does *not* automatically create indexes on foreign key columns (unlike the primary key side). Missing FK indexes are the single most common cause of slow joins in production Rails apps.

### 3. Be Deliberate About NULL Semantics in Outer Joins
When using `LEFT JOIN`, remember that `WHERE` conditions on the right table's columns will silently convert it into an `INNER JOIN` (because NULLs fail the condition). Move right-table filters into the `ON` clause to preserve outer-join behavior.
```sql
-- WRONG: effectively an INNER JOIN because WHERE filters out NULLs
SELECT c.name, o.id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'shipped';

-- CORRECT: filter in ON clause preserves unmatched customers
SELECT c.name, o.id FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'shipped';
```

### 4. Prefer EXISTS Over JOIN for Existence Checks
When you only need to know *if* a related row exists (not its data), `EXISTS` often outperforms a join because the planner can stop at the first match rather than producing all matching pairs.
```sql
-- Faster than JOIN + DISTINCT for "customers who have at least one order"
SELECT c.name FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
```

## 4. Interview Preparation

### Q: What is the difference between `WHERE` filtering and `ON` clause filtering in a LEFT JOIN?
**A:** The `ON` clause determines which right-table rows are *paired* with left-table rows. The `WHERE` clause filters the *combined result set* after the join. Placing a right-table filter in `WHERE` eliminates NULLs from unmatched rows, effectively converting the LEFT JOIN into an INNER JOIN. To preserve all left-table rows while filtering the right side, put the condition in the `ON` clause.

### Q: When would you use a FULL OUTER JOIN in production?
**A:** FULL OUTER JOIN is ideal for data reconciliation and audit queries—for example, comparing an `orders` table against a `payments` table to find orders without payments *and* payments without orders. It's also useful in ETL pipelines when merging two datasets that may each have records the other lacks.

### Q: How does PostgreSQL execute a join under the hood, and what join strategies exist?
**A:** PostgreSQL's planner chooses among three strategies: **Nested Loop** (best for small result sets or indexed lookups—iterates the outer table and probes the inner), **Hash Join** (builds an in-memory hash table from the smaller table, then probes with the larger—great for equi-joins on unindexed columns), and **Merge Join** (sorts both inputs and merges—efficient when inputs are pre-sorted or when sorts can exploit indexes). Use `EXPLAIN ANALYZE` to see which strategy the planner selected and whether it's optimal.

### Q: How would you debug a query that returns more rows than expected after adding a JOIN?
**A:** This almost always indicates a many-to-many or one-to-many relationship that produces row multiplication. First, check the join key cardinality: `SELECT customer_id, COUNT(*) FROM orders GROUP BY 1 HAVING COUNT(*) > 1`. If duplicates exist and you only want one match, use `DISTINCT ON`, a `LATERAL` subquery with `LIMIT 1`, or aggregate functions. Understanding the data model's cardinality before writing joins prevents this class of bugs entirely.
