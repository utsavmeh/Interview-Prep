# Mastering SQL Aggregations

## 1. Overview
*   **What it is:** Aggregate functions collapse multiple rows into a single summary value, enabling statistical and analytical queries over datasets.
*   **Why it exists:** Raw row-level data is rarely useful on its own — business decisions require summaries like totals, averages, counts, and distributions.
*   **When to use it:** Whenever you need to compute metrics across groups of rows — revenue reports, user cohort analysis, dashboard statistics, or data validation checks.
*   **Common Misconceptions:**
    *   *"COUNT(*) and COUNT(column) are the same thing"* (False: `COUNT(*)` counts all rows including NULLs; `COUNT(column)` only counts rows where `column` is non-NULL).
    *   *"HAVING is just another WHERE"* (False: `WHERE` filters rows *before* aggregation; `HAVING` filters *groups after* aggregation. They operate at fundamentally different stages of query execution).
    *   *"AVG handles NULLs by treating them as zero"* (False: `AVG` silently *skips* NULL values entirely, which can produce misleading results if you expect zeros).

## 2. Core Concepts

### Basic Aggregate Functions
The five foundational aggregates each serve a distinct purpose. Understanding their NULL behavior is critical for production correctness.
```sql
-- Revenue dashboard for an e-commerce platform
SELECT
    COUNT(*)              AS total_orders,
    COUNT(shipped_at)     AS shipped_orders,    -- excludes NULLs (unshipped)
    SUM(amount_cents)     AS revenue_cents,
    AVG(amount_cents)     AS avg_order_cents,
    MIN(created_at)       AS first_order_at,
    MAX(created_at)       AS last_order_at
FROM orders
WHERE created_at >= DATE_TRUNC('month', CURRENT_DATE);
```

### GROUP BY and COUNT(DISTINCT)
`GROUP BY` partitions rows into buckets before aggregation. `COUNT(DISTINCT ...)` deduplicates within each bucket — essential for metrics like "unique users."
```sql
-- Monthly active users and revenue by product category
SELECT
    DATE_TRUNC('month', o.created_at)  AS month,
    p.category,
    COUNT(DISTINCT o.user_id)          AS unique_buyers,
    COUNT(*)                           AS total_orders,
    SUM(o.amount_cents) / 100.0        AS revenue_dollars
FROM orders o
JOIN products p ON p.id = o.product_id
GROUP BY DATE_TRUNC('month', o.created_at), p.category
ORDER BY month DESC, revenue_dollars DESC;
```

### HAVING vs WHERE — Filtering at the Right Stage
`WHERE` eliminates rows before groups are formed. `HAVING` eliminates entire groups after aggregation. Placing a filter in the wrong clause is a common source of subtle bugs.
```sql
-- Find high-value customer segments: users who placed 5+ orders
-- totalling over $500, excluding cancelled orders
SELECT
    user_id,
    COUNT(*)                    AS order_count,
    SUM(amount_cents) / 100.0   AS total_spent
FROM orders
WHERE status <> 'cancelled'          -- row-level filter: BEFORE aggregation
GROUP BY user_id
HAVING COUNT(*) >= 5                 -- group-level filter: AFTER aggregation
   AND SUM(amount_cents) > 50000;
```

### NULL Handling in Aggregates
All standard aggregates (except `COUNT(*)`) ignore NULLs. This is convenient but dangerous — a table full of NULLs returns NULL from `SUM`, not zero.
```sql
-- Safe aggregation with explicit NULL handling
SELECT
    department_id,
    COUNT(*)                                          AS total_employees,
    COUNT(salary)                                     AS employees_with_salary,
    COALESCE(AVG(salary), 0)                          AS avg_salary,
    COALESCE(SUM(salary), 0)                          AS total_payroll,
    -- Percentage of employees missing salary data
    ROUND(
        100.0 * (COUNT(*) - COUNT(salary)) / COUNT(*), 1
    )                                                 AS pct_missing_salary
FROM employees
GROUP BY department_id;
```

### GROUPING SETS, ROLLUP, and CUBE (PostgreSQL)
These extensions generate multiple levels of aggregation in a single query — replacing the need for `UNION ALL` of several grouped queries. They are essential for building reporting tables and OLAP-style summaries.
```sql
-- Revenue report with subtotals and grand total in one query
-- ROLLUP(year, quarter, category) produces:
--   (year, quarter, category), (year, quarter), (year), ()
SELECT
    EXTRACT(YEAR FROM created_at)::INT    AS year,
    EXTRACT(QUARTER FROM created_at)::INT AS quarter,
    category,
    SUM(amount_cents) / 100.0             AS revenue,
    COUNT(*)                              AS order_count
FROM orders
JOIN products ON products.id = orders.product_id
GROUP BY ROLLUP(
    EXTRACT(YEAR FROM created_at)::INT,
    EXTRACT(QUARTER FROM created_at)::INT,
    category
)
ORDER BY year NULLS LAST, quarter NULLS LAST, category NULLS LAST;

-- CUBE generates ALL possible combinations of grouping columns
-- Useful for pivot-table-style analysis
SELECT
    region,
    category,
    SUM(amount_cents) / 100.0 AS revenue
FROM orders
JOIN products ON products.id = orders.product_id
JOIN users ON users.id = orders.user_id
GROUP BY CUBE(region, category)
ORDER BY region NULLS LAST, category NULLS LAST;

-- GROUPING SETS for explicit control over which aggregation levels appear
SELECT
    EXTRACT(YEAR FROM created_at)::INT AS year,
    category,
    SUM(amount_cents) / 100.0          AS revenue
FROM orders
JOIN products ON products.id = orders.product_id
GROUP BY GROUPING SETS (
    (EXTRACT(YEAR FROM created_at)::INT, category),  -- per year+category
    (EXTRACT(YEAR FROM created_at)::INT),             -- per year subtotal
    ()                                                 -- grand total
);
```

### STRING_AGG and ARRAY_AGG (PostgreSQL)
These aggregates collect values into a single composite result — a comma-separated string or a PostgreSQL array. They eliminate the need for application-level concatenation and reduce N+1-style data fetching.
```sql
-- User profile summary: list each user's purchased product names
SELECT
    u.id,
    u.email,
    COUNT(DISTINCT o.id)                                    AS order_count,
    STRING_AGG(DISTINCT p.name, ', ' ORDER BY p.name)       AS purchased_products,
    ARRAY_AGG(DISTINCT p.category ORDER BY p.category)      AS categories
FROM users u
JOIN orders o ON o.user_id = u.id
JOIN products p ON p.id = o.product_id
GROUP BY u.id, u.email
ORDER BY order_count DESC
LIMIT 20;
```

## 3. Best Practices for Lead Engineers

### 1. Push Filtering into WHERE, Not HAVING
Any predicate that doesn't reference an aggregate belongs in `WHERE`. Filtering before grouping reduces the dataset the engine must hash or sort, which can be orders of magnitude faster on large tables. Reserve `HAVING` strictly for conditions on aggregated values.

### 2. Be Explicit About NULL Semantics
Wrap aggregates in `COALESCE` when a zero default is required. Document whether NULLs represent "unknown" or "not applicable" — the distinction changes whether `AVG` skipping them is correct or a data bug. Use `COUNT(*) - COUNT(col)` to surface NULL rates in monitoring queries.

### 3. Use ROLLUP/CUBE Instead of UNION ALL
Multi-level summary reports built with `UNION ALL` are fragile, hard to maintain, and force the engine to scan the table multiple times. `ROLLUP` and `CUBE` produce the same results in a single pass. Use the `GROUPING()` function to distinguish genuine NULLs from rollup-generated NULLs in the output.

### 4. Watch for Combinatorial Explosion with CUBE
`CUBE(a, b, c, d)` produces 2^n grouping sets (16 for 4 columns). On high-cardinality columns, this generates enormous result sets. Prefer `GROUPING SETS` with explicitly listed combinations when you only need specific aggregation levels.

## 4. Interview Preparation

### Q: What is the difference between WHERE and HAVING, and why does it matter for performance?
**A:** `WHERE` filters individual rows *before* `GROUP BY` forms groups, reducing the volume of data the aggregation engine processes. `HAVING` filters *after* groups are computed, so it can reference aggregate results like `COUNT(*)` or `SUM(col)`. Performance-wise, moving a non-aggregate filter from `HAVING` to `WHERE` can drastically reduce I/O and memory usage because fewer rows enter the grouping phase. The optimizer in PostgreSQL can sometimes rewrite this automatically, but you should not rely on it.

### Q: How do aggregate functions handle NULLs, and when can this cause incorrect results?
**A:** All standard aggregates except `COUNT(*)` silently skip NULL values. This means `AVG(salary)` computes the average of only non-NULL salaries, which inflates the result if NULLs represent employees earning zero. `SUM` over an all-NULL column returns NULL, not zero — which can break downstream arithmetic. The fix is to use `COALESCE(column, 0)` inside the aggregate when NULLs should be treated as zero, or to use `COALESCE` on the aggregate result to guarantee a non-NULL output.

### Q: Explain ROLLUP vs CUBE vs GROUPING SETS with a concrete example.
**A:** Given `GROUP BY ROLLUP(region, category)`, PostgreSQL produces three grouping levels: `(region, category)`, `(region)`, and `()` — a hierarchical drill-down from most to least specific. `CUBE(region, category)` produces all four combinations: `(region, category)`, `(region)`, `(category)`, and `()` — useful for pivot-table-style analysis. `GROUPING SETS` lets you list exactly which combinations you want, avoiding the combinatorial explosion of CUBE while still getting multi-level summaries in a single pass. Use `GROUPING(column)` to distinguish rollup-generated NULLs from actual NULL data values.

### Q: When would you use ARRAY_AGG or STRING_AGG instead of solving the problem in application code?
**A:** Use them when you need to return a "one-to-many" relationship as a single row — for example, fetching a user along with all their tags or product categories. Doing this in SQL avoids the N+1 query problem and reduces the number of round-trips to the database. `STRING_AGG` is ideal for display-ready output (e.g., CSV exports or UI labels), while `ARRAY_AGG` preserves the PostgreSQL array type, which is useful for further server-side processing or passing arrays into `ANY()` / `@>` operators in subsequent queries. Both support `ORDER BY` and `DISTINCT` within the aggregate call, giving you precise control over the output.
