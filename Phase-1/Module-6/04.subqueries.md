# Mastering SQL Subqueries

## 1. Overview
*   **What it is:** A subquery is a SQL query nested inside another query (in SELECT, FROM, WHERE, or HAVING clauses), used to compute intermediate results that feed into the outer query.
*   **Why it exists:** Subqueries allow you to break complex logic into composable steps—filtering by aggregated values, computing per-row derived columns, or constructing inline virtual tables—without requiring temporary tables or multiple round-trips.
*   **When to use it:** Use subqueries when you need a result that depends on another query's output, especially for existence checks, row-level computed values, or when a JOIN would produce unwanted row multiplication.
*   **Common Misconceptions:**
    *   *"Subqueries are always slower than JOINs"* (False: PostgreSQL's optimizer often rewrites subqueries into joins internally; correlated subqueries can be slow, but scalar and EXISTS subqueries are frequently as fast or faster than equivalent joins).
    *   *"NOT IN and NOT EXISTS are interchangeable"* (False: `NOT IN` produces no rows if the subquery returns any NULL, while `NOT EXISTS` handles NULLs correctly—this is a critical production bug source).

## 2. Core Concepts

### Scalar Subqueries
A scalar subquery returns exactly one row and one column. It can appear anywhere a single value is expected—in SELECT lists, WHERE comparisons, or even DEFAULT expressions.

```sql
-- Show each order with the company-wide average for context
SELECT id, total,
       (SELECT AVG(total) FROM orders) AS company_avg,
       total - (SELECT AVG(total) FROM orders) AS delta_from_avg
FROM orders
WHERE total > (SELECT AVG(total) FROM orders);
```
If a scalar subquery returns more than one row, PostgreSQL raises a runtime error. If it returns zero rows, the result is NULL.

### Column Subqueries (IN / ANY / ALL)
A column subquery returns a single column of multiple rows and is used with operators like `IN`, `ANY`, or `ALL`.

```sql
-- Find customers who placed orders above $500
SELECT name, email
FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE total > 500);

-- Equivalent using ANY (allows comparison operators beyond equality)
SELECT name, email
FROM customers
WHERE id = ANY(SELECT customer_id FROM orders WHERE total > 500);

-- Find products more expensive than ALL products in category 'basic'
SELECT name, price
FROM products
WHERE price > ALL(SELECT price FROM products WHERE category = 'basic');
```

### Derived Tables (Table Subqueries in FROM)
A subquery in the FROM clause produces an inline virtual table. PostgreSQL requires an alias for it.

```sql
-- Rank customers by their total spend
SELECT ranked.name, ranked.total_spend, ranked.rnk
FROM (
    SELECT c.name,
           SUM(o.total) AS total_spend,
           RANK() OVER (ORDER BY SUM(o.total) DESC) AS rnk
    FROM customers c
    JOIN orders o ON o.customer_id = c.id
    GROUP BY c.name
) ranked
WHERE ranked.rnk <= 10;
```

### Correlated vs Non-Correlated Subqueries
A **non-correlated** subquery runs once independently. A **correlated** subquery references the outer query and re-executes for each outer row (though PostgreSQL may optimize this).

```sql
-- Non-correlated: subquery is independent
SELECT * FROM products WHERE price > (SELECT AVG(price) FROM products);

-- Correlated: subquery references outer table
-- Find employees who earn more than their department average
SELECT e.name, e.salary, e.department_id
FROM employees e
WHERE e.salary > (
    SELECT AVG(e2.salary)
    FROM employees e2
    WHERE e2.department_id = e.department_id  -- references outer row
);
```

### EXISTS vs IN (and the NULL Trap)
`EXISTS` tests for row existence and short-circuits—it stops as soon as one matching row is found. `IN` materializes the full subquery result and compares. The critical difference surfaces with NULLs.

```sql
-- EXISTS: safe with NULLs, often faster on large sets
SELECT c.name
FROM customers c
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.id
);

-- NOT IN with NULLs — THE TRAP
-- If ANY row in the subquery returns NULL, NOT IN returns NO ROWS AT ALL
SELECT c.name
FROM customers c
WHERE c.id NOT IN (SELECT customer_id FROM orders);
-- If orders has a row where customer_id IS NULL, this returns NOTHING.

-- NOT EXISTS: safe alternative — always prefer this over NOT IN
SELECT c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.customer_id = c.id
);
```
**Why the NULL trap happens:** SQL uses three-valued logic. `x NOT IN (1, NULL)` evaluates to `x != 1 AND x != NULL`. Since `x != NULL` is UNKNOWN, the entire expression is UNKNOWN, so the row is excluded.

### LATERAL Joins (PostgreSQL-Specific)
`LATERAL` allows a subquery in FROM to reference columns from preceding tables in the same FROM clause—essentially a correlated subquery in the FROM position. This is invaluable for "top-N per group" patterns.

```sql
-- Get the 3 most recent orders for each customer
SELECT c.name, recent.*
FROM customers c
CROSS JOIN LATERAL (
    SELECT o.id, o.total, o.created_at
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY o.created_at DESC
    LIMIT 3
) recent;

-- LATERAL with LEFT JOIN (include customers with no orders)
SELECT c.name, recent.total
FROM customers c
LEFT JOIN LATERAL (
    SELECT o.total
    FROM orders o
    WHERE o.customer_id = c.id
    ORDER BY o.total DESC
    LIMIT 1
) recent ON true;
```
Without LATERAL, you'd need window functions with a wrapping query, which is often less readable and harder to optimize.

### Subqueries in HAVING
Subqueries in HAVING filter groups based on aggregate comparisons.

```sql
-- Find departments whose average salary exceeds the company average
SELECT department_id, AVG(salary) AS dept_avg
FROM employees
GROUP BY department_id
HAVING AVG(salary) > (SELECT AVG(salary) FROM employees);
```

## 3. Best Practices for Lead Engineers

### 1. Default to NOT EXISTS Over NOT IN
In production code, always use `NOT EXISTS` instead of `NOT IN` with subqueries. A single NULL in the subquery result silently returns zero rows with `NOT IN`. This is one of the most common subtle bugs in SQL. Enforce this via code review standards.

### 2. Use LATERAL for Top-N-Per-Group
When you need the top N related rows per parent record, `LATERAL` with `LIMIT` is cleaner and often faster than window-function approaches (especially when N is small and you have an index on the join + order columns). It leverages index scans per group rather than scanning the entire child table.

### 3. Prefer CTEs for Readability, Subqueries for Performance
PostgreSQL 12+ treats CTEs as inline (optimizable) by default, but in older versions CTEs are optimization fences. For complex queries, use CTEs for readability, but benchmark against equivalent subquery forms. Use `MATERIALIZED` / `NOT MATERIALIZED` hints in PG12+ to control this explicitly.

### 4. Watch for N+1 Correlated Subqueries in SELECT
A correlated subquery in the SELECT list executes once per outer row. While PostgreSQL sometimes optimizes these into joins, on large datasets this can be catastrophic. Profile with `EXPLAIN ANALYZE` and consider rewriting as a JOIN or window function if the subquery isn't being flattened.

## 4. Interview Preparation

### Q: What is the difference between a correlated and a non-correlated subquery? When would you choose one over the other?
**A:** A non-correlated subquery is independent of the outer query—it runs once and its result is reused. A correlated subquery references columns from the outer query and logically re-executes per outer row. Choose correlated subqueries (especially with EXISTS) for existence checks where you need to test a condition per row. Prefer non-correlated subqueries or JOINs for set-based operations, as they're easier to reason about and optimize.

### Q: Explain why `NOT IN` can silently return zero rows and how to avoid it.
**A:** SQL uses three-valued logic (TRUE, FALSE, UNKNOWN). When the subquery list contains NULL, the comparison `x != NULL` yields UNKNOWN, and `FALSE AND UNKNOWN` remains UNKNOWN, so the WHERE clause excludes the row. This means if even one NULL exists in the subquery result, `NOT IN` returns nothing. Always use `NOT EXISTS` instead, or add a `WHERE column IS NOT NULL` filter to the subquery.

### Q: What is a LATERAL join in PostgreSQL and when would you use it over a regular subquery?
**A:** A `LATERAL` join allows a subquery in the FROM clause to reference columns from tables that appear earlier in the FROM list—essentially a correlated derived table. The classic use case is "top-N per group": for each parent row, fetch the N most recent or highest-ranked child rows using LIMIT inside the lateral subquery. This is often more efficient than window functions because it can use an index seek per group rather than scanning the entire child table.

### Q: When should you use a subquery versus a JOIN?
**A:** Use a JOIN when you need columns from both tables in the result set or when you're doing a straightforward relationship traversal—JOINs are the optimizer's bread and butter. Use a subquery when you need existence checks (EXISTS/NOT EXISTS), when a JOIN would cause row duplication (e.g., many-to-many inflating aggregates), or when the logic is naturally hierarchical (e.g., "find rows where X exceeds the average of Y"). In practice, PostgreSQL often rewrites between the two forms internally, so readability and correctness (especially around NULLs) should guide your choice.
