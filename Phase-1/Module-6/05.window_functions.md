# Mastering SQL Window Functions

## 1. Overview
*   **What it is:** Window functions perform calculations across a set of rows related to the current row without collapsing them into a single output row, unlike `GROUP BY` aggregations.
*   **Why it exists:** They solve problems requiring row-level detail alongside aggregate computations—rankings, running totals, comparisons to neighboring rows—without resorting to correlated subqueries or self-joins.
*   **When to use it:** Whenever you need to compute a value that depends on other rows (e.g., rank within a group, cumulative sum, previous row's value) while still returning every individual row.
*   **Common Misconceptions:**
    *   *"Window functions are just another way to GROUP BY"* (False: `GROUP BY` collapses rows; window functions preserve every row and add computed columns alongside them).
    *   *"Window functions can be used in WHERE clauses"* (False: They are evaluated after `WHERE` and `GROUP BY`. To filter on a window function result, wrap it in a CTE or subquery).
    *   *"ORDER BY in OVER() sorts the final result set"* (False: It defines the logical ordering for the window computation only. You need a separate outer `ORDER BY` to sort the final output).

## 2. Core Concepts

### The OVER() Clause and Anatomy of a Window
Every window function uses `OVER()` to define its window. An empty `OVER()` treats the entire result set as one partition. The full syntax is: `function(...) OVER (PARTITION BY ... ORDER BY ... frame_clause)`.

```sql
-- Total salary across entire company alongside each employee's row
SELECT employee_id, department_id, salary,
       SUM(salary) OVER () AS company_total,
       SUM(salary) OVER (PARTITION BY department_id) AS dept_total,
       SUM(salary) OVER (PARTITION BY department_id ORDER BY hire_date) AS dept_running_total
FROM employees;
```

### PARTITION BY and ORDER BY Within Windows
`PARTITION BY` divides rows into independent groups (like `GROUP BY` but without collapsing). `ORDER BY` within `OVER()` defines the sequence for ranking and cumulative functions. Together they form the core of every window expression.

```sql
-- Rank employees within each department by salary (descending)
SELECT employee_id, department_id, salary,
       RANK()       OVER w AS rank,
       DENSE_RANK() OVER w AS dense_rank,
       ROW_NUMBER() OVER w AS row_num
FROM employees
WINDOW w AS (PARTITION BY department_id ORDER BY salary DESC);
```

### Ranking Functions: ROW_NUMBER, RANK, DENSE_RANK, NTILE
`ROW_NUMBER()` assigns a unique sequential integer (no ties). `RANK()` assigns the same number to ties but leaves gaps (1,2,2,4). `DENSE_RANK()` assigns tied values the same rank with no gaps (1,2,2,3). `NTILE(n)` divides rows into `n` roughly equal buckets.

```sql
-- Divide orders into quartiles by amount within each region
SELECT order_id, region, amount,
       NTILE(4) OVER (PARTITION BY region ORDER BY amount DESC) AS quartile
FROM orders;

-- Classic interview pattern: top-N per group using ROW_NUMBER
SELECT * FROM (
    SELECT *, ROW_NUMBER() OVER (PARTITION BY department_id ORDER BY salary DESC) AS rn
    FROM employees
) ranked
WHERE rn <= 3;  -- top 3 earners per department
```

### Offset Functions: LAG, LEAD, FIRST_VALUE, LAST_VALUE, NTH_VALUE
These access values from other rows without self-joins. `LAG(expr, n, default)` looks back `n` rows; `LEAD` looks forward. `FIRST_VALUE` / `LAST_VALUE` return the first/last value in the window frame. `NTH_VALUE(expr, n)` returns the n-th row's value.

```sql
-- Month-over-month revenue change
SELECT month, revenue,
       revenue - LAG(revenue, 1) OVER (ORDER BY month) AS mom_change,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / LAG(revenue) OVER (ORDER BY month), 2) AS mom_pct_change
FROM monthly_revenue;

-- LAST_VALUE requires explicit frame or it only sees up to current row
SELECT employee_id, department_id, salary,
       FIRST_VALUE(salary) OVER w AS highest_in_dept,
       LAST_VALUE(salary)  OVER w AS lowest_in_dept
FROM employees
WINDOW w AS (PARTITION BY department_id ORDER BY salary DESC
             ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING);
```

### Aggregate Window Functions and Frame Clauses
Standard aggregates (`SUM`, `AVG`, `COUNT`, `MIN`, `MAX`) become window functions when paired with `OVER()`. The **frame clause** controls exactly which rows feed the aggregate. `ROWS BETWEEN` operates on physical row offsets; `RANGE BETWEEN` operates on logical value ranges. The default frame when `ORDER BY` is present is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`.

```sql
-- Running total and 7-day moving average
SELECT order_date, daily_amount,
       SUM(daily_amount) OVER (ORDER BY order_date
           ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
       AVG(daily_amount) OVER (ORDER BY order_date
           ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS moving_avg_7d
FROM daily_sales;

-- Count of orders in the surrounding ±2 rows
SELECT order_id, order_date, amount,
       COUNT(*) OVER (ORDER BY order_date
           ROWS BETWEEN 2 PRECEDING AND 2 FOLLOWING) AS nearby_count
FROM orders;
```

### Named Windows (WINDOW Clause) and Reuse
PostgreSQL supports the `WINDOW` clause to define reusable window definitions, reducing duplication and improving readability. A named window can be referenced by multiple window functions and even extended inline.

```sql
SELECT employee_id, department_id, salary,
       SUM(salary)   OVER w AS dept_total,
       AVG(salary)   OVER w AS dept_avg,
       ROW_NUMBER()  OVER (w ORDER BY salary DESC) AS dept_rank  -- extend inline
FROM employees
WINDOW w AS (PARTITION BY department_id);
```

### Practical Pattern: Gap-and-Island Detection
Window functions elegantly solve gap-and-island problems—identifying contiguous sequences in data. The technique subtracts `ROW_NUMBER()` from a sequential value; rows in the same "island" produce the same difference.

```sql
-- Detect consecutive days a server was in 'error' status
WITH numbered AS (
    SELECT log_date, status,
           log_date - (ROW_NUMBER() OVER (ORDER BY log_date))::int AS island_id
    FROM server_logs
    WHERE status = 'error'
)
SELECT MIN(log_date) AS island_start,
       MAX(log_date) AS island_end,
       COUNT(*)       AS consecutive_days
FROM numbered
GROUP BY island_id
ORDER BY island_start;
```

## 3. Best Practices for Lead Engineers

### 1. Mind the Default Frame
When using `ORDER BY` in `OVER()`, the default frame is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`—not the entire partition. This is the #1 source of bugs with `LAST_VALUE()` and aggregate windows. Always specify an explicit frame clause (`ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`) when you need the full partition.

### 2. Use Named Windows for Maintainability
When multiple window functions share the same partitioning or ordering, use `WINDOW w AS (...)` to define it once. This reduces typo risk, makes intent clearer during code review, and simplifies changes when partitioning logic evolves.

### 3. Prefer ROW_NUMBER for Top-N Queries Over LIMIT with Self-Joins
The `ROW_NUMBER() ... WHERE rn <= N` pattern is the canonical way to fetch top-N per group. It is more performant and readable than `LATERAL` joins with `LIMIT` for most cases. Ensure the partitioning column has an index to support the sort.

### 4. Watch for Performance with Large Partitions
Window functions must sort or buffer entire partitions in memory. If a partition contains millions of rows, consider whether a materialized view, partial index, or pre-aggregated table is more appropriate. Check `EXPLAIN ANALYZE` for `Sort` and `WindowAgg` nodes and their memory usage.

## 4. Interview Preparation

### Q: What is the difference between ROW_NUMBER(), RANK(), and DENSE_RANK()?
**A:** All three assign a positional number to rows within a partition. `ROW_NUMBER()` is always unique—ties are broken arbitrarily. `RANK()` gives tied rows the same value but skips subsequent numbers (e.g., 1,2,2,4). `DENSE_RANK()` also handles ties but never skips (1,2,2,3). Use `ROW_NUMBER()` for top-N-per-group deduplication, `RANK()` when you want gap-aware competition-style ranking, and `DENSE_RANK()` when you need contiguous rank values.

### Q: Why does LAST_VALUE() often return the current row's value instead of the partition's last value?
**A:** Because the default window frame with `ORDER BY` is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, which ends at the current row. `LAST_VALUE()` over that frame naturally returns the current row. To get the actual last value in the partition, you must explicitly set the frame to `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING`.

### Q: How would you compute a running total that resets each month?
**A:** Partition by the month (or a truncated date) and order by the date within each partition: `SUM(amount) OVER (PARTITION BY DATE_TRUNC('month', order_date) ORDER BY order_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)`. The `PARTITION BY` resets the accumulation at each month boundary, while `ORDER BY` ensures the cumulative sum proceeds chronologically.

### Q: Explain how you would solve a gap-and-island problem with window functions.
**A:** The classic technique assigns `ROW_NUMBER()` ordered by the sequential column (e.g., date) to each qualifying row. Subtracting the row number from the sequential value produces a constant for contiguous rows—the "island ID." You then `GROUP BY` that island ID to find each island's start, end, and length. This avoids expensive self-joins and runs in O(n log n) due to the sort. Variations use `LAG()` to detect gaps directly and then a cumulative `SUM` of gap flags to assign island identifiers.
