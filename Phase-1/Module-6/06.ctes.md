# Mastering Common Table Expressions (CTEs)

## 1. Overview
*   **What it is:** A CTE (Common Table Expression) is a named, temporary result set defined with a `WITH` clause that exists only for the duration of a single SQL statement.
*   **Why it exists:** CTEs solve the problem of deeply nested subqueries, enable recursive queries for hierarchical data, and allow writable operations (INSERT/UPDATE/DELETE) to be composed within a single statement.
*   **When to use it:** Use CTEs when you need to break a complex query into readable, named steps, traverse hierarchical/graph data recursively, or chain DML operations with `RETURNING`.
*   **Common Misconceptions:**
    *   *"CTEs are always optimization fences in PostgreSQL"* (False: Since PostgreSQL 12, non-recursive CTEs are inlined by default — the optimizer can push predicates into them just like subqueries. Only `MATERIALIZED` CTEs act as optimization fences).
    *   *"Recursive CTEs can only handle trees"* (False: Recursive CTEs can traverse arbitrary graphs, generate series, and solve iterative problems like shortest-path computations — not just parent-child trees).

## 2. Core Concepts

### WITH Clause Syntax and Multiple CTEs
A CTE is introduced by the `WITH` keyword. Multiple CTEs are comma-separated, and later CTEs can reference earlier ones — forming a pipeline of transformations.

```sql
WITH monthly_revenue AS (
    SELECT date_trunc('month', created_at) AS month,
           SUM(amount_cents) / 100.0 AS revenue
    FROM orders
    WHERE status = 'completed'
    GROUP BY 1
),
revenue_with_growth AS (
    SELECT month, revenue,
           LAG(revenue) OVER (ORDER BY month) AS prev_revenue,
           ROUND((revenue - LAG(revenue) OVER (ORDER BY month))
                 / NULLIF(LAG(revenue) OVER (ORDER BY month), 0) * 100, 2) AS growth_pct
    FROM monthly_revenue
)
SELECT month, revenue, growth_pct
FROM revenue_with_growth
WHERE growth_pct IS NOT NULL
ORDER BY month;
```

### CTEs vs Subqueries: Readability and Performance
Subqueries and CTEs produce equivalent results, but CTEs name each logical step. Pre-PostgreSQL 12, CTEs were always materialized (executed once, results stored in a work table), which could hurt performance when the outer query filtered heavily. Post-12, the planner inlines non-recursive CTEs unless you explicitly say `MATERIALIZED`.

```sql
-- Subquery approach: harder to read when nested
SELECT * FROM (
    SELECT user_id, COUNT(*) AS order_count
    FROM orders GROUP BY user_id
) AS oc
WHERE oc.order_count > 10;

-- CTE approach: self-documenting
WITH order_counts AS (
    SELECT user_id, COUNT(*) AS order_count
    FROM orders GROUP BY user_id
)
SELECT * FROM order_counts WHERE order_count > 10;
```

### Materialized vs Not Materialized Hints (PostgreSQL 12+)
You can override the planner's inlining decision. `MATERIALIZED` forces the CTE to execute once and store results — useful when the CTE is referenced multiple times or when you want a deliberate optimization fence. `NOT MATERIALIZED` forces inlining even when the planner wouldn't.

```sql
-- Force materialization: CTE executes once, result reused
WITH active_users AS MATERIALIZED (
    SELECT id, email FROM users
    WHERE last_sign_in_at > NOW() - INTERVAL '30 days'
)
SELECT a.email, o.total
FROM active_users a
JOIN orders o ON o.user_id = a.id
WHERE o.created_at > NOW() - INTERVAL '7 days';

-- Force inlining: planner can push filters into the CTE
WITH recent_orders AS NOT MATERIALIZED (
    SELECT * FROM orders
)
SELECT * FROM recent_orders
WHERE user_id = 42 AND status = 'pending';
```

### Recursive CTEs for Hierarchical Data
`WITH RECURSIVE` defines a CTE with two parts: an anchor (base case) and a recursive term joined by `UNION ALL`. PostgreSQL iterates the recursive term until it produces no new rows. Always include a termination guard (depth limit or cycle detection) in production.

```sql
-- Org chart: find all reports under a manager
WITH RECURSIVE org_tree AS (
    -- Anchor: the top-level manager
    SELECT id, name, manager_id, 1 AS depth
    FROM employees
    WHERE id = 100

    UNION ALL

    -- Recursive: join children to the growing tree
    SELECT e.id, e.name, e.manager_id, ot.depth + 1
    FROM employees e
    JOIN org_tree ot ON e.manager_id = ot.id
    WHERE ot.depth < 20  -- safety limit
)
SELECT id, name, depth FROM org_tree ORDER BY depth, name;

-- Category tree: materialized path construction
WITH RECURSIVE cat_path AS (
    SELECT id, name, parent_id, name::TEXT AS full_path
    FROM categories WHERE parent_id IS NULL

    UNION ALL

    SELECT c.id, c.name, c.parent_id,
           cp.full_path || ' > ' || c.name
    FROM categories c
    JOIN cat_path cp ON c.parent_id = cp.id
)
SELECT id, full_path FROM cat_path ORDER BY full_path;
```

### Writable CTEs (PostgreSQL-Specific)
PostgreSQL allows DML statements (`INSERT`, `UPDATE`, `DELETE`) inside CTEs using `RETURNING`. This lets you chain mutations — archive rows, move data between tables, or implement upsert-then-report patterns in a single atomic statement.

```sql
-- Archive and delete old orders in one atomic statement
WITH archived AS (
    INSERT INTO orders_archive (id, user_id, amount, created_at)
    SELECT id, user_id, amount_cents, created_at
    FROM orders
    WHERE created_at < NOW() - INTERVAL '2 years'
    RETURNING id
),
deleted AS (
    DELETE FROM orders
    WHERE id IN (SELECT id FROM archived)
    RETURNING id
)
SELECT COUNT(*) AS rows_archived FROM deleted;

-- Upsert then return the final state
WITH upserted AS (
    INSERT INTO user_preferences (user_id, key, value)
    VALUES (42, 'theme', 'dark')
    ON CONFLICT (user_id, key)
    DO UPDATE SET value = EXCLUDED.value, updated_at = NOW()
    RETURNING *
)
SELECT * FROM upserted;
```

### CTEs vs Temporary Tables
CTEs exist only within a single statement; temp tables persist for the session (or transaction). Use CTEs for composability and readability. Use temp tables when you need indexes on intermediate results, the result set is large and referenced by multiple separate statements, or you need to `ANALYZE` the intermediate data.

```sql
-- Temp table approach: useful when you need an index on intermediate data
CREATE TEMP TABLE active_subscriptions AS
SELECT user_id, plan_id, expires_at
FROM subscriptions
WHERE status = 'active';

CREATE INDEX ON active_subscriptions (user_id);

-- Now multiple queries can efficiently use this indexed temp table
SELECT * FROM active_subscriptions WHERE user_id = 42;
```

## 3. Best Practices for Lead Engineers

### 1. Default to CTEs for Readability, Profile Before Forcing Materialization
Start with plain CTEs and let PostgreSQL 12+ decide on inlining. Only add `MATERIALIZED` after `EXPLAIN ANALYZE` shows the CTE is being re-evaluated expensively across multiple references or when you deliberately want to isolate planning boundaries.

### 2. Always Guard Recursive CTEs Against Infinite Loops
Add a `depth` counter with a `WHERE depth < N` clause, or use PostgreSQL 14+'s `CYCLE` detection clause (`SEARCH BREADTH FIRST ... SET ... CYCLE ... RESTRICT`). Unbounded recursion on cyclic graphs will exhaust `work_mem` and crash the query.

### 3. Use Writable CTEs for Atomic Multi-Table Mutations
Instead of multi-statement transactions with application-level coordination, use writable CTEs with `RETURNING` to archive-then-delete, insert-then-update, or move data between tables. This guarantees atomicity at the statement level and avoids intermediate visibility issues in long transactions.

## 4. Interview Preparation

### Q: When would you choose a CTE over a subquery, and vice versa?
**A:** CTEs win on readability when a query has multiple logical steps or when the same derived table is referenced more than once — `MATERIALIZED` CTEs compute once and share results. Subqueries are preferable for simple, one-off derivations where inlining is critical for the optimizer to push down predicates, especially on pre-12 PostgreSQL where CTEs were always materialized.

### Q: Explain how recursive CTEs work and how you prevent infinite loops.
**A:** A recursive CTE has an anchor query (base case) `UNION ALL`'d with a recursive term that references the CTE itself. PostgreSQL iterates the recursive term, appending new rows each pass, until no new rows are produced. To prevent infinite loops on cyclic data, add a depth counter (`WHERE depth < N`), maintain a visited-path array (`WHERE NOT id = ANY(path)`), or use PostgreSQL 14's built-in `CYCLE` clause.

### Q: What are writable CTEs and when would you use them in production?
**A:** Writable CTEs allow `INSERT`, `UPDATE`, or `DELETE` statements inside a `WITH` block, using `RETURNING` to pass affected rows downstream. They're ideal for atomic multi-step mutations — e.g., archiving old records into a history table and deleting them from the source in one statement, or performing an upsert and immediately joining the result for a response. All DML in the CTEs executes within a single statement snapshot.

### Q: How does PostgreSQL 12 change CTE behavior, and what do MATERIALIZED / NOT MATERIALIZED do?
**A:** Before PostgreSQL 12, all CTEs were optimization fences — materialized into a temp work table regardless of usage. PostgreSQL 12+ inlines non-recursive CTEs by default, letting the planner push filters and joins into them. `MATERIALIZED` forces the old fence behavior (execute once, store results), useful when referenced multiple times. `NOT MATERIALIZED` forces inlining even when the planner prefers materialization, giving the optimizer full control.
