# Mastering Database Indexes

## 1. Overview
*   **What it is:** An index is a separate data structure (by default a B-tree in PostgreSQL) that maintains a sorted reference to rows in a table, enabling the database to locate data without scanning every row.
*   **Why it exists:** Without indexes, every query must perform a sequential scan of the entire table — indexes reduce lookup time from O(n) to O(log n) for B-trees.
*   **When to use it:** Add indexes on columns frequently used in WHERE clauses, JOIN conditions, and ORDER BY — but only after profiling, since each index adds write overhead and storage cost.
*   **Common Misconceptions:**
    *   *"More indexes always mean faster queries"* (False: Every index must be updated on INSERT, UPDATE, and DELETE — over-indexing can drastically degrade write performance and bloat storage).
    *   *"PostgreSQL always uses an index if one exists"* (False: The query planner may choose a sequential scan if the table is small, the query returns a large percentage of rows, or statistics indicate a seq scan is cheaper).
    *   *"A multi-column index on (a, b) helps queries filtering only on b"* (False: B-tree multi-column indexes follow a leftmost-prefix rule — the index on (a, b) is usable for filters on `a` or `a AND b`, but not `b` alone).

## 2. Core Concepts

### B-Tree Indexes (The Default)
PostgreSQL creates a B-tree index by default. B-trees keep data sorted in a balanced tree structure, supporting equality (`=`) and range queries (`<`, `>`, `BETWEEN`, `LIKE 'prefix%'`) efficiently. Every `PRIMARY KEY` and `UNIQUE` constraint automatically creates a B-tree index.

```sql
-- Explicit B-tree index (default type)
CREATE INDEX idx_orders_customer_id ON orders (customer_id);

-- This is equivalent to:
CREATE INDEX idx_orders_customer_id ON orders USING btree (customer_id);

-- Check what indexes exist on a table
SELECT indexname, indexdef
FROM pg_indexes
WHERE tablename = 'orders';
```

### Single-Column vs Multi-Column Indexes
A single-column index covers one column. A multi-column (composite) index covers multiple columns and is critical for queries that filter or sort on several columns together. Column order matters — place the most selective (highest cardinality) column first, or the column most frequently used in equality conditions.

```sql
-- Multi-column index: optimizes WHERE status = 'shipped' AND created_at > '2026-01-01'
CREATE INDEX idx_orders_status_created ON orders (status, created_at);

-- This index supports:
--   WHERE status = 'shipped'                          ✅ (leftmost prefix)
--   WHERE status = 'shipped' AND created_at > '...'   ✅ (full match)
--   WHERE created_at > '2026-01-01'                   ❌ (skips leading column)

-- Unique index — enforces uniqueness as a constraint
CREATE UNIQUE INDEX idx_users_email ON users (email);
```

### Covering Indexes and Index-Only Scans
An **index-only scan** occurs when all columns needed by a query are present in the index itself — PostgreSQL never touches the heap (table). PostgreSQL 11+ introduced the `INCLUDE` clause to add non-searchable payload columns to an index, making covering indexes explicit without affecting the B-tree sort order.

```sql
-- Covering index: the INCLUDE columns are stored in the index leaf pages
-- but are NOT part of the search key
CREATE INDEX idx_orders_covering ON orders (customer_id)
  INCLUDE (total_amount, status);

-- This enables an index-only scan for:
SELECT total_amount, status FROM orders WHERE customer_id = 42;

-- Verify with EXPLAIN:
EXPLAIN (ANALYZE, BUFFERS) SELECT total_amount, status
FROM orders WHERE customer_id = 42;
-- Look for "Index Only Scan" in the output

-- Important: index-only scans also require the visibility map to be up-to-date.
-- Run VACUUM to ensure the visibility map is current.
```

### Expression Indexes (Functional Indexes)
You can index the result of an expression or function. This is essential when queries filter on transformed values — a regular index on the raw column won't help if the query applies a function to it.

```sql
-- Problem: this query cannot use a standard index on email
SELECT * FROM users WHERE lower(email) = 'alice@example.com';

-- Solution: index the expression
CREATE INDEX idx_users_lower_email ON users (lower(email));

-- Now the planner can use the expression index
EXPLAIN SELECT * FROM users WHERE lower(email) = 'alice@example.com';
-- → Index Scan using idx_users_lower_email

-- Another common use: indexing a JSONB field
CREATE INDEX idx_profiles_city ON profiles ((data->>'city'));
SELECT * FROM profiles WHERE data->>'city' = 'Mumbai';
```

### Partial Indexes
A partial index covers only a subset of rows, reducing index size and write overhead. Use them when queries consistently filter on a known condition.

```sql
-- Only index unshipped orders — much smaller than a full index
CREATE INDEX idx_orders_pending ON orders (created_at)
  WHERE status = 'pending';

-- This index is used only when the query includes the matching predicate:
SELECT * FROM orders WHERE status = 'pending' AND created_at > '2026-09-01';
```

### GIN and GiST Indexes
B-trees are not suitable for every data type. PostgreSQL provides specialized index types:

- **GIN (Generalized Inverted Index):** Best for values that contain multiple elements — full-text search (`tsvector`), arrays, JSONB containment queries. Fast reads, slower writes.
- **GiST (Generalized Search Tree):** Best for geometric, range, and proximity queries. Supports operations like overlaps (`&&`), contains (`@>`), and nearest-neighbor (`<->`).

```sql
-- GIN index for full-text search
CREATE INDEX idx_articles_search ON articles USING gin (to_tsvector('english', body));
SELECT * FROM articles
WHERE to_tsvector('english', body) @@ to_tsquery('english', 'postgresql & indexing');

-- GIN index for JSONB containment
CREATE INDEX idx_events_data ON events USING gin (metadata jsonb_path_ops);
SELECT * FROM events WHERE metadata @> '{"type": "purchase"}';

-- GiST index for range overlap queries
CREATE INDEX idx_reservations_period ON reservations USING gist (during);
SELECT * FROM reservations WHERE during && '[2026-09-01, 2026-09-30]'::daterange;
```

## 3. Best Practices for Lead Engineers

### 1. Profile Before Indexing
Never add indexes speculatively. Use `pg_stat_user_tables` to find tables with high sequential scans (`seq_scan` vs `idx_scan`), and `pg_stat_user_indexes` to identify unused indexes that waste write cycles and storage. Run `EXPLAIN (ANALYZE, BUFFERS)` to confirm the planner's chosen strategy.

### 2. Use Concurrent Index Creation in Production
`CREATE INDEX` takes a full lock on the table, blocking writes. In production, always use `CREATE INDEX CONCURRENTLY` — it builds the index without locking the table for writes, though it takes longer and cannot run inside a transaction.

```sql
-- Safe for production — no write locks
CREATE INDEX CONCURRENTLY idx_orders_customer_id ON orders (customer_id);
```

### 3. Maintain Index Health with REINDEX and pg_stat_user_indexes
Indexes accumulate bloat from updates and deletes. Monitor `pg_stat_user_indexes` for low-usage indexes and periodically run `REINDEX CONCURRENTLY` (PG12+) to rebuild bloated indexes without downtime. Drop unused indexes — each one slows down every INSERT and UPDATE.

### 4. Align Index Strategy with Query Patterns
Design composite indexes to match your most critical query patterns. Place equality columns before range columns (`WHERE status = 'x' AND created_at > '...'` → index `(status, created_at)`). Consider covering indexes for hot read paths to eliminate heap fetches entirely.

## 4. Interview Preparation

### Q: Why might PostgreSQL choose a sequential scan over an index scan, even when an index exists?
**A:** The query planner estimates cost based on table statistics (`pg_statistic`). If the query returns a large fraction of the table (low selectivity), random I/O from an index scan is more expensive than a single sequential pass. Small tables also favor seq scans since they fit in a few pages. Additionally, stale statistics (not running `ANALYZE`) can mislead the planner into wrong estimates.

### Q: What is the difference between an index scan, an index-only scan, and a bitmap index scan?
**A:** An **index scan** traverses the index and fetches each matching row from the heap one by one. An **index-only scan** returns results directly from the index without touching the heap — possible only when all selected columns are in the index and the visibility map confirms tuple visibility. A **bitmap index scan** builds an in-memory bitmap of matching pages from the index, sorts them by physical location, then fetches pages sequentially — this avoids random I/O when many rows match and can combine multiple indexes via BitmapAnd/BitmapOr.

### Q: When would you use a GIN index instead of a B-tree?
**A:** GIN indexes are designed for values that contain multiple elements — arrays, JSONB documents, and `tsvector` for full-text search. A B-tree can only compare scalar values with operators like `=`, `<`, `>`. GIN supports containment (`@>`), overlap (`&&`), and text-search match (`@@`) operators. The trade-off is that GIN indexes are slower to build and update, but significantly faster for these multi-valued lookups. For write-heavy JSONB workloads, consider `jsonb_path_ops` operator class, which is smaller and faster for `@>` queries but doesn't support key-exists checks.

### Q: How does the column order in a composite index affect query performance?
**A:** In a B-tree composite index on `(a, b, c)`, data is sorted first by `a`, then by `b` within each `a` value, then by `c`. The index efficiently supports queries filtering on `a`, `(a, b)`, or `(a, b, c)` — but NOT queries filtering only on `b` or `c` (leftmost prefix rule). For optimal design, place columns used in equality filters before columns used in range filters: `WHERE status = 'active' AND created_at > '2026-01-01'` benefits from `(status, created_at)` but not `(created_at, status)`, because the range on the leading column prevents efficiently narrowing the second column.
