# Mastering Composite Indexes

## 1. Overview
*   **What it is:** A composite (multi-column) index is a single B-tree index built on two or more columns, storing sorted entries based on the combined values of those columns in the order they are defined.
*   **Why it exists:** Many real-world queries filter or sort on multiple columns simultaneously; a composite index satisfies these multi-predicate queries with a single index scan instead of requiring multiple index lookups and merges.
*   **When to use it:** When queries consistently filter, join, or sort on a specific combination of columns—especially when you can order the columns to maximize the number of queries the index serves.
*   **Common Misconceptions:**
    *   *"A composite index on (a, b, c) helps queries that filter only on b or c."* (False: PostgreSQL can only use a composite index efficiently starting from the leftmost column; a query on `b` alone skips the first key and forces a full index scan or seq scan).
    *   *"Two single-column indexes are equivalent to one composite index."* (False: single-column indexes require a BitmapAnd/BitmapOr merge step, which is slower and less efficient than a single composite index scan for multi-column predicates).

## 2. Core Concepts

### Multi-Column Index Syntax
PostgreSQL supports composite indexes on any number of columns. The column order in the definition determines the sort order of the B-tree and which queries can use it.

```sql
-- Basic composite index
CREATE INDEX idx_orders_status_created
    ON orders (status, created_at);

-- With specific sort directions per column
CREATE INDEX idx_orders_status_created_desc
    ON orders (status ASC, created_at DESC);

-- Partial composite index (only index rows matching the WHERE)
CREATE INDEX idx_orders_active_by_date
    ON orders (customer_id, created_at)
    WHERE status = 'active';
```

### The Leftmost Prefix Rule
A composite index on `(a, b, c)` is effectively three indexes in one: it can serve queries on `(a)`, `(a, b)`, or `(a, b, c)`. It **cannot** efficiently serve queries on `(b)`, `(c)`, or `(b, c)` alone because those columns are only sorted within groups of the preceding columns.

```sql
-- Given: CREATE INDEX idx_composite ON orders (status, customer_id, created_at);

-- ✅ Uses index (matches leftmost prefix)
SELECT * FROM orders WHERE status = 'shipped';
SELECT * FROM orders WHERE status = 'shipped' AND customer_id = 42;
SELECT * FROM orders WHERE status = 'shipped' AND customer_id = 42
                       AND created_at > '2026-01-01';

-- ❌ Cannot use index efficiently (skips leftmost column)
SELECT * FROM orders WHERE customer_id = 42;
SELECT * FROM orders WHERE created_at > '2026-01-01';
```

### Equality First, Then Range
The most impactful rule for choosing column order: place columns used with equality (`=`, `IN`) before columns used with range operators (`>`, `<`, `BETWEEN`, `>=`). After a range predicate, subsequent index columns cannot narrow the scan.

```sql
-- Query: find pending orders in a date range
SELECT * FROM orders
WHERE status = 'pending'
  AND created_at BETWEEN '2026-01-01' AND '2026-06-30';

-- ✅ Optimal: equality column first, range column second
CREATE INDEX idx_status_date ON orders (status, created_at);
-- Seeks to status='pending', then scans the date range within that group

-- ❌ Suboptimal: range column first
CREATE INDEX idx_date_status ON orders (created_at, status);
-- Scans the entire date range, then filters status for each row
```

### Composite Index vs Multiple Single-Column Indexes
PostgreSQL can combine single-column indexes via **BitmapAnd** or **BitmapOr**, but this is slower than a single composite index. Bitmap scans build in-memory bitmaps, merge them, then re-read heap pages—adding CPU and I/O overhead.

```sql
-- Two single-column indexes
CREATE INDEX idx_status ON orders (status);
CREATE INDEX idx_date   ON orders (created_at);

-- PostgreSQL plan for: WHERE status = 'pending' AND created_at > '2026-01-01'
-- BitmapAnd
--   -> Bitmap Index Scan on idx_status
--   -> Bitmap Index Scan on idx_date
--   -> Bitmap Heap Scan on orders    ← extra merge + recheck step

-- Single composite index eliminates the merge entirely
CREATE INDEX idx_status_date ON orders (status, created_at);
-- Index Scan using idx_status_date   ← direct, single-pass
```

### Covering Indexes (INCLUDE)
A covering index stores additional non-key columns in the leaf pages so PostgreSQL can answer queries with an **Index Only Scan**, never touching the heap. Use `INCLUDE` for columns that appear in `SELECT` but not in `WHERE` or `ORDER BY`.

```sql
-- The query needs total_amount but only filters on status + date
SELECT status, created_at, total_amount
FROM orders
WHERE status = 'shipped' AND created_at > '2026-01-01';

-- Covering composite index
CREATE INDEX idx_orders_covering
    ON orders (status, created_at)
    INCLUDE (total_amount);

-- Result: Index Only Scan — zero heap fetches (if visibility map is clean)
```

### Practical Design: Multi-Pattern Index Strategy
When a table serves several query patterns, design the fewest composite indexes that cover the most queries by leveraging the leftmost prefix rule.

```sql
-- Pattern 1: WHERE customer_id = ? AND status = ?
-- Pattern 2: WHERE customer_id = ? AND status = ? AND created_at > ?
-- Pattern 3: WHERE customer_id = ? ORDER BY created_at DESC

-- One index serves all three patterns:
CREATE INDEX idx_orders_cust_status_date
    ON orders (customer_id, status, created_at DESC);

-- Pattern 1 → uses prefix (customer_id, status)
-- Pattern 2 → uses full index (customer_id, status, created_at)
-- Pattern 3 → uses prefix (customer_id) + index ordering on created_at DESC

-- Verify with EXPLAIN:
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE customer_id = 100 AND status = 'pending'
  AND created_at > '2026-06-01'
ORDER BY created_at DESC;
```

## 3. Best Practices for Lead Engineers

### 1. Audit Before Adding — Don't Over-Index
Before creating a new composite index, run `pg_stat_user_indexes` to check if existing indexes already cover the query pattern. Every additional index slows down `INSERT`, `UPDATE`, and `DELETE` operations and consumes disk and memory. A well-chosen composite index should serve multiple query patterns via its leftmost prefixes.

### 2. Order Columns by Selectivity Within Equality Predicates
When multiple equality columns exist, place the higher-cardinality column first. If `status` has 5 distinct values and `region` has 50, index `(region, status)` narrows the B-tree search faster. However, always prioritize equality-before-range over cardinality ordering.

### 3. Combine Composite Indexes with Partial Indexes for Hot Paths
For queries that overwhelmingly target a subset of rows (e.g., `status = 'pending'`), a partial composite index dramatically reduces index size and speeds up both reads and writes. A 10M-row orders table with only 50K pending rows benefits enormously from `WHERE status = 'pending'`.

### 4. Monitor Index Usage and Bloat in Production
Use `pg_stat_user_indexes.idx_scan` to identify composite indexes with zero scans—these are dead weight. Schedule `REINDEX CONCURRENTLY` for bloated composite indexes whose size has grown far beyond the live tuple count, especially after bulk deletes.

## 4. Interview Preparation

### Q: How does the leftmost prefix rule work, and what happens if a query skips the first column of a composite index?
**A:** A composite B-tree on `(a, b, c)` sorts by `a` first, then `b` within each `a` group, then `c` within each `(a, b)` group. If a query filters only on `b`, the planner cannot seek to a specific position because `b` values are scattered across different `a` groups. PostgreSQL may fall back to a full index scan (reading every entry) or choose a sequential table scan instead, making the index useless for that query.

### Q: Why should equality columns come before range columns in a composite index?
**A:** Equality predicates (`=`, `IN`) pin the index to a specific branch of the B-tree, allowing subsequent columns to further narrow the scan. A range predicate (`>`, `BETWEEN`) opens up a span of entries; any columns after the range column cannot be used to skip entries—they can only be evaluated as filters on each row within that span. Placing equality columns first maximizes the portion of the index that actively narrows results.

### Q: When would you prefer multiple single-column indexes over a single composite index?
**A:** When queries use the columns independently in various combinations that share no common leftmost prefix. For example, if some queries filter only on `status` and others filter only on `region` with no overlap, two single-column indexes are better because no single composite ordering serves both. PostgreSQL can still combine them via BitmapAnd when both predicates appear, though this is slower than a purpose-built composite index.

### Q: How do covering indexes interact with composite indexes, and what is the trade-off?
**A:** Adding `INCLUDE` columns to a composite index turns it into a covering index, enabling Index Only Scans that avoid heap fetches entirely. The trade-off is increased index size—every leaf page stores the extra columns—which means more disk, more memory pressure on `shared_buffers`, and slower writes. Use `INCLUDE` only for columns frequently selected alongside the indexed predicates, and validate the benefit with `EXPLAIN (ANALYZE, BUFFERS)` to confirm heap fetches drop to zero.
