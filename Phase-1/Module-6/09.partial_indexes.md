# Mastering Partial Indexes

## 1. Overview
*   **What it is:** A partial index is an index built over a subset of rows in a table, defined by a `WHERE` predicate on the `CREATE INDEX` statement.
*   **Why it exists:** Full indexes on large tables waste storage and I/O on rows that queries never filter by — partial indexes eliminate that overhead by indexing only the rows that matter.
*   **When to use it:** When your queries consistently target a small, well-defined subset of a table (e.g., active users, unprocessed jobs, non-null values).
*   **Common Misconceptions:**
    *   *"A partial index speeds up any query on the indexed column."* (False: The planner will only use a partial index when the query's `WHERE` clause logically implies the index predicate — a mismatch means a sequential scan or a different index).
    *   *"Partial indexes are just smaller regular indexes."* (False: They fundamentally change which queries can use them and enable conditional uniqueness constraints that regular indexes cannot express).

## 2. Core Concepts

### CREATE INDEX ... WHERE Syntax
A partial index adds a `WHERE` clause to a standard `CREATE INDEX` statement. Only rows satisfying the predicate are included in the index. The predicate can use any immutable expression — comparisons, `IS NOT NULL`, `IN` lists, boolean columns, etc.
```sql
-- Only index orders that haven't shipped yet
CREATE INDEX idx_orders_pending ON orders (created_at)
  WHERE status = 'pending';

-- Only index non-null email addresses
CREATE INDEX idx_users_email_present ON users (email)
  WHERE email IS NOT NULL;
```

### Use Cases: Indexing Subsets
Partial indexes shine when a column's value distribution is heavily skewed. Indexing the minority subset keeps the index small, fast to update, and cache-friendly.
```sql
-- Active records: only 5% of accounts are active
CREATE INDEX idx_active_accounts ON accounts (last_login_at)
  WHERE active = true;

-- Rare conditions: only 0.1% of transactions are flagged
CREATE INDEX idx_flagged_txns ON transactions (flagged_at)
  WHERE is_flagged = true;
```

### Size Savings vs. Full Indexes
A partial index stores entries only for matching rows. On a 100M-row table where 2% match the predicate, the partial index is roughly 50x smaller than a full index — consuming less disk, less WAL traffic on writes, and staying resident in shared_buffers far more effectively.
```sql
-- Compare sizes
SELECT pg_size_pretty(pg_relation_size('idx_orders_pending'))   AS partial_size,
       pg_size_pretty(pg_relation_size('idx_orders_created_at')) AS full_size;
-- Example output: partial_size = '12 MB', full_size = '580 MB'
```

### Query Planner Interaction
PostgreSQL will only consider a partial index when it can prove that the query's `WHERE` clause **implies** the index predicate. The match must be exact or logically entailed — paraphrasing or equivalent expressions may not be recognised.
```sql
-- This query WILL use idx_orders_pending (predicate matches exactly)
SELECT * FROM orders WHERE status = 'pending' AND created_at > now() - interval '1 day';

-- This query will NOT use idx_orders_pending (different predicate)
SELECT * FROM orders WHERE status IN ('pending', 'shipped') AND created_at > now() - interval '1 day';

-- Tip: EXPLAIN to verify
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE status = 'pending' ORDER BY created_at LIMIT 10;
```

### Combining Partial and Composite Indexes
You can create multi-column partial indexes that serve highly targeted queries. This stacks selectivity from the predicate with selectivity from the composite key.
```sql
-- Composite partial index for admin dashboard: only unprocessed jobs, sorted by priority then created_at
CREATE INDEX idx_jobs_unprocessed_priority ON jobs (priority DESC, created_at ASC)
  WHERE processed_at IS NULL;

-- The planner uses this for:
SELECT * FROM jobs
  WHERE processed_at IS NULL
  ORDER BY priority DESC, created_at ASC
  LIMIT 50;
```

### Unique Partial Indexes for Conditional Uniqueness
A `UNIQUE` partial index enforces uniqueness only among the rows matching the predicate. This is the idiomatic PostgreSQL way to express conditional unique constraints — something `UNIQUE` constraints alone cannot do.
```sql
-- Each user may have only one active subscription at a time
CREATE UNIQUE INDEX idx_one_active_sub ON subscriptions (user_id)
  WHERE status = 'active';

-- This allows multiple cancelled rows for the same user_id,
-- but INSERT of a second active row raises a unique violation.
INSERT INTO subscriptions (user_id, status) VALUES (42, 'active');
-- ERROR: duplicate key value violates unique constraint "idx_one_active_sub"
```

## 3. Best Practices for Lead Engineers

### 1. Match Predicates Exactly in Application Queries
Document the partial index predicate alongside the queries that use it. If a future developer changes `WHERE status = 'pending'` to `WHERE status != 'completed'`, the index silently stops being used. Add a comment on the migration and consider an `EXPLAIN` regression test.

### 2. Prefer Boolean or Enum Predicates Over Ranges
Predicates like `WHERE active = true` or `WHERE status = 'pending'` are stable and unambiguous for the planner. Range predicates (`WHERE created_at > '2024-01-01'`) work but become stale — you'd need to recreate the index as the boundary shifts, making them poor candidates for long-lived partial indexes.

### 3. Monitor Partial Index Bloat Separately
Partial indexes on volatile subsets (e.g., unprocessed jobs) see intense churn — rows enter and leave the predicate frequently. Schedule targeted `REINDEX CONCURRENTLY` for these indexes more aggressively than for stable full indexes, and monitor their size relative to the expected row count.

## 4. Interview Preparation

### Q: When would you choose a partial index over a full index?
**A:** When queries consistently target a small, well-defined subset of rows — e.g., only active records, unprocessed jobs, or non-null values. A partial index on that subset is drastically smaller, cheaper to maintain on writes, and more likely to fit in memory, while providing the same lookup speed for those specific queries.

### Q: What happens if the query's WHERE clause doesn't exactly match the partial index predicate?
**A:** PostgreSQL's planner will not use the partial index. The match must be logically implied — identical or a stricter subset of the predicate. For example, an index with `WHERE status = 'pending'` won't be used by a query filtering `WHERE status IN ('pending', 'shipped')`, because the query's condition is broader than the index predicate. Always verify with `EXPLAIN`.

### Q: How do you enforce "only one active subscription per user" in PostgreSQL?
**A:** Use a unique partial index: `CREATE UNIQUE INDEX ON subscriptions (user_id) WHERE status = 'active'`. This allows unlimited cancelled or expired rows per user but raises a unique violation if a second active row is inserted. This is more flexible than a full unique constraint and avoids the need for application-level locking or triggers.

### Q: A background job queue table has 50M rows but only ~10K are unprocessed at any time. How do you optimize polling queries?
**A:** Create a partial index like `CREATE INDEX ON job_queue (priority DESC, created_at) WHERE completed_at IS NULL`. The index covers only the ~10K unprocessed rows, making it tiny and fast. The polling query `SELECT * FROM job_queue WHERE completed_at IS NULL ORDER BY priority DESC, created_at LIMIT 100` does an index-only or index scan over a structure that fits entirely in cache, regardless of how many millions of completed rows exist.
