# Mastering the PostgreSQL Query Planner

## 1. Overview
*   **What it is:** The query planner (optimizer) is the component of PostgreSQL that examines all possible ways to execute a SQL query and chooses the plan with the lowest estimated cost.
*   **Why it exists:** A single query can be executed via dozens of different strategies (different join orders, scan types, sort methods); the planner automates picking the fastest one so developers don't have to hand-optimize every query.
*   **When to use it:** You interact with the planner every time you run a query — understanding it becomes critical when diagnosing slow queries, choosing indexes, or tuning PostgreSQL configuration.
*   **Common Misconceptions:**
    *   *"The planner always picks the best plan."* (False: The planner relies on **statistics** and a **cost model** — stale stats, skewed data, or misconfigured cost parameters lead it to choose suboptimal plans.)
    *   *"Adding an index always makes queries faster."* (False: The planner may ignore an index if the table is small, selectivity is low, or `random_page_cost` makes index access look expensive relative to a sequential scan.)
    *   *"EXPLAIN shows actual execution time."* (False: Plain `EXPLAIN` shows **estimated** costs only; you need `EXPLAIN ANALYZE` to see actual row counts and timings.)

## 2. Core Concepts

### Cost-Based Optimization
PostgreSQL uses a cost-based optimizer (CBO). It assigns a numeric "cost" (in arbitrary units roughly corresponding to disk page fetches) to every possible plan and picks the cheapest one. The cost has two components: **startup cost** (time before the first row is returned) and **total cost** (time to return all rows).

```sql
-- Reading a query plan: (startup_cost..total_cost)
EXPLAIN SELECT * FROM orders WHERE total > 100;
-- Seq Scan on orders  (cost=0.00..1520.00 rows=5000 width=48)
--   Filter: (total > 100)

-- The planner estimated 5000 rows, total cost 1520 cost units
```

### Scan Strategies
The planner chooses between several table-access methods based on selectivity, table size, and available indexes.

| Scan Type | When Chosen | Characteristics |
|---|---|---|
| **Sequential Scan** | Low selectivity or small table | Reads every page in order; cheap I/O but processes all rows |
| **Index Scan** | High selectivity (few rows) | Follows index pointers to heap pages; random I/O per row |
| **Bitmap Index Scan** | Medium selectivity | Builds a bitmap of matching pages, then reads them sequentially; combines benefits of both |
| **Index-Only Scan** | All needed columns are in the index and visibility map is current | Never touches the heap; fastest possible scan |

```sql
-- Force the planner to show different scan plans by adjusting selectivity
EXPLAIN ANALYZE SELECT * FROM orders WHERE id = 42;
-- Index Scan using orders_pkey on orders (actual time=0.02..0.03 rows=1)

EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'pending';
-- Bitmap Heap Scan on orders (actual time=1.2..15.4 rows=12000)
--   -> Bitmap Index Scan on idx_orders_status (actual time=0.8..0.8 rows=12000)

-- Index-only scan when the index covers all selected columns
EXPLAIN ANALYZE SELECT id FROM orders WHERE id BETWEEN 1 AND 100;
-- Index Only Scan using orders_pkey on orders (actual time=0.02..0.05 rows=100)
```

### Join Strategies
PostgreSQL supports three physical join algorithms. The planner picks one based on table sizes, available indexes, and join selectivity.

```sql
-- Nested Loop: best for small outer table or indexed inner table
-- Hash Join: best for large unsorted tables with equi-joins
-- Merge Join: best when both inputs are pre-sorted or can use index ordering

EXPLAIN ANALYZE
SELECT o.id, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at > '2026-01-01';

-- Possible plans:
-- Hash Join  (cost=200..5000 rows=15000)
--   Hash Cond: (o.customer_id = c.id)
--   -> Seq Scan on orders (filter on created_at)
--   -> Hash -> Seq Scan on customers
```

### Sort Strategies and Work Memory
PostgreSQL uses **quicksort** when the data fits in `work_mem`, and falls back to **external merge sort** (disk-based) when it doesn't. The `EXPLAIN ANALYZE` output tells you which was used.

```sql
-- Check which sort method was chosen
SET work_mem = '4MB';
EXPLAIN ANALYZE SELECT * FROM orders ORDER BY created_at;
-- Sort (actual time=120..145 rows=500000)
--   Sort Key: created_at
--   Sort Method: external merge  Disk: 35000kB   <-- exceeded work_mem

SET work_mem = '64MB';
EXPLAIN ANALYZE SELECT * FROM orders ORDER BY created_at;
-- Sort Method: quicksort  Memory: 42000kB          <-- fit in memory
```

### The Cost Model
The planner's cost estimates are driven by configurable constants that reflect your hardware characteristics.

| Parameter | Default | Meaning |
|---|---|---|
| `seq_page_cost` | 1.0 | Cost of reading one page sequentially |
| `random_page_cost` | 4.0 | Cost of reading one page randomly (seeks) |
| `cpu_tuple_cost` | 0.01 | Cost of processing one row |
| `cpu_index_tuple_cost` | 0.005 | Cost of processing one index entry |
| `cpu_operator_cost` | 0.0025 | Cost of evaluating one operator/function |
| `effective_cache_size` | 4GB | Planner's estimate of OS + PostgreSQL cache available |

```sql
-- On SSDs, random reads are nearly as fast as sequential reads
-- Lowering random_page_cost encourages index usage
SET random_page_cost = 1.1;   -- SSD-tuned (default 4.0 assumes spinning disk)
SET seq_page_cost = 1.0;

-- effective_cache_size doesn't allocate memory — it tells the planner
-- how much data is likely cached, influencing index vs seq scan decisions
SET effective_cache_size = '16GB';
```

### Statistics and pg_stats
The planner depends on table statistics collected by `ANALYZE`. These statistics live in `pg_statistic` (internal) and are readable via the `pg_stats` view.

```sql
-- Key columns in pg_stats:
SELECT tablename, attname, null_frac, avg_width, n_distinct,
       most_common_vals, most_common_freqs, histogram_bounds
FROM pg_stats
WHERE tablename = 'orders' AND attname = 'status';

-- n_distinct: estimated number of distinct values (-1 means unique)
-- null_frac: fraction of NULL values
-- most_common_vals / most_common_freqs: top values and their frequencies
-- histogram_bounds: equal-frequency histogram for range estimates

-- Refresh statistics after bulk operations
ANALYZE orders;

-- Increase statistics granularity for a skewed column (default target: 100)
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;
ANALYZE orders;
```

## 3. Best Practices for Lead Engineers

### 1. Keep Statistics Fresh
Run `ANALYZE` after bulk loads, large deletes, or schema changes. Configure `autovacuum` aggressively on high-churn tables — the planner is only as good as its statistics. Set higher `default_statistics_target` (e.g., 500) on columns with skewed distributions.

### 2. Tune Cost Parameters for Your Hardware
The default `random_page_cost = 4.0` assumes spinning disks. On SSDs, set it to `1.1–1.5` to stop the planner from unnecessarily avoiding indexes. Set `effective_cache_size` to roughly 75% of total system RAM so the planner accurately estimates cache hit rates.

### 3. Use EXPLAIN (ANALYZE, BUFFERS, FORMAT YAML) for Diagnosis
Always use `EXPLAIN (ANALYZE, BUFFERS)` — not just `EXPLAIN` — when debugging. The `BUFFERS` option shows shared/local block hits vs reads, revealing whether slowness is from I/O or computation. Compare estimated rows to actual rows; large discrepancies indicate stale or insufficient statistics.

### 4. Don't Fight the Planner — Fix the Inputs
Avoid session-level `enable_seqscan = off` hacks in production. Instead, fix the root cause: update statistics, add the right index, rewrite the query to be more planner-friendly, or adjust cost parameters. The planner usually makes good decisions when given accurate information.

## 4. Interview Preparation

### Q: How does PostgreSQL decide between a sequential scan and an index scan?
**A:** The planner estimates the total cost of each approach using its cost model. A sequential scan reads all pages in order (cheap per-page I/O at `seq_page_cost`) but processes every row. An index scan does random I/O (`random_page_cost`, typically 4× higher) but reads fewer pages. When selectivity is high (few matching rows), the index scan wins; when a large fraction of the table matches, the sequential scan's lower per-page cost makes it cheaper overall. Table size, `effective_cache_size`, and correlation (physical row ordering) also factor in.

### Q: What is a Bitmap Index Scan and when does PostgreSQL use it?
**A:** A Bitmap Index Scan is a two-phase approach: first, PostgreSQL scans the index and builds an in-memory bitmap of which heap pages contain matching rows. Then it performs a Bitmap Heap Scan, reading those pages in physical order (sequential I/O). This is chosen for medium-selectivity queries — too many rows for an index scan (which would cause excessive random I/O) but too few for a full sequential scan. It also enables combining multiple indexes via BitmapAnd/BitmapOr operations.

### Q: When does the planner make wrong decisions, and how do you fix it?
**A:** The planner makes wrong decisions primarily due to: (1) **stale statistics** — fix with `ANALYZE` or increasing `default_statistics_target`; (2) **correlated columns** — the planner assumes column independence, so `WHERE city = 'NYC' AND state = 'NY'` underestimates rows — fix with extended statistics (`CREATE STATISTICS`); (3) **misconfigured cost parameters** — e.g., `random_page_cost = 4.0` on SSDs penalizes index usage — fix by tuning to match hardware; (4) **parameterized queries** with highly skewed distributions — the generic plan may be wrong for specific values — fix with plan invalidation or query restructuring.

### Q: Explain the three join strategies and when each is optimal.
**A:** **Nested Loop** iterates through each row of the outer table and probes the inner table (ideally via an index); it's best when the outer table is small or the inner side has a fast index lookup. **Hash Join** builds a hash table from the smaller relation and probes it with the larger one; it's optimal for large equi-joins without useful indexes but requires memory (`work_mem`). **Merge Join** sorts both inputs (or uses pre-sorted index output) and merges them; it excels when both sides are already sorted or the result must be sorted, and it handles large datasets well since it can stream from disk.
