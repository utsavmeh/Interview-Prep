# Mastering EXPLAIN ANALYZE

## 1. Overview
*   **What it is:** PostgreSQL's query introspection tools (`EXPLAIN` and `EXPLAIN ANALYZE`) that reveal the execution plan the planner chooses and, optionally, the actual runtime statistics of executing the query.
*   **Why it exists:** Without visibility into how the database executes a query, you cannot diagnose performance problems — you're guessing instead of measuring.
*   **When to use it:** Whenever a query is slower than expected, when validating that an index is being used, or when reviewing any query that touches production-scale data.
*   **Common Misconceptions:**
    *   *"`EXPLAIN` and `EXPLAIN ANALYZE` are the same thing."* (False: `EXPLAIN` only shows the planner's *estimated* plan without executing the query. `EXPLAIN ANALYZE` actually **runs** the query and reports real timings and row counts alongside the estimates.)
    *   *"EXPLAIN ANALYZE is safe on any query."* (False: It **executes** the statement. Running `EXPLAIN ANALYZE DELETE FROM orders;` will delete your data. Always wrap mutating statements in a transaction you roll back: `BEGIN; EXPLAIN ANALYZE DELETE ...; ROLLBACK;`.)

## 2. Core Concepts

### EXPLAIN vs EXPLAIN ANALYZE
`EXPLAIN` asks the planner to show its chosen plan *without* running it. `EXPLAIN ANALYZE` runs the query and annotates each node with actual execution time and row counts. Use `EXPLAIN` for safe inspection; use `EXPLAIN ANALYZE` when you need ground-truth numbers.

```sql
-- Estimated plan only (query is NOT executed)
EXPLAIN SELECT * FROM orders WHERE customer_id = 42;

-- Actual execution (query IS executed, results discarded)
EXPLAIN ANALYZE SELECT * FROM orders WHERE customer_id = 42;
```

### Reading Execution Plan Nodes
Every plan is a tree of *nodes*. Each node shows: the operation type, **startup cost..total cost** (in arbitrary planner cost units), **rows** (estimated rows produced), and **width** (average row width in bytes). With `ANALYZE`, you also see **actual time** (ms for first row..all rows), **rows** (actual count), and **loops** (how many times the node executed).

```
Index Scan using idx_orders_customer_id on orders
    (cost=0.43..8.45 rows=5 width=64)
    (actual time=0.021..0.035 rows=7 loops=1)
```
Key insight: multiply `actual time` and `rows` by `loops` to get true totals for nodes inside nested loops.

### Scan Nodes
**Seq Scan** reads every row in the table — fine for small tables or when selecting a large fraction of rows, but a red flag on large tables with selective filters. **Index Scan** traverses the B-tree index and fetches heap tuples one by one — optimal for highly selective queries. **Bitmap Heap Scan** (preceded by a Bitmap Index Scan) builds an in-memory bitmap of matching pages, then reads them in physical order — PostgreSQL's middle ground when too many rows for an Index Scan but too few for a Seq Scan.

```sql
-- Force comparison to understand planner choices
SET enable_seqscan = off;  -- temporarily discourage seq scans
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'pending';
RESET enable_seqscan;
```

### Join Nodes
**Nested Loop**: For each row in the outer relation, scans the inner relation. Best when the outer side is small and an index exists on the inner join column. **Hash Join**: Builds a hash table from the smaller relation, then probes it with rows from the larger relation. Excellent for equi-joins on larger datasets that fit in `work_mem`. **Merge Join**: Requires both inputs sorted on the join key; then merges them in a single pass. Ideal when inputs are already sorted (e.g., via index) or when datasets are very large.

```sql
-- Observe join strategy chosen by planner
EXPLAIN ANALYZE
SELECT o.id, c.name
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at > '2025-01-01';
```

### Sort Nodes and work_mem
A **Sort** node appears when the planner needs ordered output (for `ORDER BY`, merge joins, or `DISTINCT`). If the dataset fits in `work_mem`, PostgreSQL uses an in-memory quicksort. If it exceeds `work_mem`, it spills to disk (shown as `Sort Method: external merge Disk: XXkB`) — a major performance hit.

```sql
-- Check if sorts spill to disk
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders ORDER BY created_at;
-- Look for: Sort Method: quicksort  Memory: 25kB   (good)
-- vs:       Sort Method: external merge  Disk: 4096kB (bad)
```

### BUFFERS and FORMAT Options
`EXPLAIN (ANALYZE, BUFFERS)` adds I/O statistics: **shared hit** (pages found in buffer cache), **shared read** (pages fetched from disk), **shared written**, and temp read/written. This is the single most important option for diagnosing I/O-bound queries. `FORMAT JSON` outputs machine-readable plans for visualization tools.

```sql
-- Full diagnostic query
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders WHERE total > 500 ORDER BY created_at DESC LIMIT 100;

-- JSON output for tools like explain.dalibo.com
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)
SELECT * FROM orders WHERE total > 500 ORDER BY created_at DESC LIMIT 100;
```

## 3. Best Practices for Lead Engineers

### 1. Always Use BUFFERS with ANALYZE
Raw timing alone hides whether slowness comes from CPU or I/O. `BUFFERS` reveals cache hit ratios per node. A node with high `shared read` relative to `shared hit` indicates cold cache or poor access patterns — critical for understanding production behavior vs. warm-cache benchmarks.

### 2. Watch for Row Estimate Mismatches
When `estimated rows` and `actual rows` diverge by 10x or more, the planner is working with stale or missing statistics. Run `ANALYZE table_name;` to refresh stats. For columns with skewed distributions, consider increasing `default_statistics_target` or creating extended statistics with `CREATE STATISTICS`.

### 3. Establish EXPLAIN ANALYZE in Code Review Culture
Require `EXPLAIN ANALYZE` output for any new query touching large tables in pull requests. Use `auto_explain` module in staging to log plans for queries exceeding a threshold (`auto_explain.log_min_duration = '100ms'`). This catches regressions before they reach production.

### 4. Use Visualization Tools for Complex Plans
Paste JSON-formatted plans into [explain.dalibo.com](https://explain.dalibo.com) or pgAdmin's graphical explain viewer. These tools color-code expensive nodes, highlight row-estimate mismatches, and make deeply nested plans readable at a glance — far more effective than reading raw text for plans with 20+ nodes.

## 4. Interview Preparation

### Q: How do you diagnose a slow query in PostgreSQL?
**A:** Start with `EXPLAIN (ANALYZE, BUFFERS)` to get the actual execution plan with I/O stats. Look for nodes consuming the most time, check if estimated vs. actual rows diverge (indicating stale statistics), identify sequential scans on large tables that should use indexes, and check for disk-based sorts. If stats are stale, run `ANALYZE`; if an index is missing, create one; if sorts spill to disk, consider increasing `work_mem` for that session.

### Q: What's the difference between an Index Scan and a Bitmap Heap Scan?
**A:** An Index Scan traverses the B-tree and fetches each matching heap tuple individually — optimal when very few rows match. A Bitmap Heap Scan first builds an in-memory bitmap of all matching TIDs via a Bitmap Index Scan, then reads heap pages in physical order — this avoids random I/O when many rows match across many pages. The planner switches from Index Scan to Bitmap Heap Scan as selectivity decreases, and eventually to Seq Scan when a large enough fraction of the table is needed.

### Q: What does it mean when estimated rows and actual rows are very different?
**A:** It means the planner's statistics are inaccurate for that filter condition. This leads to suboptimal plan choices — for example, choosing a Nested Loop when a Hash Join would be faster, or vice versa. Common causes include stale statistics (fix with `ANALYZE`), correlated columns the planner treats as independent (fix with `CREATE STATISTICS` for extended statistics), or filtering on expressions that lack statistics. Fixing the estimate mismatch often fixes the performance problem automatically.

### Q: When would you see a Hash Join vs. a Merge Join vs. a Nested Loop?
**A:** The planner chooses **Nested Loop** when one side is very small (often after an index lookup returns few rows) and the inner side can be scanned efficiently per iteration. **Hash Join** is chosen for equi-joins on larger datasets — it builds a hash table on the smaller relation (must fit in `work_mem`). **Merge Join** is chosen when both inputs are already sorted on the join key (e.g., from an index) or when the dataset is too large for a hash table. If a Hash Join spills to disk (indicated by `Batches: N` where N > 1), increasing `work_mem` may help.
