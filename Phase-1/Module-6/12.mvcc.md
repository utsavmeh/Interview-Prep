# Mastering MVCC (Multi-Version Concurrency Control)

## 1. Overview
*   **What it is:** MVCC is a concurrency control mechanism where every write (INSERT, UPDATE, DELETE) creates a new version of a row rather than overwriting it in place, allowing multiple transactions to see consistent snapshots of data simultaneously.
*   **Why it exists:** It solves the fundamental conflict between readers and writers — without MVCC, a SELECT would need to acquire a lock and wait for any concurrent UPDATE to finish (or vice versa), destroying throughput under concurrent workloads.
*   **When to use it:** MVCC is not something you "choose" to use — it is PostgreSQL's foundational concurrency architecture. Understanding it is critical for diagnosing bloat, debugging visibility issues, and tuning VACUUM.
*   **Common Misconceptions:**
    *   *"UPDATE modifies a row in place."* (False: PostgreSQL creates an entirely new tuple on the heap; the old version remains until VACUUM removes it.)
    *   *"DELETE immediately frees disk space."* (False: DELETE only marks the tuple as dead by writing an `xmax`; physical removal is deferred to VACUUM.)
    *   *"MVCC eliminates all locking."* (False: MVCC eliminates read/write conflicts, but write/write conflicts still require row-level locks.)

## 2. Core Concepts

### Transaction IDs (XIDs) and Tuple Headers
Every transaction in PostgreSQL is assigned a monotonically increasing 32-bit transaction ID (`xid`). Each tuple (physical row) carries two critical header fields: `xmin` (the xid of the transaction that created this tuple version) and `xmax` (the xid of the transaction that deleted or replaced it — zero if still live). These headers are how PostgreSQL determines which tuple versions are visible to which transactions.

```sql
-- Inspect the hidden system columns on any table
SELECT xmin, xmax, ctid, * FROM orders WHERE id = 42;

--  xmin  | xmax | ctid  | id |  status
-- -------+------+-------+----+----------
--  10500 |    0 | (0,1) | 42 | pending    ← created by txn 10500, not yet deleted
```

### How UPDATE Creates a New Tuple Version
When you UPDATE a row, PostgreSQL does NOT modify the existing tuple. Instead it: (1) writes a new tuple with the updated values and a new `xmin` set to the current transaction's xid, (2) sets the `xmax` of the **old** tuple to the current transaction's xid, effectively marking it as "replaced," and (3) adds a pointer from the old tuple to the new one via the tuple's `ctid` chain (HOT chains when possible).

```sql
BEGIN;  -- assigned xid = 10600

UPDATE orders SET status = 'shipped' WHERE id = 42;
-- Old tuple (0,1): xmin=10500, xmax=10600  (now "dead" to future txns)
-- New tuple (0,5): xmin=10600, xmax=0       (the live version)

COMMIT;

-- After commit, any new transaction sees only the (0,5) version.
-- The old (0,1) version is invisible but still physically on disk.
```

### How DELETE Marks Tuples Dead
DELETE works identically to the first half of UPDATE — it sets `xmax` on the target tuple to the current transaction's xid. No new tuple is created. The tuple remains physically on the heap page until VACUUM reclaims it.

```sql
BEGIN;  -- assigned xid = 10700
DELETE FROM orders WHERE id = 42;
-- Tuple (0,5): xmin=10600, xmax=10700
COMMIT;

-- The tuple is now invisible to all new transactions,
-- but it still occupies space on disk → "dead tuple" / "bloat"
```

### Tuple Visibility Rules and Snapshots
When a transaction starts (under READ COMMITTED or REPEATABLE READ), PostgreSQL takes a **snapshot** — a record of which transactions are committed, in-progress, or aborted at that moment. A tuple is visible to a transaction if: (1) `xmin` is committed AND is in the snapshot's "committed" set, AND (2) `xmax` is either zero, belongs to an aborted transaction, or belongs to a transaction not yet visible in the snapshot.

```sql
-- Transaction A (xid=10800, READ COMMITTED)
BEGIN;
SELECT * FROM orders WHERE id = 100;  -- snapshot taken, sees xmin=10750 version

    -- Transaction B (xid=10810) concurrently:
    -- UPDATE orders SET status='cancelled' WHERE id = 100;
    -- COMMIT;  → old tuple gets xmax=10810, new tuple xmin=10810

-- Transaction A re-runs (READ COMMITTED takes a NEW snapshot per statement):
SELECT * FROM orders WHERE id = 100;  -- now sees the xmin=10810 version

-- Under REPEATABLE READ, Transaction A would still see the xmin=10750
-- version for its entire lifetime — same snapshot throughout.
```

### The Role of VACUUM
Dead tuples accumulate over time, causing **table bloat** — wasted disk space and slower sequential scans. VACUUM's job is to: (1) identify tuples where `xmax` is set and the deleting transaction has committed and is no longer visible to ANY active snapshot, (2) mark those tuple slots as reusable in the **Free Space Map (FSM)**, and (3) optionally freeze old `xmin` values to prevent transaction ID wraparound.

```sql
-- Check dead tuple accumulation
SELECT relname, n_dead_tup, n_live_tup,
       last_vacuum, last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'orders';

-- Manual VACUUM (non-blocking, reclaims space for reuse)
VACUUM orders;

-- VACUUM FULL rewrites the entire table to reclaim disk space
-- but requires an ACCESS EXCLUSIVE lock — avoid in production
VACUUM FULL orders;

-- Tune autovacuum for high-churn tables
ALTER TABLE orders SET (
    autovacuum_vacuum_scale_factor = 0.05,   -- trigger at 5% dead tuples (default 20%)
    autovacuum_vacuum_cost_delay = 2         -- be more aggressive
);
```

## 3. Best Practices for Lead Engineers

### 1. Tune Autovacuum Aggressively for High-Write Tables
The default autovacuum settings (20% dead tuple threshold) are too conservative for large, frequently updated tables. A 100M-row table won't trigger autovacuum until 20M rows are dead. Set per-table `autovacuum_vacuum_scale_factor` to 0.01–0.05 for hot tables, and monitor `n_dead_tup` in `pg_stat_user_tables`.

### 2. Avoid Long-Running Transactions
A transaction that stays open for hours holds its snapshot alive, preventing VACUUM from reclaiming ANY tuples deleted after that snapshot was taken. This is the single most common cause of catastrophic table bloat. Use `idle_in_transaction_session_timeout` to kill stale sessions.

### 3. Understand HOT Updates to Reduce Bloat
Heap-Only Tuple (HOT) updates avoid creating a new index entry when the updated columns are not indexed and the new tuple fits on the same heap page. Design your indexes carefully — every indexed column that changes forces a full (non-HOT) update, doubling index bloat.

### 4. Monitor for Transaction ID Wraparound
PostgreSQL's 32-bit xid space (~4 billion) wraps around. If a table isn't vacuumed in time, PostgreSQL will **shut down** to prevent data corruption. Monitor `age(datfrozenxid)` at the database level and `age(relfrozenxid)` per table — values approaching 200M warrant investigation.

## 4. Interview Preparation

### Q: How does MVCC allow readers to never block writers in PostgreSQL?
**A:** Each writer creates a new physical tuple version rather than modifying the existing one. Readers continue to see the old version via their snapshot, which tells them the old tuple's `xmin` is committed and its `xmax` (the writer's xid) is still in-progress. No lock is needed because readers and writers operate on different physical copies of the data.

### Q: What happens physically when you UPDATE a row in PostgreSQL?
**A:** PostgreSQL inserts a brand-new tuple with the updated values on the heap (possibly the same page for HOT updates). The old tuple's `xmax` is set to the updating transaction's xid, and a ctid chain links old to new. All index entries must also be updated unless the update qualifies as HOT. The old tuple persists on disk as a dead tuple until VACUUM reclaims it.

### Q: How does PostgreSQL's MVCC differ from MySQL/InnoDB's approach?
**A:** InnoDB stores the current version of a row in the clustered index and maintains older versions in a separate **undo log** (rollback segment). Reads reconstruct old versions on-the-fly from the undo log. PostgreSQL stores ALL versions directly in the heap table, making writes simpler but requiring VACUUM to clean up dead versions. InnoDB's approach avoids bloat in the main table but adds complexity in undo log management and can suffer from "history list length" issues under heavy load.

### Q: Why is a long-running idle transaction dangerous in PostgreSQL?
**A:** A long-running transaction holds its snapshot's `xmin` horizon, which tells VACUUM "some transaction might still need to see tuples deleted after this point." VACUUM cannot reclaim any dead tuples newer than that horizon, causing unbounded table and index bloat. In extreme cases, it can also block xid freezing and push the database toward transaction ID wraparound shutdown.
