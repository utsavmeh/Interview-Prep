# Mastering PostgreSQL Transactions

## 1. Overview

* **What it is:** A transaction is a sequence of SQL statements treated as one all-or-nothing unit of work.
* **Why it exists:** It preserves invariants when one business operation changes multiple rows or tables. A payment should not be recorded without its order state changing, and a debit must not succeed without its matching credit.
* **When to use it:** Use one whenever several database changes must succeed or fail together, or when a read must be coordinated safely with a later write.
* **Common Misconceptions:**
  * *"Every individual SQL statement needs an explicit transaction."* (False: PostgreSQL runs each statement in its own implicit transaction when `BEGIN` is omitted.)
  * *"A transaction makes external side effects atomic."* (False: the database cannot roll back an email, HTTP request, or message already sent to another system.)
  * *"A rollback undoes a sequence value."* (False: sequences intentionally do not roll back, so gaps in IDs are normal.)

## 2. Core Concepts

### ACID and the Transaction Lifecycle

`BEGIN` starts a transaction, `COMMIT` makes its changes durable, and `ROLLBACK` discards them. Transactions provide atomicity, consistency, isolation, and durability; constraints and application logic are still responsible for defining what a consistent state means.

```sql
BEGIN;

UPDATE accounts SET balance_cents = balance_cents - 5_000
WHERE id = 1 AND balance_cents >= 5_000;

-- Check that the guarded debit affected exactly one row in application code.
UPDATE accounts SET balance_cents = balance_cents + 5_000
WHERE id = 2;

COMMIT;
```

If any statement raises an error, PostgreSQL marks the transaction as aborted. Every following command fails with `current transaction is aborted` until `ROLLBACK` (or a rollback to a savepoint). Do not catch and ignore a database error then keep issuing statements on the same transaction.

### Savepoints

Savepoints allow a recoverable portion of a larger transaction to be undone without losing the entire operation. PostgreSQL implements nested transaction-like behavior with `SAVEPOINT`, `ROLLBACK TO SAVEPOINT`, and `RELEASE SAVEPOINT`.

```sql
BEGIN;
INSERT INTO orders (id, status) VALUES (101, 'pending');

SAVEPOINT optional_coupon;
INSERT INTO coupon_redemptions (order_id, code) VALUES (101, 'WELCOME10');
-- Suppose the code is already redeemed and the unique constraint fails.
ROLLBACK TO SAVEPOINT optional_coupon;

-- The order still exists; record the failed coupon attempt instead.
INSERT INTO order_notes (order_id, body) VALUES (101, 'Coupon unavailable');
COMMIT;
```

### Constraints Are Part of the Transaction Boundary

Use database constraints as the final authority for invariants. `NOT NULL`, `CHECK`, foreign keys, and unique constraints protect data even when concurrent requests or a different application bypass validations. Some constraints can be deferred until commit, which is useful when temporarily inconsistent intermediate states are valid.

```sql
ALTER TABLE line_items
  ADD CONSTRAINT positive_quantity CHECK (quantity > 0);

ALTER TABLE employees
  ADD CONSTRAINT employees_manager_fk
  FOREIGN KEY (manager_id) REFERENCES employees(id)
  DEFERRABLE INITIALLY DEFERRED;

BEGIN;
-- Interdependent rows may be inserted in either order.
SET CONSTRAINTS ALL IMMEDIATE; -- optional: validate before COMMIT
COMMIT;
```

### Transactions and External Work: The Outbox Pattern

Never publish a message or call a payment provider inside a transaction and assume it is atomic. Commit an **outbox event** in the same database transaction as the state change, then have a separate worker publish that event with idempotency protection.

```sql
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = 101;
INSERT INTO outbox_events (topic, payload)
VALUES ('order.paid', jsonb_build_object('order_id', 101));
COMMIT;
```

The worker can safely retry delivery because the durable event proves that the state transition committed. Consumers must also be idempotent: at-least-once delivery is the practical default.

## 3. Best Practices for Lead Engineers

### 1. Keep Transactions Small, Fast, and Observable

Hold locks only around the database work that requires atomicity. Never put slow HTTP calls, user interaction, long computations, or batch processing inside a transaction. Set sensible `statement_timeout`, `lock_timeout`, and `idle_in_transaction_session_timeout`, and monitor sessions in `pg_stat_activity`.

### 2. Let the Database Enforce Critical Invariants

Application pre-checks are helpful for user-friendly errors but are inherently racy. Back them with a constraint and translate errors such as `unique_violation` or `foreign_key_violation` into the appropriate application response. This matters especially under concurrent writes.

### 3. Design Retriable, Idempotent Write Paths

Serialization failures, deadlocks, network disconnects after commit, and worker retries all happen. Assign request or event idempotency keys, use unique indexes to enforce them, and retry only the transaction after a transient error—never blindly repeat an external side effect.

### 4. Use Explicit Locks Only When the Invariant Requires Them

Prefer constraints and single-statement conditional updates first. Reach for `SELECT ... FOR UPDATE` when a decision truly depends on a stable row value across several statements. Lock rows in a consistent order to reduce deadlock risk.

## 4. Interview Preparation

### Q: What happens after one statement fails inside a PostgreSQL transaction?

**A:** PostgreSQL marks the transaction as aborted. It will not run further statements successfully because doing so could hide a partially failed unit of work. The client must issue `ROLLBACK`, or `ROLLBACK TO SAVEPOINT` if the failing work was enclosed by a savepoint.

### Q: Why are gaps in `SERIAL` or identity values normal after a rollback?

**A:** Sequences are deliberately non-transactional. Rolling sequence increments back would require coordination that harms concurrency, and concurrent transactions may have already observed later values. Primary keys identify rows; they should never be treated as contiguous business sequence numbers.

### Q: How do you make a database write and Kafka publish reliable together?

**A:** I would use the transactional outbox pattern: write the business change and an outbox record in one database transaction, commit, then publish the outbox record asynchronously. The publisher and consumer must be idempotent because delivery can be retried. This avoids the impossible distributed-transaction assumption between PostgreSQL and Kafka.

### Q: When would you use a savepoint?

**A:** When a bounded, optional part of a larger transaction can fail without invalidating the required work—for example, attempting a nonessential coupon redemption while still creating the order. It is not a substitute for keeping transactions small or for broad error suppression.
