# Mastering PostgreSQL Isolation Levels

## 1. Overview

* **What it is:** Isolation levels define what a transaction can observe when other transactions concurrently insert, update, or delete data.
* **Why it exists:** Concurrent requests need predictable read semantics without serializing every request and destroying throughput.
* **When to use it:** Choose the default for ordinary reads and writes; explicitly select a stronger level when a correctness rule depends on a stable snapshot or on preventing write skew.
* **Common Misconceptions:**
  * *"READ UNCOMMITTED permits dirty reads in PostgreSQL."* (False: PostgreSQL treats it as READ COMMITTED because its MVCC implementation never exposes uncommitted row versions.)
  * *"REPEATABLE READ is serializable."* (False: it provides a stable snapshot, but concurrent transactions can still produce anomalies that a serial execution could not.)
  * *"Higher isolation is always safer with no cost."* (False: it increases contention, retry requirements, or the lifetime of old snapshots.)

## 2. Core Concepts

### PostgreSQL's Three Effective Levels

| Level | Snapshot timing | What it prevents | Primary trade-off |
|---|---|---|---|
| `READ COMMITTED` (default) | New snapshot per statement | Dirty reads | Two `SELECT`s in one transaction can see different committed data |
| `REPEATABLE READ` | One snapshot for the whole transaction | Dirty and non-repeatable reads; PostgreSQL also prevents phantom reads in the snapshot | A concurrent update to a row you write can cause a serialization error |
| `SERIALIZABLE` | One snapshot plus Serializable Snapshot Isolation | All anomalies observable as non-serializable behavior | Transactions can abort and must be retried |

Set the level before the first query in a transaction:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM orders WHERE status = 'pending';
-- All later reads see the same committed snapshot.
COMMIT;
```

### READ COMMITTED: Statement-Level Snapshots

At the default level, each SQL statement sees rows committed before that statement began. This is excellent for short web-request transactions, but a read-modify-write sequence can be unsafe if it reads a value in Ruby and later writes a computed replacement.

```sql
-- Session A, READ COMMITTED
BEGIN;
SELECT balance_cents FROM accounts WHERE id = 1; -- sees 10_000
-- Session B commits balance_cents = 5_000
SELECT balance_cents FROM accounts WHERE id = 1; -- now sees 5_000
COMMIT;
```

Avoid lost updates with a single atomic statement or a row lock:

```sql
UPDATE accounts
SET balance_cents = balance_cents - 1_000
WHERE id = 1 AND balance_cents >= 1_000;
```

### REPEATABLE READ: A Stable Snapshot

`REPEATABLE READ` gives the entire transaction a consistent view of the database as it existed when its first query ran. Later commits from other transactions are invisible to its reads. PostgreSQL will raise `could not serialize access due to concurrent update` rather than silently let it update a row changed since that snapshot.

This level is useful for reports, exports, and a business operation that must reason over a stable group of rows. Keep such transactions short: their old snapshot can delay vacuum cleanup.

### SERIALIZABLE: Correctness Through Retry

`SERIALIZABLE` makes concurrent execution behave as if committed transactions ran one at a time, in some order. PostgreSQL detects dangerous dependency patterns and aborts one participant with SQLSTATE `40001` instead of returning an invalid result.

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- Both doctors appear on call at the transaction snapshot.
SELECT COUNT(*) FROM on_call WHERE day = CURRENT_DATE AND active;
-- Turn one doctor off only if another is still on call.
UPDATE on_call SET active = false WHERE doctor_id = 42;
COMMIT; -- may raise serialization_failure; retry the whole transaction
```

The application must retry the **entire** transaction with bounded exponential backoff. Retrying only its final statement is wrong because its decisions came from an obsolete snapshot.

## 3. Best Practices for Lead Engineers

### 1. Start With READ COMMITTED and Fix the Actual Race

The default is usually right for request-response workloads. Use atomic updates, unique constraints, and `ON CONFLICT` before elevating isolation. Stronger levels are not a replacement for a poorly expressed invariant.

### 2. Treat Serialization Failure as an Expected Result

At `SERIALIZABLE`—and sometimes `REPEATABLE READ`—SQLSTATE `40001` is a normal concurrency outcome. Centralize a small, bounded retry wrapper around an idempotent transaction. Ensure code inside it does not send emails or charge cards before commit.

### 3. Keep Stable-Snapshot Transactions Short

Long transactions consume connections and hold an old MVCC snapshot, which prevents vacuum from reclaiming dead tuples. Stream reports in pages or send them to a replica/background job rather than holding a multi-hour `REPEATABLE READ` transaction.

### 4. Test Concurrent Invariants Deliberately

Unit tests rarely reveal write skew. Build integration tests with two independent database connections and barriers so both transactions read before either writes. Test your retry behavior, not only the happy path.

## 4. Interview Preparation

### Q: How does READ COMMITTED behave in PostgreSQL?

**A:** Each statement sees a fresh MVCC snapshot of data committed before that statement began. It prevents dirty reads, but two reads in the same transaction can observe different committed values. It is PostgreSQL's default isolation level.

### Q: What is write skew, and how does SERIALIZABLE prevent it?

**A:** Write skew occurs when two transactions read the same predicate, make changes to different rows, and together violate an invariant—for example, each doctor sees another doctor on call and takes themselves off call. Row locks alone may not conflict because different rows change. Serializable Snapshot Isolation detects the dangerous read/write dependency and aborts one transaction for retry.

### Q: Why must a serialization failure retry the whole transaction?

**A:** The transaction made decisions from a snapshot that is no longer safe to serialize. Retrying only its final update preserves those stale decisions. Restarting obtains a new snapshot and reruns all reads and validations consistently.

### Q: Does PostgreSQL support dirty reads?

**A:** No. PostgreSQL maps `READ UNCOMMITTED` to `READ COMMITTED`, so even at the weakest declared level it does not expose another transaction's uncommitted tuple versions.
