# Mastering PostgreSQL Deadlocks

## 1. Overview

* **What it is:** A deadlock is a cycle of transactions where each holds a lock another transaction needs, so none can proceed.
* **Why it exists:** Locks protect correctness under concurrent writes; incompatible locks can be acquired in an order that creates a circular wait.
* **When to use it:** You do not use a deadlock intentionally—you design transactions to avoid them and make important write paths safe to retry when PostgreSQL resolves one.
* **Common Misconceptions:**
  * *"A deadlock is just a slow query."* (False: a slow query may cause lock waits, but a deadlock is a circular dependency that cannot resolve without aborting a participant.)
  * *"PostgreSQL will leave deadlocked transactions waiting forever."* (False: it detects the cycle and aborts one transaction with SQLSTATE `40P01`.)
  * *"Adding retries fixes the underlying design."* (False: retries provide resilience; consistent lock ordering removes the recurring cause.)

## 2. Core Concepts

### The Classic Two-Row Deadlock

Two transfers acquire the same account rows in opposite order. Each holds one row lock and waits on the other.

```sql
-- Session A
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 100 WHERE id = 1;
-- waits for id = 2
UPDATE accounts SET balance_cents = balance_cents + 100 WHERE id = 2;

-- Session B, concurrently
BEGIN;
UPDATE accounts SET balance_cents = balance_cents - 100 WHERE id = 2;
-- waits for id = 1: now there is a cycle
UPDATE accounts SET balance_cents = balance_cents + 100 WHERE id = 1;
```

After `deadlock_timeout` (one second by default), PostgreSQL examines the wait graph, cancels one transaction, and lets the other proceed. The canceled transaction is fully rolled back.

### Lock Waits Are Not Necessarily Deadlocks

A transaction waiting behind a long update has a single dependency, not a cycle. It may succeed when the blocker commits. Use `lock_timeout` to fail a request that should not wait, and inspect `pg_stat_activity` and `pg_locks` to find blockers.

```sql
SELECT waiting.pid AS waiting_pid,
       blocking.pid AS blocking_pid,
       waiting.query AS waiting_query,
       blocking.query AS blocking_query
FROM pg_stat_activity AS waiting
CROSS JOIN LATERAL unnest(pg_blocking_pids(waiting.pid)) AS b(pid)
JOIN pg_stat_activity AS blocking ON blocking.pid = b.pid
WHERE waiting.wait_event_type = 'Lock';
```

### Consistent Lock Ordering

The strongest defense is to acquire resources in a universal order—for example, ascending account ID—before applying updates. A single query can lock both rows in that order.

```sql
BEGIN;
SELECT id
FROM accounts
WHERE id IN (1, 2)
ORDER BY id
FOR UPDATE;

UPDATE accounts SET balance_cents = balance_cents - 100 WHERE id = 1;
UPDATE accounts SET balance_cents = balance_cents + 100 WHERE id = 2;
COMMIT;
```

Because all transfers lock account `1` before account `2`, one waits but a circular dependency cannot form.

### Row Locks and Queue Consumers

`FOR UPDATE SKIP LOCKED` is useful when many workers claim independent jobs: locked jobs are skipped instead of making every worker wait. It is intentionally not a fair queue and should not be used when skipping a locked row changes business correctness.

```sql
WITH next_job AS (
  SELECT id FROM jobs
  WHERE status = 'ready'
  ORDER BY priority DESC, created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs
SET status = 'processing', locked_at = NOW()
FROM next_job
WHERE jobs.id = next_job.id
RETURNING jobs.*;
```

## 3. Best Practices for Lead Engineers

### 1. Establish and Document a Lock Order

For every multi-row or multi-table write path, define the order resources are locked: parent before child, then ascending primary key, for example. Apply it in stored procedures, Rails services, migrations, and background jobs. Most production deadlocks come from two code paths following different implicit orders.

### 2. Make Transactions Short and Retry Deadlock Victims

Avoid holding locks while performing remote calls or expensive computations. Catch SQLSTATE `40P01`, retry the entire idempotent transaction a small number of times with jitter, and log the operation, involved resources, and retry count for diagnosis.

### 3. Instrument Blocking Before Raising Timeouts

Monitor lock-wait duration, deadlock count, and sessions `idle in transaction`. `log_lock_waits = on` with a useful `deadlock_timeout` produces actionable server logs. A larger timeout may hide symptoms; it does not fix the blocking path.

### 4. Use `NOWAIT` and `SKIP LOCKED` for Explicit Product Semantics

`NOWAIT` is appropriate when a user should immediately learn that an exclusive edit is in progress. `SKIP LOCKED` fits worker queues. Neither is a generic performance optimization: both deliberately change how contention is exposed to callers.

## 4. Interview Preparation

### Q: How does PostgreSQL resolve a deadlock?

**A:** PostgreSQL builds a wait-for graph after `deadlock_timeout`, detects the cycle, chooses one transaction as the victim, aborts it with `deadlock_detected` (`40P01`), and releases its locks. The other transaction can then continue. The application should retry the aborted unit of work if it is idempotent.

### Q: What is the best way to prevent deadlocks during money transfers?

**A:** Lock both account rows in a deterministic order, such as ascending account ID, inside a short transaction. Every transfer must follow that same order. Use a guarded or constrained update for balance invariants and retry a rare deadlock victim rather than assuming one cannot occur.

### Q: What is the difference between `lock_timeout` and `statement_timeout`?

**A:** `lock_timeout` limits only time spent waiting to acquire a lock. `statement_timeout` limits total statement execution time, including CPU, I/O, and lock waiting. A short `lock_timeout` protects latency-sensitive requests; `statement_timeout` is a broader guardrail against runaway queries.

### Q: When is `SKIP LOCKED` appropriate?

**A:** It is ideal for competing workers claiming independent work items, where processing another ready job is acceptable if the first is locked. It is inappropriate for financial or user-facing workflows where silently skipping a locked row could violate ordering, fairness, or correctness.
