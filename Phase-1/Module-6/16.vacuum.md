# Mastering PostgreSQL VACUUM

## 1. Overview

* **What it is:** `VACUUM` is PostgreSQL's maintenance process for reclaiming space from MVCC-dead tuples, updating visibility information, and preventing transaction-ID wraparound.
* **Why it exists:** Updates and deletes create obsolete row versions instead of overwriting or removing them immediately. Without cleanup, tables and indexes bloat and eventually risk wraparound protection shutdown.
* **When to use it:** Autovacuum should run continuously in every production database. Use manual `VACUUM`, `ANALYZE`, or focused tuning when metrics show a high-churn table falling behind.
* **Common Misconceptions:**
  * *"VACUUM immediately returns disk space to the operating system."* (False: ordinary vacuum makes space reusable inside the table; it normally does not shrink the physical file.)
  * *"VACUUM FULL is a harmless stronger vacuum."* (False: it rewrites the table and requires an `ACCESS EXCLUSIVE` lock.)
  * *"Autovacuum is optional for a small application."* (False: it is essential to MVCC health and transaction-ID wraparound safety at every scale.)

## 2. Core Concepts

### Dead Tuples, Visibility Maps, and Reuse

When an update or delete commits, old tuple versions cannot be removed until no active transaction could still see them. Vacuum marks their storage reusable through the free space map and updates the visibility map, which can enable index-only scans. Ordinary vacuum runs concurrently with normal reads and writes, although it takes lighter locks at phases of its work.

```sql
-- Reclaim dead tuples for future reuse and refresh planner statistics.
VACUUM (ANALYZE, VERBOSE) orders;
```

`ANALYZE` samples table data to refresh planner statistics. It is related but distinct maintenance; autovacuum can run vacuum, analyze, or both depending on their separate thresholds.

### Autovacuum Thresholds

For vacuum, a table becomes eligible approximately when:

```text
dead_tuples > autovacuum_vacuum_threshold
              + autovacuum_vacuum_scale_factor × estimated_live_tuples
```

The defaults are often too slow for very large or high-churn tables. On a 100-million-row table, a 20% scale factor means roughly 20 million dead tuples before vacuum starts. Use per-table settings instead of globally making workers aggressive without measurement.

```sql
ALTER TABLE audit_events SET (
  autovacuum_vacuum_scale_factor = 0.02,
  autovacuum_vacuum_threshold = 5_000,
  autovacuum_analyze_scale_factor = 0.02
);
```

### Monitoring Vacuum Health

`n_dead_tup` is an estimate, but it is a valuable early-warning signal when paired with autovacuum timestamps and table size.

```sql
SELECT relname,
       n_live_tup,
       n_dead_tup,
       last_autovacuum,
       last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 20;

SELECT pid, usename, state, xact_start, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

An old `xact_start` may reveal a long-running transaction that prevents vacuum from removing tuples. An `idle in transaction` session is especially dangerous because it holds a snapshot without doing useful work.

### Vacuum Full, Reindex, and Online Alternatives

`VACUUM FULL` rewrites a table into a compact new file and releases disk space to the OS, but it blocks reads and writes with an exclusive lock. Prefer maintenance windows or online tools such as `pg_repack` when reclaiming severe bloat. Use `REINDEX CONCURRENTLY` for an individual bloated index when supported; it avoids blocking normal reads and writes for the entire rebuild.

```sql
-- Requires a maintenance window; blocks concurrent access.
VACUUM FULL orders;

-- Lower-impact index rebuild (run outside a transaction block).
REINDEX INDEX CONCURRENTLY index_orders_on_customer_id;
```

## 3. Best Practices for Lead Engineers

### 1. Treat Autovacuum as Production-Critical Capacity

Monitor autovacuum worker saturation, dead tuples, table growth, transaction age, and vacuum duration. Ensure the server has enough workers, I/O capacity, and memory for the workload. Disabling autovacuum to reduce temporary I/O simply transfers the cost into bloat and an eventual incident.

### 2. Tune High-Churn Tables Per Table

Queues, sessions, audit logs, and frequently-updated counters behave differently from mostly append-only data. Lower their vacuum and analyze scale factors; use an appropriate fillfactor for update-heavy tables to leave room for HOT updates. Measure after each change.

### 3. Find Snapshot Blockers First

If vacuum is running but dead tuples do not fall, inspect long-running transactions, prepared transactions, and replication slots. Killing or fixing the blocker is safer and more effective than repeatedly running manual vacuum.

### 4. Plan Bloat Remediation, Do Not Improvise It

Estimate free disk space, lock impact, replication lag, and rollback before a table rewrite. `VACUUM FULL` may require substantial extra space and can cause an outage; choose a maintenance window or an online-repack approach deliberately.

## 4. Interview Preparation

### Q: Why does PostgreSQL need VACUUM?

**A:** MVCC leaves old tuple versions after updates and deletes so concurrent snapshots remain valid. Vacuum removes versions no longer visible to any transaction, makes their space reusable, maintains visibility data, and freezes old transaction IDs to prevent wraparound. It is a core part of PostgreSQL's storage model, not an optional cleanup task.

### Q: What is the difference between VACUUM and VACUUM FULL?

**A:** Ordinary `VACUUM` works alongside normal activity and returns dead-tuple space to the table's free space map for future reuse, but typically does not shrink the file. `VACUUM FULL` rewrites the entire table to compact it and return disk space to the OS, at the cost of an `ACCESS EXCLUSIVE` lock and extra temporary disk requirements.

### Q: How can a long-running transaction cause bloat?

**A:** Its old MVCC snapshot might still need to see tuples that newer transactions deleted or replaced. Vacuum cannot remove those tuples until the old transaction ends, so dead tuples accumulate even if autovacuum is active. `idle in transaction` sessions are common offenders.

### Q: Why should you tune autovacuum per table?

**A:** Autovacuum thresholds are proportional to table size. A default suitable for a small, mostly static table can allow millions of dead tuples on a large, update-heavy table. Per-table scale factors and thresholds align maintenance frequency with each table's write rate and performance requirements.
