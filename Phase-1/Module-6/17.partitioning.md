# Mastering PostgreSQL Partitioning

## 1. Overview

* **What it is:** Declarative partitioning divides one logical table into smaller physical child tables according to a partition key.
* **Why it exists:** It makes very large, naturally segmented datasets easier to retain, delete, index, and query by allowing PostgreSQL to prune irrelevant partitions.
* **When to use it:** Use it for proven large tables with a natural range, list, or hash key—especially time-series events, tenant-isolated data, or retention-heavy logs. Do not use it as a default substitute for indexes or query tuning.
* **Common Misconceptions:**
  * *"Partitioning automatically makes every query fast."* (False: pruning requires predicates that match the partition key; queries touching all partitions can become slower.)
  * *"A partitioned table has one global unique index."* (False: PostgreSQL unique and primary-key constraints on a partitioned table must include all partition-key columns.)
  * *"Partitioning is the same as sharding."* (False: partitions live in one PostgreSQL cluster and share its resources; sharding distributes data across independent databases.)

## 2. Core Concepts

### Partitioning Strategies

* **Range:** partitions contiguous value ranges; ideal for timestamps and monotonically increasing IDs.
* **List:** assigns known discrete values; useful for a small, stable set of regions or categories.
* **Hash:** distributes a key across a fixed number of buckets; useful when no range predicate exists and write distribution matters.

```sql
CREATE TABLE events (
  id bigint GENERATED ALWAYS AS IDENTITY,
  occurred_at timestamptz NOT NULL,
  account_id bigint NOT NULL,
  payload jsonb NOT NULL
) PARTITION BY RANGE (occurred_at);

CREATE TABLE events_2026_09
  PARTITION OF events
  FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

CREATE INDEX ON events_2026_09 (account_id, occurred_at DESC);
```

The parent is a routing and query surface; inserts are routed to a child whose bounds accept the partition key. Create future partitions ahead of time or maintain a controlled default partition so that an unexpected date does not break ingestion.

### Partition Pruning

The planner excludes partitions it can prove cannot satisfy the query. This is the chief read-performance benefit, and it depends on queries filtering the partition key with sargable expressions.

```sql
EXPLAIN
SELECT count(*)
FROM events
WHERE occurred_at >= '2026-09-01'
  AND occurred_at <  '2026-10-01';
-- Plan should reference events_2026_09, not every event partition.
```

Avoid wrapping the key in a function such as `DATE(occurred_at) = ...`; use a range predicate instead. Parameterized queries can use run-time pruning, but validate it with `EXPLAIN` on representative application queries.

### Retention Through Detach and Drop

For time-based retention, dropping a whole old partition is vastly cheaper than deleting millions of rows: it avoids row-by-row work, index churn, and vacuum debt.

```sql
ALTER TABLE events DETACH PARTITION events_2025_09;
DROP TABLE events_2025_09;
```

Detaching first can make the lifecycle explicit and lets you archive or validate the old data. Account for locks and your PostgreSQL version's detach behavior in the operational runbook.

### Constraints, Keys, and Indexes

Indexes are created per partition (a parent-level index command creates corresponding child indexes). Foreign-key and unique-key design requires care. A primary key on a partitioned table must include the partition key because PostgreSQL cannot enforce uniqueness across arbitrary child tables without it.

```sql
-- Valid: uniqueness is enforceable within each occurred_at range.
ALTER TABLE events ADD PRIMARY KEY (id, occurred_at);

-- A bare PRIMARY KEY (id) is not valid as a global partitioned-table key.
```

This may change API assumptions. If callers need a globally unique identifier, use a UUID and enforce its uniqueness through application design or a separate registry table, while understanding the added write path.

## 3. Best Practices for Lead Engineers

### 1. Partition for a Concrete Operational Problem

Adopt partitioning when retention deletion, maintenance windows, or index size on a measured large table is hurting you. Define the key, interval, partition count, growth forecast, query shapes, and archival procedure before migration. A small table split into hundreds of partitions makes planning and operations worse.

### 2. Automate the Entire Partition Lifecycle

Create future partitions before inserts arrive; apply indexes and permissions consistently; alert if the default partition receives data; detach/archive/drop old partitions on a defined schedule. Treat the schedule as production infrastructure, not a manual DBA ritual.

### 3. Keep the Partition Count Reasonable

Hundreds of well-sized partitions may be appropriate; thousands can add planning overhead and complicate migrations. Pick weekly, monthly, or quarterly intervals from data volume, retention requirements, and query windows—not from calendar aesthetics.

### 4. Verify Pruning and Migration Behavior With Real Queries

Use `EXPLAIN (ANALYZE, BUFFERS)` to confirm only intended partitions are scanned. Test inserts at boundaries, late-arriving data, default-partition handling, key constraints, and `ATTACH PARTITION` validation on staging-scale data.

## 4. Interview Preparation

### Q: When is PostgreSQL partitioning a good fit?

**A:** It fits a very large table with a natural key that queries frequently filter by, and where partition-level operations provide a material benefit—for example, monthly event data with a one-year retention policy. Dropping old monthly partitions becomes nearly instantaneous compared with deleting and vacuuming billions of rows.

### Q: What is partition pruning?

**A:** It is the planner's elimination of partitions whose bounds cannot match a query predicate. A query constrained to a September timestamp range should scan only the September partition. The query must use the partition key in a form the planner can reason about; otherwise all partitions may be visited.

### Q: Why must a partitioned-table primary key include the partition key?

**A:** PostgreSQL enforces indexes separately in child partitions. Including the partition key ensures two rows with the same complete key must fall in the same child, so per-partition uniqueness is sufficient. A unique `id` alone could be duplicated in different partitions without a global index.

### Q: How does partitioning differ from sharding?

**A:** Partitioning divides one table inside one database cluster; SQL queries, transactions, backups, and resource limits remain within that cluster. Sharding splits data across separate database instances and introduces routing, cross-shard queries, and distributed operational complexity.
