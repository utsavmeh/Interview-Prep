# Mastering PostgreSQL JSONB

## 1. Overview

* **What it is:** `JSONB` is PostgreSQL's binary JSON type: it stores parsed JSON in a normalized representation that supports operators, containment queries, and indexes.
* **Why it exists:** It gives relational applications a practical place for semi-structured data whose fields vary by event, integration, or product configuration without forcing every variation into a migration.
* **When to use it:** Use it for flexible metadata, webhook payloads, sparse settings, and attributes that are rarely joined or constrained. Use typed relational columns for stable, frequently filtered, joined, or integrity-critical facts.
* **Common Misconceptions:**
  * *"JSONB is always better than JSON."* (False: `JSON` preserves original text, including whitespace and duplicate keys; use it only when preserving that exact input matters.)
  * *"JSONB removes the need for schema design."* (False: it trades database-enforced shape and planner statistics for flexibility.)
  * *"A GIN index makes every JSONB query fast."* (False: operator class, query operator, selectivity, and index size all matter.)

## 2. Core Concepts

### JSON vs. JSONB

`JSON` stores the original JSON text and reparses it on access. `JSONB` stores a decomposed binary form; it is normally faster to query, supports indexing, does not preserve key order, and keeps only the final value for duplicate keys. In application tables, prefer `JSONB` unless exact lexical preservation is a requirement.

```sql
CREATE TABLE webhook_events (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  provider text NOT NULL,
  payload jsonb NOT NULL,
  received_at timestamptz NOT NULL DEFAULT now()
);
```

### Reading and Filtering JSONB

`->` returns JSONB, `->>` returns text, `#>` and `#>>` traverse a path, and `@>` checks containment. Use the text-returning operators when comparing a scalar to SQL text or casting it.

```sql
-- Read a top-level string and nested amount.
SELECT payload->>'event_type' AS event_type,
       (payload #>> '{data,amount_cents}')::integer AS amount_cents
FROM webhook_events;

-- Contains this structure; extra keys are allowed.
SELECT * FROM webhook_events
WHERE payload @> '{"event_type":"payment.succeeded"}'::jsonb;

-- Key existence at the top level.
SELECT * FROM webhook_events WHERE payload ? 'request_id';
```

### Updating JSONB Safely

JSONB values are immutable from SQL's perspective: an update writes a new value and participates in normal MVCC behavior. `jsonb_set` replaces or creates a path; concatenation with `||` merges top-level objects, with right-side keys winning.

```sql
UPDATE webhook_events
SET payload = jsonb_set(
  payload,
  '{processing,status}',
  to_jsonb('completed'::text),
  true
)
WHERE id = 42;

UPDATE webhook_events
SET payload = payload || '{"replayed": true}'::jsonb
WHERE id = 42;
```

Frequent updates to a large document create new tuple versions and can cause table and index bloat. Keep mutable, frequently changed fields in ordinary columns instead.

### Indexing JSONB

A general GIN index supports broad containment and key-existence queries. `jsonb_path_ops` is smaller and faster for `@>` containment, but supports fewer operators. For a single common scalar extraction, an expression B-tree index is usually smaller and more selective.

```sql
-- Flexible containment / key lookup queries.
CREATE INDEX webhook_events_payload_gin
ON webhook_events USING gin (payload);

-- Smaller option when application queries primarily use @>.
CREATE INDEX webhook_events_payload_path_gin
ON webhook_events USING gin (payload jsonb_path_ops);

-- Best for a hot, targeted equality filter.
CREATE INDEX webhook_events_event_type_idx
ON webhook_events ((payload->>'event_type'));
```

Do not create both GIN indexes without measured query needs. Use `EXPLAIN (ANALYZE, BUFFERS)` to validate the operator and index actually match.

## 3. Best Practices for Lead Engineers

### 1. Normalize Stable, Important Fields

If a value participates in joins, uniqueness, foreign keys, range scans, sorting, authorization, or common reporting, give it a typed column. A sound hybrid model keeps the durable relational core in columns and preserves variable integration metadata in JSONB.

### 2. Put Guardrails Around Flexible Documents

Use `NOT NULL`, generated columns, `CHECK` constraints, and application-level schema validation where needed. For example, a generated `event_type` column can expose a JSONB field to a normal index and make its expected presence explicit.

```sql
ALTER TABLE webhook_events
ADD COLUMN event_type text
  GENERATED ALWAYS AS (payload->>'event_type') STORED;

CREATE INDEX ON webhook_events (provider, event_type);
```

### 3. Index Query Shapes, Not the Data Type

Start from the production predicates. Choose an expression B-tree index for a specific extracted value, a partial index for a sparse subset, or GIN for genuinely flexible containment. Measure index write cost and storage: broad GIN indexes can be expensive on high-ingest tables.

### 4. Keep Raw Payloads Separate From Application State

For inbound webhooks, store the immutable original payload for audit/replay, but extract validated business fields into relational tables. Do not let downstream logic repeatedly reinterpret arbitrary JSON; it makes constraints, migrations, and observability much harder.

## 4. Interview Preparation

### Q: What is the difference between JSON and JSONB in PostgreSQL?

**A:** `JSON` stores the original text and preserves formatting, key order, and duplicate keys. `JSONB` stores a parsed binary representation, normalizes object keys, supports containment operations and indexes, and is generally the correct choice for queryable application data. Use `JSON` only when exact input representation must be retained.

### Q: When would you use JSONB instead of normalized columns?

**A:** For genuinely variable, low-relationality data such as third-party webhook metadata or optional product attributes. I would not use it for a field that needs joins, foreign keys, frequent reporting, or strong validation; those are signals to model a typed column or related table.

### Q: How would you index `payload->>'event_type'`?

**A:** For common equality filters, I would create an expression B-tree index: `CREATE INDEX ... ON events ((payload->>'event_type'));`. A broad GIN index is appropriate only if the workload needs varied containment or key-existence searches across the document. I would confirm the choice with `EXPLAIN ANALYZE`.

### Q: What are the downsides of frequently updating a large JSONB document?

**A:** Each update creates a new MVCC tuple version, rewrites the JSONB value, and may update large GIN indexes. That raises write amplification and bloat. Move frequently changing attributes into ordinary columns or a narrower related table, and keep JSONB primarily for relatively immutable flexible data.
